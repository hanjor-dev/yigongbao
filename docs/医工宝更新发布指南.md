# 医工宝更新发布指南

本文档用于规范医工宝后端、PC 前端和 H5 前端的版本发布、数据库更新、镜像构建和生产部署流程。

## 一、版本号规范

版本号统一采用 SemVer 格式，例如 `v1.0.1`。同一版本的三个代码仓库、数据库脚本和 Docker 镜像使用相同版本号。

生产环境变量名称统一为 `APP_VERSION`，禁止使用 `APP_IMAGE_TAG` 或 `APP_VERISON`。

```env
APP_VERSION=v1.0.1
```

## 二、分支模型

```text
codex/*           本地工作区开发分支
dev               最新生产候选及构建分支
main              正式生产发布分支
release/vX.Y.Z    已发布版本的冻结留存分支
hotfix/*          生产版本修复分支
```

- `codex/*` 只在本地使用，不推送到远程。
- `dev` 用于合并完成开发和测试的工作区内容。
- `main` 只接收已经确认发布的 `dev` 内容。
- `release/vX.Y.Z` 用于固定正式版本，创建后禁止继续修改。
- 不再创建普通的 `feature/*` 分支。

## 三、发布前准备

### 1. 更新 PC 前端版本号

将 PC 前端右上角显示的旧版本号修改为本次版本，例如：

```text
v1.0.0 → v1.0.1
```

修改后提交到 PC 前端仓库的 `dev` 分支，并完成前端构建验证。

### 2. 确认发布内容

- 后端、PC 前端和 H5 前端代码已经合并到各自的 `dev` 分支；
- 数据库脚本已经提交并包含在本次发布内容中；
- 后端测试、前端构建和必要的联调已经通过；
- 三个仓库使用相同的版本号。

## 四、将 `dev` 合并到 `main`

以下以后端仓库为例，PC 前端和 H5 前端仓库如果也维护 `dev`、`main`，执行相同流程。

```bash
git fetch origin
git switch dev
git pull --ff-only origin dev
git switch main
git pull --ff-only origin main
git merge --no-ff dev -m "发布 v1.0.1"
git push origin main
```

发布前可检查：

```bash
git status
git branch --show-current
git log --oneline -5
```

`main` 推送成功后，阿里云构建规则会自动触发生产镜像构建。

## 五、固定版本分支和标签

确认 `main` 推送成功后，在 `main` 当前提交上创建版本标签和版本留存分支：

```bash
git switch main
git pull --ff-only origin main
git tag -a v1.0.1 -m "发布 v1.0.1"
git push origin v1.0.1
git switch -c release/v1.0.1
git push -u origin release/v1.0.1
```

此时：

```text
main              后续继续接收新版本
release/v1.0.1    固定保存 v1.0.1，不再修改
v1.0.1            固定指向本次发布提交
```

三个仓库应使用相同的版本名称：`release/v1.0.1`。

## 六、阿里云构建镜像

进入阿里云容器镜像服务的构建规则，确认：

| 配置项 | 值 |
|---|---|
| 构建类型 | `Branch` |
| Branch/Tag | `main` |
| Dockerfile 目录 | `/` |
| Dockerfile 文件名 | `Dockerfile` |
| 镜像版本 | `v1.0.1` |

镜像版本必须与服务器 `.env` 中的 `APP_VERSION` 完全一致，禁止使用 `latest`。

构建完成后，确认仓库中存在 `yigongbao-app:v1.0.1`。

## 七、数据库更新

数据库脚本必须在拉取新镜像和启动服务之前执行。

### 1. 确认数据库脚本

脚本必须已经提交到本次发布版本，并在测试环境执行验证。建议使用明确的脚本名称，例如：

```text
sql/migration-production-process-params-zip-bag-seal-temperature-20261012.sql
```

执行前确认脚本具备幂等性、不会破坏生产数据，并已经准备必要的回滚方案。

### 2. 备份生产数据库

```bash
cd /path/to/yigongbao
mkdir -p backups
docker compose exec -T mysql sh -c 'mysqldump -uroot -p"${MYSQL_ROOT_PASSWORD}" "${MYSQL_DATABASE}"' > "backups/yigongbao_before_v1.0.1_$(date +%Y%m%d%H%M%S).sql"
ls -lh backups/
```

### 3. 执行数据库迁移

如果服务器项目目录已经同步了本次版本的 SQL 文件：

```bash
docker compose exec -T mysql sh -c 'mysql -uroot -p"${MYSQL_ROOT_PASSWORD}" "${MYSQL_DATABASE}"' < sql/migration-production-process-params-zip-bag-seal-temperature-20261012.sql
```

执行后检查数据库表结构、关键字段和数据。

> 注意：`docker-entrypoint-initdb.d` 只在 MySQL 数据卷首次初始化时执行。生产环境已有数据卷时，新增 SQL 文件不会自动执行，必须手动执行或接入数据库迁移工具。

## 八、配置版本并部署

### 1. 设置生产版本

```bash
cd /path/to/yigongbao
vim .env
```

设置：

```env
APP_VERSION=v1.0.1
```

确认配置：

```bash
grep '^APP_VERSION=' .env
```

### 2. 拉取指定版本镜像

数据库迁移成功后执行：

```bash
docker compose -f docker-compose.prod.yml pull app
```

### 3. 启动或更新服务

```bash
docker compose -f docker-compose.prod.yml up -d
docker compose -f docker-compose.prod.yml ps
docker compose -f docker-compose.prod.yml logs -f app
```

## 九、发布后验证

- 应用容器状态为 `Up`；
- 应用健康检查正常；
- PC 前端显示正确版本号；
- 登录、核心业务接口、文件上传和 WebSocket 正常；
- 数据库迁移已经执行完成。

查看当前运行镜像：

```bash
docker inspect yigongbao-app --format '{{.Config.Image}}'
```

结果应包含：`yigongbao-app:v1.0.1`。

## 十一、问题回滚

将服务器 `.env` 修改为上一个稳定版本：

```env
APP_VERSION=v1.0.1
```

重新拉取并启动：

```bash
docker compose -f docker-compose.prod.yml pull app
docker compose -f docker-compose.prod.yml up -d
docker compose -f docker-compose.prod.yml logs -f app
```

回滚时必须使用明确的历史版本号，不得使用 `latest`。

## 十二、完整发布顺序

```text
1. 更新 PC 前端左上角版本号
2. 确认三个仓库代码和数据库脚本
3. 完成 dev → main 合并
4. 创建 release/v1.0.1 和 v1.0.1 标签
5. 在阿里云构建 v1.0.1 镜像
6. 备份生产数据库
7. 执行数据库迁移脚本
8. 设置 APP_VERSION=v1.0.1
9. 拉取 v1.0.1 镜像
10. 启动服务并完成验证
11. 记录三个仓库 commit、数据库脚本和镜像版本
```
