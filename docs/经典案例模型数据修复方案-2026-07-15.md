# 经典案例模型数据关联丢失问题 - 完整修复方案

**生成时间**：2026-07-15  
**问题级别**：🔴 严重 - 生产环境数据损坏  
**影响范围**：所有已标记为经典案例的订单  

---

## 一、问题描述

### 1.1 症状表现

查询经典案例的模型数据时，**只能获取到模型的ID，但无法获取文件的详细信息**（文件名、路径、URL等字段为空）。

### 1.2 影响范围

- ✗ design_model表的file_id指向已删除的file_detail记录
- ✗ order_file表的file_id指向已删除的file_detail记录
- ✗ file_detail表中的URL存在文件名重复问题

---

## 二、根本原因分析

### 2.1 三个关键BUG

#### BUG 1：x-file-storage的move()机制

**问题**：x-file-storage框架的`move()`操作采用"创建新记录+删除旧记录"策略，而不是"更新现有记录"。

```
旧文件记录：id=A, url=/visual_model/xxx.stl, is_deleted=1 (已删除)
新文件记录：id=B, url=/classic-cases/xxx.stl, is_deleted=0 (新建)
业务表：file_id=A (❌ 还指向旧ID，查询时找不到记录)
```

#### BUG 2：路径拼接错误

**错误代码**：
```java
String newPath = newBasePath + oldFileInfo.getFilename(); // ❌
```

导致URL中文件名重复：
```
错误：/classic-cases/202607150001/model.stlmodel.stl
正确：/classic-cases/202607150001/model.stl
```

**⚠️ 关键说明：OSS文件路径问题**

由于buggy代码在`setPath()`时已包含文件名，x-file-storage再次拼接文件名后，**OSS上实际存储的文件路径就是重复的**（如`model.stlmodel.stl`）。

**影响修复策略**：
- ✅ 脚本6（更新design_model.file_id）：安全可执行
- ⚠️ 脚本12（修复URL）：**仅适用于文件已在OSS重命名的情况**
- 对于旧数据：数据库URL虽重复但反映真实OSS路径，"修复"会导致404

**处理建议**：
- 新数据（代码已修复）：正常执行所有脚本
- 旧数据（buggy代码创建）：仅执行脚本6，跳过脚本12

#### BUG 3：缺少业务表更新逻辑

文件迁移后，**没有更新业务表的file_id关联**，导致：
- design_model.file_id 还是旧ID
- order_file.file_id 还是旧ID

### 2.2 日志证据

从测试日志可以看到完整的问题过程：

```log
2026-07-15 13:40:52.341 保存文件记录成功，id=2077267130512281601
2026-07-15 13:40:52.451 删除文件记录，url=visual_model/202607/xxx.stl
```

**结论**：move()操作先创建新记录（新ID），再删除旧记录（旧ID），但业务表未更新。

## 三、修复方案设计

### 3.1 匹配逻辑设计

**❌ 不可行方案**：仅使用filename匹配
- 如果同一订单有多个同名文件会导致映射混乱

**✅ 推荐方案**：多重约束+防重复机制

1. **同一订单约束**：通过order_code限定范围
2. **文件名匹配**：filename + original_filename双重匹配
3. **时间窗口**：新文件创建时间在旧文件删除后1小时内
4. **防重复机制**：使用ROW_NUMBER()确保一对一映射
5. **冲突检测**：显示match_count，人工介入处理冲突

### 3.2 修复步骤

```
步骤1：分析脚本 → 确认问题范围
步骤2：预览脚本 → 验证映射关系正确
步骤3：开启事务 → START TRANSACTION
步骤4：执行修复 → UPDATE三个表
步骤5：验证结果 → 确认修复成功
步骤6：提交事务 → COMMIT
```

## 四、完整SQL脚本

### 4.1 问题分析脚本

```sql
-- ============================================================
-- 第一部分：问题诊断与分析
-- ============================================================

-- 1. 查找所有经典案例订单及其问题统计
SELECT 
    om.id AS order_id,
    om.order_code,
    om.is_classic_case,
    om.create_time AS order_create_time,
    COUNT(DISTINCT dm.id) AS total_model_count,
    SUM(CASE WHEN fd.is_deleted = 1 THEN 1 ELSE 0 END) AS broken_model_count,
    SUM(CASE WHEN fd.is_deleted = 0 THEN 1 ELSE 0 END) AS valid_model_count
FROM order_main om
LEFT JOIN design_model dm ON dm.order_id = om.id AND dm.is_deleted = 0
LEFT JOIN file_detail fd ON fd.id = dm.file_id
WHERE om.is_classic_case = 1
GROUP BY om.id, om.order_code, om.is_classic_case, om.create_time
ORDER BY om.create_time DESC;

-- 2. 查找design_model表中指向已删除文件的明细
SELECT 
    dm.id AS model_id,
    dm.order_id,
    om.order_code,
    dm.file_id AS old_file_id,
    fd.filename,
    fd.original_filename,
    fd.url AS old_url,
    fd.is_deleted,
    fd.create_time AS file_create_time,
    fd.update_time AS file_delete_time
FROM design_model dm
JOIN order_main om ON om.id = dm.order_id AND om.is_classic_case = 1
JOIN file_detail fd ON fd.id = dm.file_id
WHERE dm.is_deleted = 0
  AND fd.is_deleted = 1
ORDER BY dm.order_id, dm.id;

-- 3. 查找order_file表中指向已删除文件的明细
SELECT 
    o.id AS order_file_id,
    o.order_id,
    om.order_code,
    o.file_id AS old_file_id,
    o.file_category,
    fd.filename,
    fd.url AS old_url,
    fd.is_deleted
FROM order_file o
JOIN order_main om ON om.id = o.order_id AND om.is_classic_case = 1
JOIN file_detail fd ON fd.id = o.file_id
WHERE o.is_deleted = 0
  AND fd.is_deleted = 1
ORDER BY o.order_id, o.id;

-- 4. 查找file_detail表中URL重复的记录
SELECT 
    id,
    url,
    path,
    filename,
    create_time
FROM file_detail
WHERE url LIKE '%classic-cases%'
  AND url LIKE CONCAT('%', filename, filename)
  AND is_deleted = 0
ORDER BY create_time DESC;
```

### 4.2 design_model表修复脚本

```sql
-- ============================================================
-- 第二部分：design_model表file_id修复
-- ============================================================

-- 5. 预览design_model的映射关系（带冲突检测）
WITH matched_files AS (
    SELECT 
        dm.id AS model_id,
        dm.order_id,
        om.order_code,
        dm.file_id AS old_file_id,
        new_fd.id AS new_file_id,
        old_fd.filename,
        old_fd.original_filename,
        old_fd.url AS old_url,
        new_fd.url AS new_url,
        old_fd.update_time AS old_delete_time,
        new_fd.create_time AS new_create_time,
        TIMESTAMPDIFF(MINUTE, old_fd.update_time, new_fd.create_time) AS time_gap_minutes,
        -- 防止一对多映射
        ROW_NUMBER() OVER (
            PARTITION BY dm.id 
            ORDER BY new_fd.create_time ASC
        ) AS rn,
        -- 检测冲突
        COUNT(*) OVER (PARTITION BY dm.id) AS match_count
    FROM design_model dm
    JOIN order_main om ON om.id = dm.order_id AND om.is_classic_case = 1
    JOIN file_detail old_fd ON old_fd.id = dm.file_id 
        AND old_fd.is_deleted = 1
        AND old_fd.url NOT LIKE '%classic-cases%'
    JOIN file_detail new_fd 
        ON new_fd.filename = old_fd.filename
        AND new_fd.original_filename = old_fd.original_filename
        AND new_fd.url LIKE CONCAT('%classic-cases/', om.order_code, '/%')
        AND new_fd.is_deleted = 0
        AND new_fd.create_time > old_fd.update_time
    WHERE dm.is_deleted = 0
)
SELECT 
    *,
    CASE 
        WHEN match_count > 1 THEN '⚠️ 警告：有多个匹配'
        ELSE '✓ 唯一匹配'
    END AS match_status
FROM matched_files 
WHERE rn = 1
ORDER BY order_id, model_id;

-- ⚠️ 执行前检查：确保上面的预览结果中所有记录都是"唯一匹配"！

-- 6. 执行design_model表的file_id更新
UPDATE design_model dm
JOIN order_main om ON om.id = dm.order_id AND om.is_classic_case = 1
JOIN file_detail old_fd ON old_fd.id = dm.file_id 
    AND old_fd.is_deleted = 1
    AND old_fd.url NOT LIKE '%classic-cases%'
JOIN (
    SELECT 
        dm2.id AS model_id,
        new_fd.id AS new_file_id,
        ROW_NUMBER() OVER (
            PARTITION BY dm2.id 
            ORDER BY new_fd.create_time ASC
        ) AS rn
    FROM design_model dm2
    JOIN order_main om2 ON om2.id = dm2.order_id AND om2.is_classic_case = 1
    JOIN file_detail old_fd2 ON old_fd2.id = dm2.file_id 
        AND old_fd2.is_deleted = 1
    JOIN file_detail new_fd 
        ON new_fd.filename = old_fd2.filename
        AND new_fd.original_filename = old_fd2.original_filename
        AND new_fd.url LIKE CONCAT('%classic-cases/', om2.order_code, '/%')
        AND new_fd.is_deleted = 0
        AND new_fd.create_time > old_fd2.update_time
    WHERE dm2.is_deleted = 0
) AS mapping ON mapping.model_id = dm.id AND mapping.rn = 1
SET dm.file_id = mapping.new_file_id
WHERE dm.is_deleted = 0;

-- 7. 验证design_model表修复结果
-- 预期：返回0条记录
SELECT COUNT(*) AS remaining_broken_count
FROM design_model dm
JOIN order_main om ON om.id = dm.order_id AND om.is_classic_case = 1
WHERE dm.is_deleted = 0
  AND dm.file_id IN (SELECT id FROM file_detail WHERE is_deleted = 1);
```

### 4.4 file_detail表URL修复脚本

**⚠️ 执行决策：何时执行此部分脚本**

| 数据类型 | 是否执行 | 说明 |
|---------|---------|------|
| **新数据**（代码修复后创建） | ✅ 跳过 | URL已正确，无需修复 |
| **旧数据**（buggy代码创建） | ⚠️ **不推荐** | OSS文件路径确实重复，修复URL会导致404 |

**推荐处理策略**：
- **核心修复**：执行脚本6/9（修复file_id关联）即可恢复功能
- **URL美化**（可选）：需先重命名OSS文件，再执行脚本12
- **快速修复**：仅执行脚本1-10，跳过脚本11-13

```sql
-- ============================================================
-- 第四部分：file_detail表URL重复问题修复
-- ============================================================

-- 11. 查找并预览需要修复的URL记录
SELECT 
    id,
    url AS current_url,
    REPLACE(url, CONCAT(filename, filename), filename) AS fixed_url,
    path AS current_path,
    filename,
    create_time
FROM file_detail
WHERE url LIKE '%classic-cases%'
  AND url LIKE CONCAT('%', filename, filename)
  AND is_deleted = 0
ORDER BY create_time DESC;

-- ⚠️ 执行前检查：确认fixed_url的格式正确！
-- 注意：经验证path字段无重复问题，无需修复

-- 12. 执行file_detail表的URL修复
-- 注意：仅修复URL字段，path字段无重复问题无需修改
UPDATE file_detail
SET url = REPLACE(url, CONCAT(filename, filename), filename)
WHERE url LIKE '%classic-cases%'
  AND url LIKE CONCAT('%', filename, filename)
  AND is_deleted = 0;

-- 13. 验证file_detail表URL修复结果
-- 预期：返回0条记录
SELECT COUNT(*) AS remaining_url_duplicate_count
FROM file_detail
WHERE url LIKE '%classic-cases%'
  AND url LIKE CONCAT('%', filename, filename)
  AND is_deleted = 0;
```

### 4.5 最终综合验证脚本

```sql
-- ============================================================
-- 第五部分：综合验证与统计
-- ============================================================

-- 14. 综合验证报告
SELECT 
    '修复统计' AS report_type,
    (SELECT COUNT(*) FROM order_main WHERE is_classic_case = 1) AS total_classic_case_orders,
    (SELECT COUNT(*) FROM design_model dm 
     JOIN order_main om ON om.id = dm.order_id AND om.is_classic_case = 1
     WHERE dm.is_deleted = 0 
     AND dm.file_id IN (SELECT id FROM file_detail WHERE is_deleted = 1)) AS broken_design_model_count,
    (SELECT COUNT(*) FROM order_file of 
     JOIN order_main om ON om.id = of.order_id AND om.is_classic_case = 1
     WHERE of.is_deleted = 0 
     AND of.file_id IN (SELECT id FROM file_detail WHERE is_deleted = 1)) AS broken_order_file_count,
    (SELECT COUNT(*) FROM file_detail 
     WHERE url LIKE '%classic-cases%' 
     AND url LIKE CONCAT('%', filename, filename)
     AND is_deleted = 0) AS url_duplicate_count;

-- 15. 修复后的经典案例完整性检查
SELECT 
    om.id AS order_id,
    om.order_code,
    COUNT(DISTINCT dm.id) AS model_count,
    COUNT(DISTINCT CASE WHEN fd.is_deleted = 0 THEN dm.id END) AS valid_model_count,
    COUNT(DISTINCT CASE WHEN fd.is_deleted = 1 THEN dm.id END) AS broken_model_count,
    CASE 
        WHEN COUNT(DISTINCT CASE WHEN fd.is_deleted = 1 THEN dm.id END) > 0 
        THEN '❌ 仍有问题'
        ELSE '✓ 已修复'
    END AS status
FROM order_main om
LEFT JOIN design_model dm ON dm.order_id = om.id AND dm.is_deleted = 0
LEFT JOIN file_detail fd ON fd.id = dm.file_id
WHERE om.is_classic_case = 1
GROUP BY om.id, om.order_code
HAVING broken_model_count > 0
ORDER BY om.create_time DESC;
```

## 六、注意事项与风险控制

### 6.1 执行时机

- ✅ **推荐时段**：凌晨2:00-5:00（业务低峰期）
- ✅ **避开时段**：工作日9:00-18:00（业务高峰期）

### 6.2 风险控制

| 风险项 | 控制措施 |
|--------|----------|
| 数据丢失 | 执行前完整备份数据库 |

**✅ 执行前检查**：

3. 记录执行日志

**✅ 执行后检查**：
1. 综合验证报告显示所有问题已修复
2. 随机抽查几个经典案例，确认模型数据正常
