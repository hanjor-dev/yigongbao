# 打印设备完整状态与打印生命周期设计

## 目标

将打印设备状态从原有的 `0-空闲 / 1-占用` 扩展为完整的七种状态，同时修正状态变更驱动打印开始和完成的规则，保证设备短暂离线、报警、暂停或重连时不会错误推进生产流转卡。

本次只调整既有 `state` 字段的取值、状态展示、设备可分配判断和生产生命周期解释，不改变 WebSocket 协议。

## 已确认的状态定义

| 状态码 | 名称 | 对流转卡的处理 | 是否允许分配 |
|---|---|---|---|
| 0 | 空闲 | 仅当前一设备状态为 1、2 或 6，且流转卡正在打印时完成；其他情况保持原状态 | 仅在没有活跃流转卡占用时允许 |
| 1 | 工作中 | 已分配且待打印的流转卡进入打印中 | 否 |
| 2 | 打印完成 | 保持原状态，等待设备随后上报空闲 | 否 |
| 3 | 报警 | 保持原状态 | 否 |
| 4 | 暂停 | 保持原状态 | 否 |
| 5 | 准备就绪 | 保持原状态 | 否 |
| 6 | 离线 | 保持原状态 | 否 |

“保持原状态”适用于流转卡的任何当前状态，例如待打印仍为待打印、打印中仍为打印中、已经完成仍保持完成。即使设备状态转换命中完成白名单，关联流转卡也必须仍为 `PRINTING` 才能执行完成逻辑。

## 打印生命周期

生命周期根据设备相邻的旧状态、新状态以及流转卡当前业务状态共同判断，不再按“0 与非 0”判断，也不需要预先配置设备属于新型号还是旧型号。

### 打印开始

收到 `newState=1` 时，查找绑定该设备且状态为 `PENDING_PRINT` 的流转卡，并通过带状态条件的更新将其变为 `PRINTING`。只有条件更新成功后，才继续写入打印开始时间、打印工序、产品状态、订单生产开始时间和 Flow 聚合状态。

该规则不限定前一设备状态，因此可以正确处理 `0→1`、`5→1`、`4→1` 等设备实际序列。已经处于 `PRINTING` 的流转卡不会重复开始。

### 打印完成

生产完成采用相邻状态转换白名单：

```text
newState == 0
&& oldState in {1, 2, 6}
&& productionRecord.status == PRINTING
```

命中条件时，查找绑定该设备且状态为 `PRINTING` 的流转卡，并通过带状态条件的更新将其变为打印完成。只有条件更新成功后，才继续写入打印结束时间、完成打印工序、安排后处理时间并执行 Flow 聚合推进。

该规则同时兼容：

- 新设备 `1→2→0`：状态 2 到达时保持打印中，`2→0` 时完成；
- 旧设备 `1→0`：直接完成；
- 打印中离线 `1→6→0`：状态 6 到达时保持打印中，`6→0` 时默认完成；
- 新设备完成信号后离线 `1→2→6→0`：最终在 `6→0` 时默认完成。

以下状态变化不完成打印：

- `1→2`；
- `3→0`；
- `4→0`；
- `5→0`；
- 任何白名单转换到达时，流转卡不处于 `PRINTING`。

### 离线和重连

打印过程中收到状态 6 时，只更新设备状态和已有设备状态日志，流转卡继续保持原状态。

设备软件重连后上报 `6→0`，默认本次打印已经完成；但只有关联流转卡仍为 `PRINTING` 时才执行完成副作用。若流转卡仍为待打印或已经完成，则不推进。

WebSocket 真正断开时，现有实现只修改 `connectionStatus`，不会覆盖设备业务 `state`。因此重连后首次上报状态 0 时，会继续使用断线前保存的状态判断：断线前为 1 或 2 时完成，断线前为 3 或 4 时不完成；设备主动上报过 6 时按 `6→0` 完成。

### 报警、暂停和准备就绪

状态 2、3、4、5、6 到达时都只更新设备自身状态和状态日志，不立即改变流转卡、打印工序、产品、订单或后处理排程。只有后续状态转换命中完成白名单时才完成。

状态 3 不增加报警记录、报警通知、人工处置接口或报警锁存逻辑。

由于不锁存报警或暂停历史，`3→0`、`4→0` 不完成，但 `3→6→0`、`4→6→0` 会按照已确认的“离线后空闲默认完成”规则，在最终 `6→0` 时完成。

## 设备状态与生产占用分离

设备实时状态和生产流转卡占用是两个独立条件。状态 0 只是设备允许分配的必要条件，不是充分条件。

打印机可以分配必须同时满足：

1. WebSocket 连接状态符合现有在线要求；
2. 设备实时状态严格等于 0；
3. 不存在绑定该设备的 `PENDING_PRINT` 或 `PRINTING` 流转卡。

设备发生 `3→0`、`4→0` 或 `5→0` 后，即使实时状态已变为 0，只要原流转卡仍处于打印中，该设备仍不可再次分配。状态 5“准备就绪”本身也不允许分配。

设备选择列表和实际分配接口必须复用同一套可用性判断，避免列表显示可选、提交时又被拒绝，或并发情况下重复分配。

## WebSocket 契约

以下内容保持现状，不在本次改造范围内：

- WebSocket 地址和连接方式；
- 加工中心身份识别和认证；
- 请求消息体结构及字段名称；
- 成功和失败响应结构；
- 连接建立、心跳、关闭及中心连接状态处理；
- 现有 `DeviceStateChangeEvent` 的字段结构和同步发布方式。

现有消息中的 `devices[].state` 合法值扩展为 0～6，不增加协议版本、消息 ID、签名或新消息类型，也不增加旧消息格式的兼容解析。

状态校验在现有设备状态更新服务入口执行。打印设备收到 null 或 0～6 之外的状态时，整个批次沿用当前错误响应和事务回滚行为，避免部分更新。非打印设备继续遵循其原有状态范围。

## 状态定义与展示

在公共模块建立统一的打印设备状态枚举，集中维护状态码和中文名称。Basic 和 Production 模块均使用该枚举，避免继续使用仅支持 0/1 的生产常量或各自拼接状态名称。

设备管理接口继续返回原始 `state`；打印机选择接口同步返回完整设备状态和中文名称。为避免破坏既有前端字段，优先新增明确的原始状态字段，不改变现有 WebSocket 消息体，也不在同一改造中重新解释其他无关接口字段。

状态日志继续使用现有 `device_state_log`，可以直接保存 0～6，无需新增报警表或状态历史机制。

## 手工状态、删除和首次上报

### 手工状态

打印设备的手工状态校验范围同步为 0～6；其他类型设备保持原有 0/1 规则。手工修改继续只更新设备状态及日志，不发布打印生命周期事件。

生命周期的相邻状态判断使用设备表中持久化的旧状态，因此手工修改仍可能间接污染下一次 WebSocket 上报的 `oldState`。为避免后台手工操作错误完成或阻止完成，打印设备只要存在绑定的 `PENDING_PRINT` 或 `PRINTING` 流转卡，就禁止手工修改状态。没有活跃占用时允许手工修改，但不会触发生产生命周期。该占用判断与设备分配、删除保护复用同一公共检查接口和状态范围。

手工修改打印设备状态必须与正式分配采用相同的设备锁顺序：在同一事务内先通过 `SELECT ... FOR UPDATE` 锁定设备行，再在锁内检查活跃占用并更新状态。这样手工修改与设备分配会在同一设备上串行执行，避免“检查时无占用、写入前已被分配”的竞态。占用检查器缺失、查询异常或无法确认结果时一律拒绝手工修改且不更新设备状态，不能静默放行。

### 删除设备

删除打印设备除检查实时状态外，还必须确认不存在绑定该设备的待打印或打印中流转卡。这样可以防止设备重连变为 0 后，仍在打印中的流转卡所使用的设备被删除。

Basic 模块不能反向依赖 Production。删除引用检查沿用项目现有跨模块检查器模式：公共模块声明设备占用检查接口，Production 模块基于 `production_record` 实现，Basic 设备服务只依赖公共接口。对打印设备执行删除时，如果检查器缺失或检查失败，应拒绝删除并返回业务错误，不能静默跳过占用校验；非打印设备维持现有删除规则。

### 首次上报

首次上报并自动创建设备时继续沿用现有处理，不额外触发打印生命周期。新设备尚未经过业务分配，不存在可推进的流转卡。

## 数据库与文档

现有设备状态字段和状态日志字段使用 `TINYINT`，能够保存 0～6，不需要修改字段类型或新增业务字段。只同步开发 DDL、生产 DDL、测试建表脚本中的字段注释和状态说明。

同步修改设备接口文档、生产接口文档、需求说明和手工测试文档中的二态描述，明确：

- 状态 1 是唯一开始打印信号；
- 状态 2 是新设备的完成中间信号，本身不推进流转卡；
- 只有 `1→0`、`2→0`、`6→0` 能够完成仍处于打印中的流转卡；
- `3→0`、`4→0`、`5→0` 不完成；
- 只有状态 0 且没有活跃流转卡占用的打印机可以分配。

## 影响范围

主要影响以下代码区域：

- 公共模块：统一打印设备状态枚举；
- Basic 设备模块：DTO/实体注释、状态值校验、设备展示、手工状态和删除保护；
- Production 模块：`DeviceStatusListener` 的开始/完成条件、打印机列表可用性和状态展示；
- 数据库脚本：设备状态字段注释；
- 接口与业务文档：完整状态字典和生命周期规则；
- 测试：设备服务、WebSocket 处理器、生产状态监听器、设备选择和分配服务。

不修改现有 WebSocket Handler、连接管理、身份认证和消息结构本身。

## 幂等与一致性

- 状态 1 只更新 `PENDING_PRINT`，重复状态或恢复工作不会重复开始；
- 状态 2 本身不完成流转卡，重复状态 2 不产生生产副作用；
- 只有状态 0 且旧状态位于 `{1,2,6}` 时才尝试完成；完成更新仍以 `PRINTING` 为条件，重复空闲或已完成记录不会重复安排后处理或推进 Flow；
- 状态 3、4、5、6 到达时不调用生产生命周期副作用；
- 生命周期条件更新失败时，不执行工序、产品、订单、排程和 Flow 的后续写入；
- 设备可分配查询用于页面展示，正式分配仍必须在现有事务和锁保护下再次校验状态及活跃占用。

## 测试矩阵

### 生命周期

- `0→1`、`5→1`：待打印进入打印中；
- `4→1`：已有打印中记录不重复开始；
- `1→2`：保持打印中，不执行完成副作用；
- `1→2→0`：新设备在 `2→0` 时完成，并只执行一次全部完成副作用；
- `1→0`：旧设备直接完成；
- `1→6→0`：离线时保持打印中，`6→0` 时默认完成；
- `1→2→6→0`：最终在 `6→0` 时完成；
- `1→3`、`3→0`：保持打印中；
- `1→4`、`4→0`：保持打印中；
- `1→5`、`5→0`：保持打印中；
- `1→3→6→0`、`1→4→6→0`：最终在 `6→0` 时完成；
- `1→4→1`：暂停和恢复不重复开始；
- 状态 3 到达待打印或已完成流转卡时保持各自原状态；
- 参数化覆盖 `oldState={1,2,6}`、`newState=0` 且流转卡分别为 `PENDING_PRINT`、已完成及其他非 `PRINTING` 状态：均不得更新流转卡，也不得执行打印工序完成、后处理排程或 Flow 推进；
- 重复 1、2、3、4、5、6 不产生重复业务副作用。

### 分配与设备管理

- 只有状态 0 可进入可分配候选；
- 状态 5 不可分配；
- 状态 0 但存在待打印或打印中占用时不可分配；
- `3→0`、`4→0`、`5→0` 后原流转卡仍打印中时不可再次分配；
- 非法状态使批次失败且不部分落库；
- 打印设备手工状态接受 0～6，非打印设备维持原范围；
- 打印设备存在待打印或打印中占用时，所有手工状态修改均被拒绝且不改写设备旧状态；
- 打印设备手工状态修改先锁设备，再在同一事务内完成占用检查和状态写入；与正式分配并发时必须串行，不能出现检查后被并发分配再写状态的竞态；
- 手工修改时占用检查器缺失或查询异常应拒绝修改并保持设备原状态；
- 存在活跃流转卡引用时禁止删除打印设备。
- 打印设备删除时占用检查器缺失或查询失败应拒绝删除，不能形成跨模块失效放行。

### 回归

- WebSocket 请求及响应 JSON 结构保持不变；
- 连接、断开和心跳行为保持不变；
- 打印开始和完成时现有工序、产品、订单、后处理排程及 Flow 聚合逻辑仍完整执行；
- 现有设备状态日志继续正确记录 0～6 的状态变化。

## 明确不做

- 不改变 WebSocket 协议、认证、地址或消息体；
- 不兼容其他旧消息内容格式；
- 不增加报警通知、报警处置、报警锁存或超时离线功能；
- 不在状态 2 到达时立即完成流转卡；
- 不让 `3→0`、`4→0`、`5→0` 完成流转卡；
- 不允许状态 5 的设备参与打印机分配；
- 不修改与本次状态扩展无关的连接管理或安全机制。
