# 区域管理员账户级多机构数据权限完整方案

## 1. 结论

采用轻量的账户级扩展方案，不重构现有部门、机构和角色权限体系：

```text
区域管理员有效机构 = 主所属机构 sys_user.org_id
                    ∪ 账户额外管理机构 sys_user_managed_org.org_id
```

- 主所属机构必填且只有一个，是账户身份和提单归属的唯一事实源。
- 额外管理机构选填，可以完全不配置。
- 关系表只保存额外机构，不保存主机构，不设置 `is_primary`。
- 区域管理员角色的数据范围从 `dept` 改为 `user_orgs`。
- 其他角色继续沿用现有 `self/hospitals/org/dept/all/center`，不改变语义。
- 现有区域管理员不自动初始化额外机构，由管理员后续编辑账户手动分配。

该方案能够满足当前需求，改造量明显小于组织关系图完全重构，并且不会改变设计、生产、质管、财务、仓储、公司管理员等角色的权限。

## 2. 核心业务规则

### 2.1 账户配置

区域管理员账户字段：

| 字段 | 必填 | 含义 |
|---|---:|---|
| `orgId` | 是 | 主所属机构，保存在 `sys_user.org_id` |
| `managedOrgIds` | 否 | 额外管理机构集合，保存在新关系表 |

机构限制：

- 主机构和额外机构仅允许正常状态的经销商（`1.2`）或服务商（`1.4`）。
- 主机构停用、删除或变为其他类型时，有效机构集合整体为空，账户不能继续访问订单，必须先由管理员修复主机构。
- 医疗机构（`1.3`）不能成为区域管理员的所属或管理机构。
- 前端误将主机构放入 `managedOrgIds` 时，后端去重且不写关系表。
- 重复机构去重保存。
- 非区域管理员不能配置 `managedOrgIds`。
- 角色从区域管理员切换为其他角色时，清空额外机构关系。

`UpdateUserDTO.managedOrgIds` 采用以下语义：

- `null`：本次不修改额外机构。
- `[]`：清空全部额外机构，随后只管理主机构。
- 非空数组：全量覆盖额外机构。

### 2.2 查询与操作订单

区域管理员所有订单查询直接使用：

```sql
WHERE order_main.org_id IN (:effectiveOrgIds)
```

不采用“先查机构下业务员，再按 `operator_id` 匹配”的方式，原因如下：

- `order_main.org_id` 是订单归属机构的稳定快照。
- 业务员调岗、离职或变更机构不会改变历史订单归属。
- 查询链路更短，不受账号状态及部门变化影响。
- 可直接利用订单机构索引，性能和语义更稳定。

权限必须同时用于列表、详情、修改、动作列表、审核、取消、导出、下载及其他按订单 ID 操作，防止只限制列表而详情接口横向越权。

### 2.3 区域管理员提单

- 区域管理员可以提单。
- 新订单的 `order_main.org_id` 必须等于其 `sys_user.org_id`。
- 不能以额外管理机构名义提单。
- 后端不信任前端传入的提单人、机构名称或机构归属。
- 草稿可以暂存，但转正式订单时必须重新校验主机构和医院权限。

### 2.4 可选医院

区域管理员候选医院为所有有效机构关联医院的并集：

```text
orderableHospitalIds = hospitals(primaryOrgId)
                     ∪ hospitals(each additionalManagedOrgId)
```

- 基于 `sys_org_hospital` 查询。
- 同一医院被多个机构关联时只返回一次。
- 医院或关系被停用/删除后，下次查询立即失效。
- 创建订单、修改医院和草稿转正式订单时，后端必须再次验证，不只依赖下拉列表。
- 管理集合为空时，仍可选择主机构关联的全部医院。

## 3. 数据模型

### 3.1 保留主机构

```text
sys_user.org_id NOT NULL
```

不改成用户多机构主表，避免影响登录身份、提单归属、用户名生成、收费模板和现有业务逻辑。

### 3.2 新增额外管理关系

```sql
CREATE TABLE sys_user_managed_org (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id     BIGINT NOT NULL,
    org_id      BIGINT NOT NULL,
    create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    create_by   BIGINT NULL,
    UNIQUE KEY uk_user_managed_org (user_id, org_id),
    KEY idx_managed_org_user (user_id),
    KEY idx_managed_org_org (org_id)
);
```

表中不保存：

- 主机构记录；
- `is_primary`；
- 部门关系快照；
- 历史订单推导关系。

## 4. API 合同

创建或更新区域管理员账户：

```json
{
  "roleId": 3,
  "orgId": 1001,
  "managedOrgIds": [1002, 1003]
}
```

详情响应：

```json
{
  "roleCode": "regional-manager",
  "dataScopeType": "user_orgs",
  "orgId": 1001,
  "managedOrgIds": [1002, 1003],
  "effectiveOrgIds": [1001, 1002, 1003]
}
```

`managedOrgIds` 用于编辑回显，`effectiveOrgIds` 用于解释实际权限；前端不能把两者混为同一字段。

## 5. 前端操作要求

本仓库当前只有 `frontend/dist` 编译产物，没有可维护的前端源码，因此本次不直接修改压缩后的构建文件。前端源码仓库需要按以下合同接入：

- 普通角色保持原账户表单。
- 选择“区域管理员”时显示“主所属机构”和“额外管理机构”。
- 主所属机构单选且必填。
- 额外管理机构多选、可搜索、可为空。
- 候选仅展示正常经销商和服务商。
- 主机构在额外列表中禁选或自动排除。
- 切换为非区域管理员时清空页面上的额外选择。
- 编辑详情使用 `managedOrgIds` 回显，不使用 `effectiveOrgIds` 回填。

## 6. 数据变更与历史数据

### 6.1 上线迁移

1. 检查区域管理员是否都存在主机构。
2. 检查主机构是否为正常经销商或服务商。
   任一检查不通过时脚本通过 `SIGNAL SQLSTATE '45000'` 自动中止，禁止带病切换角色权限。
3. 创建 `sys_user_managed_org`。
4. 备份区域管理员角色原 `data_scope_type`。
5. 将角色范围从 `dept` 更新为 `user_orgs`。
6. 不写入任何额外机构关系。
7. 输出待管理员人工维护账户清单。

完整脚本：`sql/migration-regional-manager-managed-orgs-2026-08-22.sql`。

### 6.2 历史订单

- 不修改任何历史订单。
- 历史订单继续以已经固化的 `order_main.org_id` 判断归属。
- 上线后，区域管理员立即只能查看主机构历史订单。
- 管理员增加额外机构后，该区域管理员可以查看这些机构的历史及新增订单。
- 管理员移除额外机构后，对应历史及新增订单立即不可见。
- 权限变更不转移订单归属，也不改变订单流程状态、审核记录和生产记录。

### 6.3 机构集合变更

采用“即时生效、历史数据不改写”原则：

| 操作 | 结果 |
|---|---|
| 增加额外机构 | 立即获得该机构全部历史及后续订单权限 |
| 移除额外机构 | 立即失去该机构全部历史及后续订单权限 |
| 清空额外机构 | 仅保留主机构权限 |
| 更换主机构 | 后续只能以新主机构提单，有效权限重新计算 |
| 额外机构停用/删除/变为其他类型 | 该额外机构实时排除 |
| 主机构停用/删除/变为其他类型 | 整个有效集合为空，拒绝订单访问并要求修复账户 |
| 业务机构—医院关系变化 | 可选医院和提交校验立即按新关系生效 |

不缓存有效机构集合，避免修改后仍短暂保留旧权限。账户修改请求及 `managedOrgIds` 会进入现有接口操作日志，作为授权变更审计依据。

## 7. 完整影响域

### 7.1 账户与角色

- `DataScopeTypeEnum` 新增 `USER_ORGS`。
- 创建/修改 DTO 新增 `managedOrgIds`。
- 用户详情增加 `managedOrgIds` 和 `effectiveOrgIds`。
- 创建、更新、角色切换和删除账户需维护关系表。
- 区域管理员主机构允许经销商或服务商。
- 其他角色权限逻辑不变。

### 7.2 订单

- 列表、分页、导出统一通过 `OrderQueryHelper` 按 `org_id IN (...)`。
- 详情及写操作统一进行数据范围校验。
- 区域管理员只能以主机构提单。
- 修改订单医院时重新验证医院权限。
- 草稿转正式订单沿用正式创建校验。
- 设计、生产、质检、财务和仓储仍使用各自原范围。

### 7.3 医院

- 区域管理员按有效机构并集查询 `sys_org_hospital`。
- 后端提交校验与下拉候选使用相同范围。
- 共享医院去重。
- 医院关系变化即时生效。

### 7.4 首页看板

- 区域管理员看板由按部门人员统计改为按订单 `org_id` 的有效机构集合统计。
- 业务员排行仍按 `operator_id` 分组，但候选订单先按机构范围过滤。
- 卡片标题应从“部门订单”调整为“管理机构订单”。

### 7.5 通知

当前订单提交通知只面向设计管理员，没有现存的区域管理员订单审核通知，因此本次不新增通知链路。若以后新增区域管理员通知，接收人必须按订单 `org_id` 反查“主机构匹配或额外机构匹配”的区域管理员，不能再按部门广播。

### 7.6 性能与索引

- `sys_user_managed_org(user_id, org_id)` 唯一索引支持账户范围读取。
- `idx_managed_org_org(org_id)` 支持按机构反查管理员。
- 订单查询依赖 `order_main.org_id` 索引；上线前应确认生产表已有该索引。
- 单个区域管理员机构数预期较小时使用 `IN` 查询；若未来达到数千个机构，再考虑关联子查询或权限快照表。

## 8. 安全边界

- 数据权限由后端计算，前端传入范围不可信。
- 查不到用户、主机构为空或有效机构集合为空时采用拒绝访问，不降级为全量。
- 关系表只接受真实、正常的经销商或服务商。
- 所有按订单 ID 的接口返回统一的“订单不存在”语义，避免泄露越权订单是否存在。
- 主机构和额外机构的并集只扩大“可查看/管理”范围，不扩大“可代表提单”的身份范围。

## 9. 验收场景

1. 区域管理员 A 主机构 B，无额外机构：只能看到 B 的全部订单。
2. A 额外配置 C、D：可看到 B、C、D 的全部订单。
3. A 以 C 提单：后端拒绝；以 B 提单：允许。
4. B、C 关联不同医院：医院下拉返回两边医院并集。
5. B、C 关联同一医院：只返回一次。
6. 移除 C：C 的历史订单、详情、导出及写操作立即不可用。
7. 清空额外机构：A 仍能管理 B。
8. 医疗机构被提交为额外管理机构：后端拒绝。
9. 非区域管理员提交 `managedOrgIds`：后端拒绝。
10. 现有区域管理员执行迁移后：关系表无自动数据，仅能查看主机构，待管理员手工补充。

2. 部署支持 `user_orgs` 的后端代码。
3. 执行建表和角色范围更新。
4. 验证区域管理员默认仅主机构权限。
5. 部署账户表单前端改造。
6. 管理员逐个维护额外管理机构。
7. 抽查订单列表、详情、导出、看板、提单和医院选择。
8. 观察越权拒绝日志和慢查询。
