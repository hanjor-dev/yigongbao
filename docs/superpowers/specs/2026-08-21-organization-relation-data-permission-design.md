# 组织关系驱动的订单数据权限重构方案

> 文档状态：评审稿  
> 编写日期：2026-08-21  
> 适用范围：系统管理、账户管理、部门管理、机构管理、订单、订单草稿、仪表盘及订单关联业务模块

## 1. 背景

当前订单数据权限以角色的 `data_scope_type` 为入口，支持 `self`、`hospitals`、`dept`、`org`、`center` 和 `all` 等固定范围。其中区域管理员使用 `dept` 范围，订单查询实际按 `order_main.operator_dept_id = 当前用户.dept_id` 过滤。

该模型可以表达“同部门可见”，但无法满足以下场景：

- 市场部后勤统一管理市场部、销售部、业务员及下级经销商订单；
- 区域管理员管理下级区域管理员、业务员和经销商；
- 经销商、服务商及医疗机构之间存在多层发展或服务关系；
- 同一管理范围由多个管理员共享；
- 后台可以调整组织关系，同时保留历史业务归属；
- 机构数量达到数百条后，仍能以可维护方式配置权限。

因此，需要从“固定部门过滤”重构为“组织关系驱动的数据权限”。

## 2. 目标与非目标

### 2.1 目标

1. 支持部门—部门、部门—机构集合、机构—机构等受约束的组织关系。
2. 账户不逐一配置数据范围，而是通过所属部门或机构自动继承权限。
3. 同时支持机构类型、机构集合和全部实际机构三种配置粒度，由客户按复杂度选择。
4. 支持查看、提单、修改、导出等权限沿关系分别继承。
5. 防止循环关系、重复路径、非法跨类型关系及跨公司越权。
6. 组织调整后可以重算当前权限，同时保留历史订单归属和审计依据。
7. 关系变更支持草稿、影响预览、定时生效、审计和回滚。

### 2.2 非目标

- 不改变公司管理员、超级管理员、财务、设计、生产、质管、仓储等当前已满足需求的角色范围。
- 不用组织关系替代菜单、按钮和接口功能权限。
- 不在第一阶段引入复杂的显式拒绝规则。
- 不允许通过任意节点自由连线构造无约束权限图。

## 3. 核心原则

### 3.1 功能权限与数据权限分离

- 角色决定账户是否具有“查看订单、提单、修改、审核、导出”等功能权限。
- 组织关系决定这些功能可以作用于哪些部门、机构和订单。
- 最终权限为：

```text
最终操作权限 = 账户角色功能权限 ∩ 组织关系路径权限
```

组织关系不能赋予角色本身没有的功能。

### 3.2 画布表达上下级管理范围

画布中的每一条连线都表示明确的上下级关系：

```text
父级节点 → 子级节点
```

父级必然可以查看子级及其后代节点的数据。服务、协作、普通业务关联等不产生上下级数据权限的关系，不进入该画布，避免出现“画了连线但不影响权限”的歧义。

源数据提供两种可选方案，详见第 4.1 节。客户在项目实施时选择一种主方案，不建议两套方案在同一组织图中无规则混用。

### 3.3 账户不进入组织画布

账户只需要绑定一个主要所属部门或机构。系统从该归属节点出发计算组织关系及数据范围。

临时跨区域管理、代理管理等场景使用独立的额外授权，不修改组织结构。

### 3.4 当前权限与历史事实分离

- 当前组织关系用于计算现在谁可以管理数据；
- 订单中的提单人、提单部门、提单机构和创建时组织路径属于历史事实，不随组织调整覆盖；
- 历史责任追溯通过组织版本和订单快照完成。

## 4. 领域模型

### 4.1 源数据与节点方案

#### 方案一：实际部门 + 机构类型

画布节点包括：

| 节点类型 | 示例 |
|---|---|
| 实际部门 | 市场部、销售部 |
| 机构类型 | 经销商、服务商、医疗机构 |

机构类型节点代表当前公司内该类型的全部有效机构。后台新增、停用或修改机构类型后，节点成员自动变化。

优点：

- 节点数量最少，配置简单；
- 客户理解成本低；
- 新增机构自动进入对应权限范围，日常维护量小；
- 适合按机构类型整体管理的客户。

缺点：

- 权限颗粒度较粗；
- 同类型机构不能分区域或分团队管理；
- 单个机构需要特殊归属时难以表达；
- 类型节点成员变化可能一次影响大量账户和订单。

#### 方案二：实际部门 + 同类型机构集合组 + 特殊单机构

画布节点包括：

| 节点类型 | 示例 |
|---|---|
| `DEPT` 实际部门 | 市场部、销售部 |
| `ORG_GROUP` 同类型机构集合 | 华东经销商组、华南服务商组 |
| `ORG` 特殊单机构 | 上海康瑞经销商 |

一个机构集合内部只允许包含同一种机构类型。集合支持：

- `DYNAMIC`：根据地区、标签、关联部门等条件自动计算；
- `STATIC`：人工选择固定机构列表；
- 显式包含和排除少量例外。

优点：

- 可以按地区、渠道、团队等维度细分同类型机构；
- 支持少量特殊机构单独挂载；
- 权限范围更精确，适合复杂业务网络；
- 数百家机构仍只需要少量集合节点。

缺点：

- 配置和维护成本高于方案一；
- 需要处理集合重叠、遗漏和成员变化；
- 发布前必须预览成员差异；
- 需要机构集合规则、成员物化和异常清单等额外能力。

#### 方案三：实际部门 + 全部实际机构

画布源数据包括全部实际部门以及 `sys_org` 中的全部有效机构。经销商、服务商和医疗机构均以具体机构节点 `ORG` 进入画布，不再通过类型或集合间接代表。

由于机构可能达到数百甚至数千条，左侧源数据必须使用搜索、类型/地区筛选、分页或虚拟滚动、批量拖入和“已加入画布”标识，不能一次渲染全部机构。画布提供折叠、按层展开、快速定位和自动布局。

优点：

- 权限粒度最细，每个机构可以拥有独立父级和下级；
- 机构之间的多层发展关系表达最直接；
- 无需解释集合规则，权限路径能落到具体机构。

缺点：

- 节点和连线数量大，初始配置与持续维护成本最高；
- 批量调整、布局和权限影响预览更复杂；
- 机构新增后不会自动进入组织图，必须进入“待编排机构”清单；
- 大图发布、闭包计算及前端渲染需要更严格的性能控制。

#### 选择建议

| 客户特征 | 建议方案 |
|---|---|
| 所有经销商由同一管理链统一管理 | 方案一 |
| 同类型机构需要按地区或团队拆分 | 方案二 |
| 当前业务简单但预计快速扩张 | 方案二，先建立少量大集合 |
| 强调配置简洁、维护人员较少 | 方案一 |
| 每家机构上下级都不同且必须精确表达 | 方案三 |
| 机构数量很多但仅少量存在例外 | 方案二 |

正式启用时建议每家公司选择一种主方案。三种方案共用同一套部门、机构和关系主数据，但不建议在同一已发布版本中大量混用类型、集合和具体机构节点，否则容易出现范围重叠和权限解释困难。

### 4.2 机构集合示例

```text
华东经销商组
  机构类型 = 经销商
  地区 ∈ 上海、江苏、浙江
  状态 = 正常
  显式包含 = 特殊经销商A
  显式排除 = 暂停合作经销商B
```

画布只展示“华东经销商组（87家）”，点击后在属性面板查看机构明细。

### 4.3 上下级关系

画布不再区分“隶属、管理、发展、服务、协作”等不会统一产生权限的连线。所有连线只有一种核心语义：

```text
上级/管理方 → 下级/被管理方
```

规则如下：

- 上级必然继承下级及其后代的查看权限；
- 子级默认不能查看父级或兄弟节点数据；
- 提单、修改、导出等操作仍与账户角色取交集，可按上下级关系配置；
- 非上下级的服务、合作、医院关联关系保留在原业务模块，不参与组织权限图。

## 5. 关系白名单

不能允许任意节点建立上下级关系。建议按源数据方案、父子节点类型配置白名单：

| 上级节点 | 下级节点 | 是否允许上下级 | 说明 |
|---|---|---:|---|
| 公司根节点 | 部门 | 允许 | 公司内部组织结构 |
| 部门 | 部门 | 允许 | 支持多个直接父级 |
| 部门 | 机构类型 | 方案一允许 | 表示管理该类型全部机构 |
| 部门 | 机构集合 | 方案二允许 | 常规精细化管理范围 |
| 部门 | 实际机构 | 方案二、三允许 | 特殊机构例外或全量实际机构编排 |
| 机构类型 | 机构类型 | 按白名单允许 | 例如服务商 → 医疗机构 |
| 机构集合 | 机构集合 | 按机构类型白名单允许 | 集合必须分别保持同类型 |
| 实际机构 | 机构集合 | 按机构类型白名单允许 | 单一上级机构管理一组下级机构 |
| 实际机构 | 实际机构 | 按机构类型白名单允许 | 具体机构上下级 |
| 机构/机构集合 | 部门 | 默认禁止 | 防止外部机构成为公司部门父级 |
| 任意节点 | 自己 | 禁止 | 防止自环 |

机构类型还需要进一步限制，例如：

- 经销商可以发展经销商；
- 服务商可以服务医疗机构；
- 经销商和医疗机构只有在确实存在上下级管理时才允许连线；普通业务关联不进入画布；
- 医疗机构默认不能成为经销商或公司部门的管理父级。

## 6. 图结构边界规则

### 6.1 禁止循环

已有：

```text
A部门 → B部门 → C机构集合
```

必须禁止：

```text
C机构集合 → A部门
C机构集合 → B部门
B部门 → A部门
```

循环检查必须覆盖所有会参与数据权限继承的关系，而不是只检查同类型节点。

### 6.2 层级深度由系统计算

“一级父级、二级父级”由关系闭包计算，禁止人工维护 `+1`、`+2` 等级。任何新增关系都要检查目标是否已经是来源节点的祖先。

### 6.3 直接父级数量

- 每个节点允许零个、一个或多个直接父级；
- 多父级属于组织模型的标准能力，不需要额外启用“共享管理”开关；
- 任一父级都固定继承该节点及其全部后代的查看权限；
- 保存和发布时必须展示新增父级将扩大的账户与订单范围；
- 属性面板展示全部直接父级，支持逐条定位和解除关系。

### 6.4 重复和冗余路径

已有 `A → B → C` 时，再增加 `A → C` 会形成一条额外的直接授权路径。系统允许保存，但必须提示其可能改变提单、修改和导出权限；如果两条路径的能力完全相同，则标记为冗余连线，建议删除但不强制阻断。

### 6.5 多路径权限

同一节点存在多条合法管理路径时：

- 单条路径上的操作权限逐级取交集；
- 多条完整路径之间取并集；
- 权限结果必须展示来源路径；
- 机构集合重叠时提示重复成员数量，但可以保留合法重叠。

### 6.6 其他限制

- 禁止跨公司建立继承关系；
- 禁用节点不能新增下级；
- 停用或删除节点前必须迁移直接子节点和账户；
- 设置最大层级深度，防止异常深链；
- 关系必须支持生效时间和失效时间。

## 7. 权限计算

### 7.1 账户归属

第一阶段每个账户只允许一个主要数据归属节点：

- 企业内部账户通常绑定部门；
- 经销商、服务商、医疗机构账户通常绑定具体机构；
- 具体机构通过机构集合成员关系进入组织权限图。

账户的部门和机构主数据仍由现有账户管理维护，新增绑定历史用于记录有效期。

### 7.2 计算步骤

```text
读取账户主要归属
  ↓
将具体机构映射到一个或多个机构集合
  ↓
查找当前有效组织关系路径
  ↓
计算可见部门、机构和账户集合
  ↓
沿路径计算查看、提单、修改、导出权限
  ↓
与角色功能权限取交集
  ↓
应用到订单列表、详情、导出、草稿和仪表盘
```

### 7.3 路径权限示例

```text
市场部
  -- 查看/提单/修改/导出 --> 一级经销商组
  -- 仅查看/导出       --> 二级经销商组
```

市场部账户对二级经销商订单只能查看和导出，不能代提单或修改。

### 7.4 额外授权

以下需求不修改组织图，使用带有效期的额外授权：

- 临时代理另一个区域；
- 某管理员跨部门协助；
- 只授权查看某个机构；
- 短期项目组管理。

额外授权同样不能突破角色功能权限。

## 8. 订单归属与历史数据

### 8.1 保留现有历史快照

现有订单字段继续作为创建时事实保存：

- `operator_id`、`operator_name`；
- `operator_dept_id`、`operator_dept_name`；
- `org_id`、`org_name`；
- `create_time`。

组织调整、账户调岗、部门合并时不得批量覆盖这些字段。

### 8.2 新增订单数据归属

建议在订单创建时增加：

| 字段 | 说明 |
|---|---|
| `data_owner_type` | `DEPT` 或 `ORG` |
| `data_owner_id` | 实际归属部门或机构ID |
| `owner_path_snapshot` | 创建时组织路径快照，JSON存储 |
| `scope_version_id` | 创建时生效的组织关系版本 |

订单归属必须落到实际部门或具体机构，不能落到会动态变化的机构集合。

### 8.3 当前业务可见性

普通订单列表按当前有效组织关系计算。组织调整后：

- 新管理方获得目标节点现有及历史订单的业务管理权限；
- 旧管理方失去普通业务查看权限；
- 订单历史提单部门和机构保持不变。

### 8.4 历史审计可见性

旧管理方如需查看曾经负责的数据，应使用独立的历史审计权限，例如：

- `VIEW_HISTORICAL_ORDER`；
- `VIEW_ORG_CHANGE_AUDIT`。

审计查询依据订单快照和历史组织版本，不应让旧管理方永久保留普通业务权限。

### 8.5 进行中订单交接

账户调岗或部门调整不应自动修改所有进行中订单。需要提供显式业务交接：

- 修改当前处理人；
- 转移订单数据归属；
- 记录来源节点、目标节点、原因、生效时间和操作人。

## 9. 组织架构变更处理

| 变更 | 账户处理 | 组织数据处理 | 订单处理 |
|---|---|---|---|
| 部门/机构改名 | 无需重绑 | 更新显示缓存 | 历史名称快照不覆盖 |
| 部门移动上级 | 无需重绑 | 重建闭包和权限缓存 | 当前可见性随新关系变化 |
| 机构调整管理部门 | 无需重绑 | 更新集合或管理关系 | 当前可见性重新计算 |
| 机构移入/移出集合 | 无需重绑 | 重算集合成员 | 当前可见性重新计算 |
| 账户调岗 | 关闭旧绑定并新增绑定 | 无 | 旧订单历史归属不变 |
| 部门合并 | 迁移有效账户 | 迁移子节点和集合，原部门停用 | 历史订单保留原部门 |
| 部门拆分 | 人工分配账户 | 人工分配子节点和集合 | 进行中订单按需交接 |
| 部门停用 | 必须先迁移 | 禁止新增关系 | 历史订单保留 |
| 机构停用 | 账户按业务迁移 | 从动态集合中失效 | 禁止新订单，历史订单保留 |
| 经销商/服务商类型转换 | 账户保持绑定，检查角色兼容性 | 更新类型、集合成员并校验所有关系 | 历史类型快照不变，当前权限重算 |
| 删除关系 | 无需重绑 | 重建闭包 | 当前权限减少，需影响预览 |

账户绑定应保留有效期：

```text
user_id
node_type
node_id
effective_from
effective_to
is_primary
```

旧绑定不物理删除，以支持历史追溯。

### 9.1 经销商与服务商类型转换

类型转换只修改机构当前类型，必须保持 `sys_org.id`、机构编码、已有账户绑定和业务主体身份不变。已有用户名和机构编码不因前缀规则重新生成。

转换采用“预检—审批—生效—重算”流程：

```text
选择目标类型与生效时间
  ↓
计算集合、上下级关系、角色、账户和订单影响
  ↓
阻断硬冲突，确认可接受警告
  ↓
审批并在事务中更新当前类型和类型历史
  ↓
退出旧动态集合、加入新动态集合
  ↓
重校验关系白名单并重建权限闭包
  ↓
刷新账户当前数据权限，保留转换审计快照
```

影响处理规则：

| 影响项 | 处理规则 |
|---|---|
| 动态机构集合 | 自动退出旧类型集合并按规则加入新类型集合 |
| 静态机构集合 | 不静默移除，标记类型冲突并要求人工确认 |
| 类型节点 | 从旧类型节点范围移出，进入新类型节点范围 |
| 上下级关系 | 对全部入边和出边重新执行新类型白名单校验；非法关系必须先解除或替换 |
| 多父级权限 | 计算转换前后每条路径及最终权限差异，展示新增/减少的账户与订单 |
| 账户归属 | 机构 ID 不变，账户无需重绑 |
| 账户角色 | 经销商/服务商专属角色标记为不兼容，转换前必须调整或确认保留的通用角色 |
| 经销商专属业务关系 | 转为历史、终止或迁移到服务商关系，不允许无提示保留失效业务语义 |
| 历史订单 | 保存创建时机构类型快照，不批量回写 |
| 当前订单权限 | 按转换后组织关系和集合成员重新计算 |
| 报表 | 历史统计按订单类型快照，当前主体统计按最新机构类型 |

硬冲突包括循环关系、转换后不合法的上下级组合、未处理的专属角色，以及必须存在但缺失的新类型业务资料。硬冲突未解决时禁止生效；集合成员变化、权限增减和报表口径变化属于警告，需要审批人确认。

### 9.2 并发与回滚

- 转换请求记录机构数据版本号，审批时版本不一致则重新预检；
- 生效事务锁定机构主记录，避免同时修改机构类型或发布相关组织版本；
- 转换与组织关系发布使用同一权限重算队列；
- 生效失败时回滚当前类型、集合成员和关系版本；
- 已成功生效的转换原则上通过“反向转换”纠正，不直接删除审计记录。

## 10. 关系发布与变更控制

组织关系不应保存即生效，建议采用版本化发布：

```text
编辑草稿
  ↓
类型白名单、循环、重复、多路径和机构类型转换冲突检查
  ↓
重算机构集合和关系闭包
  ↓
计算账户与订单影响
  ↓
人工确认生效时间
  ↓
发布新版本
  ↓
刷新权限缓存和统计口径
  ↓
保留旧版本供审计和回滚
```

发布前至少展示：

- 新增和减少的可见账户数；
- 新增和减少的可见订单数；
- 新增和移除的机构集合成员；
- 失去权限的管理员；
- 待迁移账户和未归属节点；
- 受影响的进行中订单；
- 循环、重复路径和多父级警告。
- 机构类型转换导致的集合、角色、关系和业务资料冲突。

## 11. 数据库设计建议

### 11.1 权限范围节点

```sql
CREATE TABLE sys_scope_node (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    company_id      BIGINT NOT NULL,
    node_name       VARCHAR(128) NOT NULL,
    node_type       VARCHAR(20) NOT NULL COMMENT 'DEPT/ORG_TYPE/ORG_GROUP/ORG',
    ref_id          BIGINT NULL COMMENT '部门、机构类型或实际机构主数据ID',
    member_mode     VARCHAR(16) NULL COMMENT 'DYNAMIC/STATIC，ORG_GROUP专用',
    status          TINYINT NOT NULL DEFAULT 1,
    create_time     DATETIME DEFAULT CURRENT_TIMESTAMP,
    update_time     DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    is_deleted      TINYINT DEFAULT 0
);
```

### 11.2 机构集合规则

```sql
CREATE TABLE sys_scope_group_rule (
    id                  BIGINT PRIMARY KEY AUTO_INCREMENT,
    scope_node_id       BIGINT NOT NULL,
    org_type            VARCHAR(16) NULL,
    area_rule_json      JSON NULL,
    dept_rule_json      JSON NULL,
    tag_rule_json       JSON NULL,
    include_org_json    JSON NULL,
    exclude_org_json    JSON NULL,
    update_time         DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

生产查询建议将规则结果物化：

```sql
CREATE TABLE sys_scope_group_member (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    scope_node_id   BIGINT NOT NULL,
    org_id          BIGINT NOT NULL,
    member_source   VARCHAR(16) NOT NULL COMMENT 'RULE/MANUAL',
    UNIQUE KEY uk_scope_org (scope_node_id, org_id),
    KEY idx_org_id (org_id)
);
```

### 11.3 组织关系

```sql
CREATE TABLE sys_scope_relation (
    id                  BIGINT PRIMARY KEY AUTO_INCREMENT,
    version_id          BIGINT NOT NULL,
    company_id          BIGINT NOT NULL,
    parent_node_id      BIGINT NOT NULL,
    child_node_id       BIGINT NOT NULL,
    allow_create        TINYINT NOT NULL DEFAULT 0,
    allow_edit          TINYINT NOT NULL DEFAULT 0,
    allow_export        TINYINT NOT NULL DEFAULT 0,
    effective_from      DATETIME NULL,
    effective_to        DATETIME NULL,
    status              TINYINT NOT NULL DEFAULT 1,
    UNIQUE KEY uk_version_relation (version_id, parent_node_id, child_node_id),
    KEY idx_parent (parent_node_id),
    KEY idx_child (child_node_id)
);
```

### 11.4 关系闭包

```sql
CREATE TABLE sys_scope_relation_closure (
    version_id          BIGINT NOT NULL,
    ancestor_node_id    BIGINT NOT NULL,
    descendant_node_id  BIGINT NOT NULL,
    depth               INT NOT NULL,
    create_allowed      TINYINT NOT NULL,
    edit_allowed        TINYINT NOT NULL,
    export_allowed      TINYINT NOT NULL,
    PRIMARY KEY (version_id, ancestor_node_id, descendant_node_id),
    KEY idx_descendant (descendant_node_id)
);
```

闭包表中的操作能力是所有合法路径的最终聚合结果：单条路径逐边取交集，多条路径之间取并集。为了展示权限来源，另存路径明细：

```sql
CREATE TABLE sys_scope_permission_path (
    id                  BIGINT PRIMARY KEY AUTO_INCREMENT,
    version_id          BIGINT NOT NULL,
    ancestor_node_id    BIGINT NOT NULL,
    descendant_node_id  BIGINT NOT NULL,
    path_hash           VARCHAR(64) NOT NULL,
    path_node_json      JSON NOT NULL,
    create_allowed      TINYINT NOT NULL,
    edit_allowed        TINYINT NOT NULL,
    export_allowed      TINYINT NOT NULL,
    UNIQUE KEY uk_version_path (version_id, path_hash),
    KEY idx_path_lookup (version_id, ancestor_node_id, descendant_node_id)
);
```

闭包表用于快速判断最终权限，路径表只用于权限解释、影响预览和审计，避免普通订单查询递归遍历整个关系图。

### 11.5 账户归属历史

```sql
CREATE TABLE sys_user_scope_binding (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id         BIGINT NOT NULL,
    owner_type      VARCHAR(16) NOT NULL COMMENT 'DEPT/ORG',
    owner_id        BIGINT NOT NULL,
    effective_from  DATETIME NOT NULL,
    effective_to    DATETIME NULL,
    is_primary      TINYINT NOT NULL DEFAULT 1,
    KEY idx_user_effective (user_id, effective_from, effective_to),
    KEY idx_owner (owner_type, owner_id)
);
```

现有 `sys_user.dept_id`、`org_id` 可在兼容期继续作为当前归属缓存。

### 11.6 版本与审计

建议增加：

- `sys_scope_version`：草稿、已发布、已废弃版本；
- `sys_scope_change_log`：节点、关系、集合规则变更记录；
- `order_owner_transfer`：进行中订单归属转移记录；
- `sys_extra_scope_grant`：临时额外授权及有效期。

### 11.7 机构类型变更历史

现有 `sys_org.org_type` 继续保存当前类型，新增不可覆盖的变更记录：

```sql
CREATE TABLE sys_org_type_change (
    id                  BIGINT PRIMARY KEY AUTO_INCREMENT,
    org_id              BIGINT NOT NULL,
    from_org_type       VARCHAR(16) NOT NULL,
    to_org_type         VARCHAR(16) NOT NULL,
    effective_time      DATETIME NOT NULL,
    change_status       VARCHAR(16) NOT NULL COMMENT 'DRAFT/APPROVED/EFFECTIVE/FAILED/CANCELLED',
    org_version         BIGINT NOT NULL,
    impact_snapshot     JSON NOT NULL,
    conflict_snapshot   JSON NULL,
    reason              VARCHAR(500) NULL,
    applicant_id        BIGINT NOT NULL,
    approver_id         BIGINT NULL,
    create_time         DATETIME DEFAULT CURRENT_TIMESTAMP,
    update_time         DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    KEY idx_org_effective (org_id, effective_time),
    KEY idx_change_status (change_status)
);
```

订单建议增加 `org_type_snapshot`，用于稳定历史统计。若现有订单已存在可表达该事实的机构快照 JSON，可复用而不重复加字段。

## 12. 服务架构建议

新增统一的数据权限域服务，避免订单、导出、草稿和仪表盘分别实现权限逻辑。

### 12.1 `OrganizationScopeService`

负责：

- 获取账户当前归属；
- 解析具体机构所属机构集合；
- 查询祖先、后代及权限路径；
- 返回可见部门、机构和账户集合；
- 解释权限来源。

### 12.2 `ScopeRelationService`

负责：

- 节点和关系维护；
- 类型白名单校验；
- 循环、重复、冗余和多父级校验；
- 草稿版本与发布；
- 闭包表构建。

### 12.3 `ScopeGroupService`

负责：

- 动态和静态机构集合；
- 集合成员重算；
- 重叠检测；
- 规则变更影响预览。

### 12.4 `OrganizationTypeChangeService`

负责：

- 经销商与服务商类型转换预检；
- 集合、上下级关系、角色、业务资料和权限差异分析；
- 审批、生效、失败回滚与反向转换；
- 类型历史及转换前后快照查询。

### 12.5 `DataPermissionResolver`

统一输出：

```text
visibleDeptIds
visibleOrgIds
visibleUserIds
allowedActions
permissionPaths
scopeVersionId
```

订单列表、详情、更新、导出、草稿、仪表盘及后续关联模块必须复用该结果。

## 13. 前端交互方案

### 13.1 左侧源数据

页面顶部首先选择源数据方案：

- 方案一：所有实际部门 + 经销商/服务商/医疗机构类型；
- 方案二：所有实际部门 + 同类型机构集合组 + 可搜索的特殊单机构。
- 方案三：所有实际部门 + 可搜索、筛选、批量拖入的全部实际机构。

方案切换前必须检查画布是否已有数据；正式系统中切换方案应通过迁移向导完成，不能直接丢弃原关系。

### 13.2 无限矢量画布

- 拖入节点；
- 节点在逻辑坐标系中不受当前窗口大小限制；
- 鼠标滚轮或工具栏放大、缩小；
- 拖动空白区域平移视口；
- 一键适应全部节点；
- 显示当前缩放比例；
- 移动和自动布局；
- 连接上级和下级；
- 折叠、展开管理范围；
- 显示集合成员数量；
- 显示非法关系和影响警告；
- 支持多个直接父级和多路径高亮；
- 不允许账户节点进入画布。

### 13.3 右侧属性面板

- 编辑节点名称和集合规则；
- 查看集合成员明细；
- 明确展示父节点和子节点；
- 展示全部直接父级，而不是单一父级输入框；
- 查看权限固定向父级继承；
- 分别配置提单、修改、导出等操作能力；
- 删除节点或关系；
- 展示权限路径和冲突说明。

### 13.4 账户权限预览

选择一个账户后展示：

- 当前所属部门或机构；
- 命中的机构集合；
- 可见部门、机构和账户；
- 可见订单数量和样例；
- 每项权限的来源路径；
- 调整前后的权限差异。

### 13.5 机构类型转换

机构管理页和本工作台提供统一转换入口：选择机构与目标类型后，先展示集合成员变化、失效关系、角色冲突、可见账户/订单增减和历史数据处理方式。存在硬冲突时禁用“确认转换”；无硬冲突时提交审批或按权限直接生效。

交互原型见：`docs/prototypes/iam-relation-workbench.html`。

## 14. 兼容与迁移方案

### 14.1 保留现有角色范围

第一阶段保留：

- `all`：公司管理员、超管、财务、设计管理员、质管等；
- `center`：生产相关角色；
- `self`、`hospitals`、`org`：现有仍适用角色。

为市场部后勤、区域管理员等新增 `organization` 数据范围类型，逐步替代 `dept` 固定过滤。

### 14.2 初始化组织节点

1. 将现有 `sys_dept` 转换为 `DEPT` 节点；
2. 根据 `sys_dept_org` 创建初始机构集合或管理关系；
3. 将现有经销商、服务商和医疗机构按类型、地区生成默认集合；
4. 将区域管理员当前部门生成默认管理根；
5. 生成第一版关系闭包。

### 14.3 初始化账户归属

- 企业账户优先使用 `sys_user.dept_id`；
- 业务账户优先使用 `sys_user.org_id`；
- 无部门、无机构或归属冲突账户进入迁移异常清单；
- 不自动猜测不明确归属。

### 14.4 初始化订单归属

- 根据订单现有 `operator_dept_id`、`org_id` 回填实际数据归属；
- 无法确定归属的订单进入异常清单；
- 不覆盖订单现有历史快照字段；
- 第一版上线前完成权限结果抽样对比。

### 14.5 双轨运行

上线初期同时计算旧 `dept` 权限和新组织权限，只记录差异，不立即影响用户。确认差异符合预期后，再按角色逐批切换。

### 15.1 图结构测试

- 自环、两节点环、多节点环；
- 祖先与后代反向连接；
- 重复和冗余边；
- 多父级；
- 跨公司关系；
- 禁用节点和超深层级。

### 15.2 机构集合测试

- 手工包含和排除；
- 同一机构命中多个集合；
- 机构类型或地区变更；
- 大批量机构的重算性能。

### 15.3 全部实际机构方案测试

- 数百至数千机构的搜索、筛选、虚拟滚动和批量拖入；
- 已入画布状态与快速定位；
- 新增机构进入待编排清单；
- 大图折叠、自动布局、发布和闭包构建性能。

### 15.4 权限测试

- 单路径逐级权限交集；
- 多路径权限并集；
- 角色权限与组织权限交集；
- 下级不能反向查看上级；
- 列表、详情、更新、导出结果一致；
- 草稿和仪表盘使用相同范围；
- 越权访问返回统一结果。

### 15.5 组织变更测试

- 部门移动、合并、拆分和停用；
- 账户调岗；
- 机构移入或移出集合；
- 关系定时生效和失效；
- 进行中订单交接；
- 历史订单快照不被覆盖；
- 版本发布和回滚。

### 15.6 机构类型转换测试

- 经销商转服务商、服务商转经销商；
- 动态集合自动迁移、静态集合冲突；
- 入边、出边和多父级路径重新校验；
- 专属角色和业务关系冲突阻断；
- 账户绑定与机构 ID 保持不变；
- 历史订单类型快照不变，当前权限按新类型更新；
- 并发修改、定时生效、失败回滚和反向转换。

## 16. 风险与控制措施

| 风险 | 控制措施 |
|---|---|
| 任意连线导致越权 | 类型白名单、循环检测和发布前影响预览 |
| 数百机构导致画布失控 | 优先采用集合；方案三使用检索、虚拟列表、折叠和按需渲染 |
| 动态集合变化导致权限突增 | 成员差异预览、审批和审计 |
| 多路径难以解释 | 保存权限路径并在账户预览中展示 |
| 组织调整破坏历史事实 | 订单归属快照和组织版本 |
| 各模块权限实现不一致 | 统一 `DataPermissionResolver` |
| 递归查询性能不足 | 发布时构建闭包表和缓存 |
| 迁移后权限差异过大 | 双轨计算、差异报告和分角色切换 |
| 机构类型转换造成隐性越权 | 转换预检、硬冲突阻断、前后权限差异和审批审计 |

## 17. 分阶段实施建议

### 第一阶段：基础模型和只读预览

- 建立范围节点、机构集合、关系和版本模型；
- 完成关系校验与闭包计算；
- 完成账户权限预览；
- 与旧权限双轨对比，不改变生产权限结果。

### 第二阶段：订单查询切换

- 新增统一权限解析服务；
- 接入订单列表、详情和导出；
- 市场部后勤和区域管理员切换到 `organization` 范围；
- 保留快速回退开关。

### 第三阶段：完整业务接入

- 接入草稿、修改、仪表盘、通知和其他订单关联模块；
- 上线组织变更影响预览；
- 上线进行中订单交接和历史审计。

### 第四阶段：清理旧逻辑

- 清理仅为区域管理员保留的 `dept` 特殊逻辑；
- 保留仍有明确业务价值的固定范围；
- 完成性能优化、审计报表和运维监控。

## 18. 待业务确认事项

1. 普通管理关系是否默认允许查看全部历史订单，还是只允许查看关系生效后的订单。
2. 市场部后勤是否可以代下级提单和修改订单，还是仅查看。
3. 区域管理员是否可以查看或管理下级账户草稿。
4. 一个账户是否允许同时拥有多个主要归属；建议第一阶段只允许一个。
5. 经销商与医疗机构之间是否存在真实上下级；普通业务关联不进入画布，进入画布即继承查看权限。
6. 机构集合发生重叠时是否仅提示，还是强制禁止部分类型重叠。
7. 部门合并后，旧部门历史订单是否只进入审计入口。
8. 组织关系变更是否需要公司管理员二次审批。
9. 机构类型转换是否必须审批，以及允许立即生效还是支持预约生效。
10. 经销商与服务商各自有哪些专属角色、资料和业务关系必须作为转换硬冲突。

## 19. 最终结论

本方案不采用无约束的任意连接，而是提供三种可选配置粒度，并统一使用支持多父级的有向无环关系：

```text
实际部门节点
  + 机构类型 / 机构集合 / 全部实际机构（三选一主方案）
  + 类型受限、支持多父级的有向无环关系
  + 独立额外授权
  + 订单历史归属快照
  + 保留机构ID的机构类型转换历史
```

账户通过所属部门或机构自动继承组织关系产生的数据范围，角色继续控制功能权限。多父级查看范围取并集，操作能力按“路径内取交集、路径间取并集”计算。组织架构和机构当前类型可以调整并触发当前权限重算，但机构主体 ID、账户绑定以及订单创建时的提单人、部门、机构类型和组织路径必须保持可追溯。
