# 订单创建时项目分类名称兜底设计

## 背景

部分历史 `rebuild_project` 数据存在 `category_code` 非空、`category_name` 为空的情况。订单创建时，`OrderDataValidator` 当前把这类数据视为系统错误，导致订单功能不可用。

## 目标

正式订单创建/提交只以 `categoryCode` 作为项目分类主数据的必需条件。项目名称为空时，使用分类编码查询有效字典名称完成订单明细快照，避免历史脏数据阻断下单，同时不允许生成空分类名称的订单明细。草稿保存仍遵守原有模式：允许不完整草稿，正式提交时重新执行完整校验。

## 方案

在订单明细项目校验逻辑中：

1. 项目不存在或已禁用时，继续按现有规则拒绝创建。
2. `categoryCode` 为 null、空字符串或全空白时，正式创建/提交拒绝；草稿模式保持原有允许不完整数据的行为。
3. `categoryCode` 有值且项目主数据 `categoryName` 有值时，使用项目主数据名称。
4. `categoryCode` 有值但项目主数据 `categoryName` 为 null、空字符串或全空白时，按 `sys_dict.dict_code = categoryCode` 精确匹配，并在数据库查询层限定 `status = 1`、`is_deleted = 0`、`dict_name IS NOT NULL`、`TRIM(dict_name) <> ''`，查询 `dict_name` 作为订单明细分类名称；名称过滤必须在 `LIMIT 1` 之前生效。
5. 字典查询不到名称、名称为空白或查询异常时，拒绝创建并记录项目 ID、分类编码及原因；不得写入空分类名称。

不信任前端提交的分类名称；订单快照始终由项目主数据名称或字典补齐。该规则同时覆盖正式订单的直提和草稿转正式入口；草稿保存入口不因名称缺失而阻断，但转正式时必须补齐。

## 测试

增加订单数据校验测试，覆盖：

- 项目已有分类名称时使用该名称，并忽略前端提交的名称；
- 项目分类名称为空但字典可查时成功补齐；
- 分类编码为空、字典查不到、字典无效或查询异常时仍拒绝正式创建/提交；
- 草稿模式允许不完整数据，转正式时执行上述完整校验。
