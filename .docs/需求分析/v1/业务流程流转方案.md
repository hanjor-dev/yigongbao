## 1. 背景与目标

### 1.1 需求背景

在订单生命周期中，流程节点可能会动态变化，例如：
- 不需要某个环节（如出库环节）
- 在生产环节前增加新的环节（A环节）
- 调整环节顺序

传统的固定枚举状态实现方式难以满足这种灵活性要求，因此需要设计一套**可配置的动态流程流转机制**。

### 1.2 核心目标

- **流程可配置**：节点可增删、顺序可调整，无需代码改动
- **版本化管理**：新流程模板发布后，不影响进行中的老订单
- **权限可控**：每个节点可配置可处理的角色范围
- **审计可追溯**：每次流转都有记录，支持问题排查和责任认定
- **实现轻量**：不过度引入复杂框架，降低维护成本

## 2. 方案概述

### 2.1 推荐方案：数据库配置化的轻量级状态机

核心思想：

| 概念 | 说明 |
|------|------|
| **节点（Node）** | 流程中的每个环节，如"待审核""设计中""已完成" |
| **事件（Event）** | 触发状态流转的动作，如"提交""通过""驳回""完成" |
| **转移规则（Transition）** | 定义从节点A + 事件E → 节点B 的流转关系 |
| **动作（Action）** | 状态变更时执行的业务逻辑 |
| **条件（Guard）** | 判断能否执行该转移的校验逻辑 |

### 2.2 核心机制

1. **流程模板化**：每种订单类型对应一个流程模板
2. **模板版本化**：流程调整通过发布新版本实现，不影响老订单
3. **节点可插拔**：新增/删除节点只需修改配置
4. **日志全记录**：每次流转都记录操作人、时间、结果

## 4. 核心模块设计

### 4.1 流程引擎（WorkflowEngine）

核心职责：
- 加载流程模板
- 执行状态流转
- 校验流转条件
- 执行流转动作
- 记录执行日志

```
┌─────────────────────────────────────────────────────────┐
│                    WorkflowEngine                       │
├─────────────────────────────────────────────────────────┤
│  fire(order, event, operator)                           │
│    │                                                    │
│    ├─→ 1. 获取当前节点                                   │
│    ├─→ 2. 查找转移规则                                   │
│    ├─→ 3. 校验流转条件（Guard）                          │
│    ├─→ 4. 校验操作权限                                   │
│    ├─→ 5. 执行流转动作（Action）                         │
│    ├─→ 6. 更新订单当前节点                               │
│    ├─→ 7. 记录流转日志                                   │
│    └─→ 8. 检查是否结束                                  │
└─────────────────────────────────────────────────────────┘
```

### 4.2 流程定义管理

后台功能：
- 新建/编辑/删除流程模板
- 可视化配置节点顺序
- 配置每个节点的属性（角色、表单要求等）
- 配置节点间的转移规则
- 发布新版本

### 4.3 节点类型

| 节点类型 | 说明 |
|----------|------|
| `start` | 起始节点 |
| `end` | 结束节点 |
| `normal` | 普通人工处理节点 |
| `decision` | 判断节点（自动根据条件分支） |
| `system` | 系统节点（自动执行） |

## 5. 流转规则设计

### 5.1 事件定义

| 事件 | 说明 |
|------|------|
| `submit` | 提交/提交审核 |
| `approve` | 通过/审核通过 |
| `reject` | 驳回/审核拒绝 |
| `complete` | 完成当前节点 |
| `skip` | 跳过当前节点 |
| `rollback` | 退回上一步 |
| `cancel` | 取消订单 |
| `terminate` | 终止流程 |

### 5.2 权限控制

每个节点可配置：
- 可处理该节点的角色列表
- 可执行哪些事件（如普通业务员只能提交，设计管理员才能通过）

## 6. 版本管理策略

### 6.1 核心原则

- **订单绑定流程版本**：订单创建时关联当前发布的流程版本
- **老订单走老流程**：流程版本发布后，已创建的订单继续使用原有版本
- **新订单走新流程**：新创建的订单使用最新发布的流程版本

### 6.2 迁移策略（可选）

如需让进行中的老订单切换到新流程：
- 仅允许在某些"安全节点"迁移（如已完成设计，未开始生产）
- 或提供"节点映射表"（旧节点→新节点）

> 迁移策略可根据实际需求后续细化

## 7. 应用示例

### 7.1 示例一：删除出库环节

**操作**：
1. 在新流程版本中删除 `warehouse_out` 节点
2. 或保留节点但设置 `required=false` + 默认跳过条件
3. 发布新版本

**效果**：
- 新订单不再经过出库环节
- 老订单继续走完原有流程

### 7.2 示例二：新增"A环节"

**操作**：
1. 在节点定义中新增 `a_step` 节点
2. 配置转移规则：`design_review → a_step → print`
3. 设置节点属性：处理角色、表单要求等
4. 发布新版本

**效果**：
- 新订单在设计和打印之间增加A环节
- 老订单不受影响

## 8. 与现有功能的关系

### 8.1 订单字段

流程节点可能需要关联特定的表单/字段要求（如某节点需要上传附件、填写备注等），这部分与订单字段设计关联。

### 8.2 权限系统

节点的"可处理角色"配置复用现有权限系统。

### 8.3 消息通知

节点流转时可触发消息通知（如审核通过通知业务员、进入新环节通知相关人员等）。

| 属性 | 说明 |

| `timeout_hours` | 超时预警时间（小时） |
| `auto_assign` | 自动分配规则 |
| `notify_config` | 节点进入时的通知配置 |
