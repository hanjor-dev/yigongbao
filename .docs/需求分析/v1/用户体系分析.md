# 用户体系分析报告

## 一、文档概述

本文档详细描述医工宝系统的**用户体系概念设计**，包括账户分类、角色体系、机构管理、部门管理、权限模型等核心概念。

整个用户体系采用**动态可配置化设计**，通过后台管理系统实现分类、角色、权限的灵活配置，以满足业务发展过程中的需求变化。

> **说明**：账户的创建、注册、审批等流程属于账户生命周期管理范畴，将单独进行需求分析，本文档仅专注用户体系的概念模型设计。

> **2026-03-12 重要更新**：
> - 账户分类简化为内部用户、外部用户两类
> - 术语变更：组织→机构，组织类型→机构类型
> - 所有账户必须归属机构
> - 新增部门概念，用户可选归属部门
> - 删除子账户/层级关系功能
> - 各种类型机构均可创建多个

---

## 二、核心设计理念

### 2.1 设计目标

- **灵活性**：分类、角色、权限均可通过后台动态配置，无需代码修改
- **扩展性**：所有账户分类预留层级关系，支持未来业务扩展
- **单一角色**：一个账户对应一个角色，职责清晰，便于管理
- **数据隔离**：按角色+功能点+数据范围控制数据可见范围
- **机构归属**：账户必须归属于具体机构，机构是业务运营的实体单位
- **部门归属（可选）**：用户可选择归属于机构下的部门，非必填

### 2.2 重要概念澄清

本文档涉及四个核心概念：**账户分类**、**机构类型**、**机构**、**部门**。这四个概念处于不同层级，理解它们的关系是掌握整个用户体系的关键。

```
┌─────────────────────────────────────────────────────────────────────┐
│                    概念层级关系图                                     │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  【维度一：账户分类】（用户来源维度）                                  │
│  ├── 内部用户：由管理员创建                                           │
│  └── 外部用户：自主注册                                               │
│                                                                     │
│  【维度二：机构类型】（业务类型）                                      │
│  ├── 生产企业                                                       │
│  ├── 经销商                                                         │
│  ├── 医疗机构                                                       │
│  └── 其他                                                           │
│                                                                     │
│  【维度三：机构】（具体实例）                                         │
│  ├── 医工宝科技股份有限公司（机构类型=生产企业）                   │
│  ├── 华东医疗器械公司（机构类型=经销商）                           │
│  ├── 上海市第一人民医院（机构类型=医疗机构）                       │
│  └── XX口腔诊所（机构类型=医疗机构）                               │
│                                                                     │
│  【维度四：部门】（机构内的二级单位，可选归属）                       │
│  ├── 生产企业：设计部、生产部、质检部、销售部...                   │
│  ├── 经销商：华东区、华南区、客服部...                              │
│  └── 医疗机构：口腔科、检验科、药剂科...                           │
│                                                                     │
│  【账户】（具体用户）                                                │
│  ├── 内部用户 + 机构 → 设计师、生产员、管理员...                  │
│  └── 外部用户 + 机构 → 机构管理员、机构用户...                      │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

> **账户分类 vs 机构类型 vs 机构 vs 部门**：
> - **账户分类**：用户来源方式（内部/外部），回答"这个用户是怎么进来的？"
> - **机构类型**：业务类型（生产企业/经销商/医疗机构），回答"这个用户属于哪类业务？"
> - **机构**：具体的企业/医院实例，回答"这个用户在哪个具体单位工作？"
> - **部门**：机构内的二级单位，回答"这个用户在单位的哪个部门工作？"
> - **关系**：账户分类 + 机构 + 部门（可选） = 一个完整的用户身份

## 三、账户分类

### 3.1 分类说明

账户分类是对用户身份的基本划分，按**用户来源**进行区分。

| 账户分类 | 说明 | 归属机构 | 备注 |
|---------|------|---------|------|
| 内部用户 | 平台方员工或其他，由管理员创建 | 是 | 必须归属具体机构 |
| 外部用户 | 外部合作机构或个人，自主注册 | 是 | 注册时需关联或创建机构 |

> **重要说明**：
> - **所有账户都必须归属于具体的机构**
> - 机构类型（生产企业/经销商/医疗机构）不属于账户分类，而是机构的属性
> - 账户分类表示的是内部/外部用户的概念，不要混淆

## 四、机构管理

### 4.1 机构概念说明

机构是业务运营的实体单位，用于**需要归属具体企业/单位的账户**。

```
┌─────────────────────────────────────────────────────────────────────┐
│                    账户与机构的关联关系                               │
├─────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  所有账户都必须归属到具体的机构：                                        │
│  ├── 内部用户：关联到具体机构（生产企业/经销商/医疗机构）            │
│  └── 外部用户：关联到自主创建或已存在的机构                           │
│                                                                         │
└─────────────────────────────────────────────────────────────────────┘
```

### 4.2 机构类型

机构类型是机构的一个属性，用于区分机构的业务类型。

| 机构类型 | 说明 | 账户约束 |
|---------|------|---------|
| 生产企业 | 生产加工企业 | 内部用户 |
| 经销商 | 销售渠道合作方 | 内部用户、外部用户 |
| 医疗机构 | 医院、诊所等 | 内部用户、外部用户 |
| 其他 | 其他类型机构 | 可扩展 |

> **说明**：一个机构只能属于一种机构类型，但一种机构类型下可以创建多个机构，且各种类型机构之间无层级关系。

## 五、角色体系

### 5.1 角色说明

角色代表用户在系统中的职能身份。

一个账户对应一个角色，职责清晰，便于管理和审计。

### 5.2 账户分类与角色的绑定关系

一个账户可以拥有什么角色，取决于**账户分类**和**机构类型**的组合。

| 账户分类 | 机构类型 | 可选角色 |
|---------|---------|---------|
| 内部用户 | 生产企业 | 设计师、设计师管理员、生产员、生产管理员、质管、库管、财务、公司管理员（一级）、公司管理员（二级）、信息中心 |
| 内部用户 | 经销商 | 区域管理员、业务员 |
| 内部用户 | 医疗机构 | 医生 |
| 外部用户 | 经销商/医疗机构/其他 | 机构管理员（外部）、机构用户 |

> **说明**：
> - 内部用户的角色与机构类型绑定，不同机构类型下可用的角色不同
> - 外部用户的角色（机构管理员/机构用户）是独立的体系，与内部用户角色不混用

### 5.3 角色说明

| 角色 | 归属分类 | 适用机构类型 | 说明 |
|------|---------|-------------|------|
| 设计师 | 内部用户 | 生产企业 | 负责设计工作 |
| 设计师管理员 | 内部用户 | 生产企业 | 设计团队管理员，负责设计工作分配、审核、统计等，数据范围为所属部门及下级 |
| 生产员 | 内部用户 | 生产企业 | 负责生产加工 |
| 生产管理员 | 内部用户 | 生产企业 | 管理生产流程、调度 |
| 质管 | 内部用户 | 生产企业 | 质量检验、质量管理 |
| 库管 | 内部用户 | 生产企业 | 仓库管理、库存管理 |
| 财务 | 内部用户 | 生产企业 | 财务对账、收款管理 |
| 区域管理员 | 内部用户 | 经销商 | 管理下属业务员 |
| 业务员 | 内部用户 | 经销商 | 负责订单开拓、客户维护 |
| 医生 | 内部用户 | 医疗机构 | 医生、查看数据 |
| 公司管理员（一级） | 内部用户 | 生产企业 | 系统最高权限，拥有全部系统功能 |
| 公司管理员（二级） | 内部用户 | 生产企业 | 业务管理员，拥有全部业务功能（不可访问系统配置） |
| 信息中心 | 内部用户 | 生产企业 | 系统运维、备份管理、部分系统配置权限 |
| 机构管理员（外部） | 外部用户 | - | 外部机构的管理员，可创建机构用户、管理本机构数据 |
| 机构用户 | 外部用户 | - | 外部机构内部普通用户，由机构管理员创建 |

## 六、部门管理

### 6.1 部门概念说明

部门是机构内的二级单位，用于更精细化管理用户。

> **重要说明**：
> - 部门是**可选归属**，用户可以仅归属于机构而不归属于部门
> - 一个机构可以创建多个部门
> - 一个用户只能归属于一个部门（或不归属于任何部门）

### 6.2 部门示例

```
┌─────────────────────────────────────────────────────────────────────┐
│ 机构（生产企业 - 医工宝科技股份有限公司）                          │
│   设计部                                                              │
│   ├── 账户：设计师-张三                                              │
│   ├── 账户：设计师-李四                                              │
│   └── 账户：设计管理员-王五                                          │
│   生产部                                                              │
│   ├── 账户：生产员-赵六                                              │
│   └── 账户：生产管理员-陈七                                          │
│   销售部（未归属部门）                                               │
│   └── 账户：业务员-陈八                                              │
└─────────────────────────────────────────────────────────────────────┘
```

### 6.3 部门信息字段

| 字段 | 必填 | 说明 |
|-----|:---:|------|
| 部门名称 | ✓ | 部门名称，同一机构下唯一 |
| 部门编码 | ✓ | 系统唯一标识，自动生成（如：DEPT-001） |
| 所属机构 | ✓ | 关联的机构 |
| 部门负责人 | - | 部门负责人账户 |
| 备注说明 | - | 补充信息 |

### 6.4 部门管理功能

| 功能 | 说明 |
|-----|------|
| 新增部门 | 在机构下创建新的部门 |
| 编辑部门 | 修改部门信息 |
| 删除部门 | 删除部门（仅当该部门下无账户时允许） |
| 部门列表 | 分页展示某机构下的所有部门 |
| 启用/停用 | 启用或停用部门 |

### 6.5 部门管理权限

| 操作 | 一级管理员 | 二级管理员 |
|:--------:|:--------:|
| 新增部门 | ✓ | ✓ |
| 编辑部门 | ✓ | ✓ |
| 删除部门 | ✓ | ✗ |
| 查看部门列表 | ✓ | ✓ |
| 查看部门详情 | ✓ | ✓ |
| 启用/停用部门 | ✓ | ✗ |

> 二级管理员可以管理部门，但不可删除或停用部门。

## 七、权限模型

### 7.1 权限组成

权限由三部分组成：
- **菜单权限**：控制用户可见的菜单项（分为业务功能菜单、系统配置菜单）
- **功能点权限**：控制用户在功能模块下的具体操作能力
- **数据可视范围权限**：控制用户可查询到的相关数据范围（比如仅自己、全部等）

### 7.2 菜单分类

菜单分为两大类：

| 分类 | 说明 | 示例 |
|------|------|------|
| 业务功能菜单 | 业务相关的功能菜单 | 订单管理、案例管理、财务管理 |
| 系统配置菜单 | 系统后台管理菜单 | 账户分类管理、角色管理、菜单权限管理、系统参数配置 |

> **说明**：一级管理员可配置全部菜单权限，二级管理员仅可配置业务功能菜单权限。

### 7.3 功能点标识规范

采用"模块:操作"格式命名权限点：

| 格式 | 示例 | 说明 |
|------|------|------|
| 模块:list | order:list | 查看列表 |
| 模块:add | order:add | 新增 |
| 模块:edit | order:edit | 编辑 |
| 模块:delete | order:delete | 删除 |
| 模块:export | order:export | 导出 |
| 模块:audit | order:audit | 审核 |
| 模块:detail | order:detail | 查看详情 |

> **扩展说明**：功能点标识采用可扩展命名规范，新增功能只需在对应模块下定义新的操作标识，无需修改表结构。

### 7.4 权限配置方式

权限配置到**角色**级别，每个角色可以独立配置菜单可见性和功能点权限。

```
权限配置 = 菜单可见 + 功能点权限

示例 - 设计师角色权限配置：
├── 案例管理
│   ├── case:list       ✓
│   ├── case:add        ✓
│   ├── case:edit       ✓
│   └── case:detail     ✓
├── 订单管理
│   ├── order:list      ✓（查看本机构数据）
│   └── order:detail    ✓

示例 - 机构管理员（外部）权限配置：
├── 订单管理
│   ├── order:list      ✓（查看本机构全部数据）
│   ├── order:add       ✓
│   ├── order:edit      ✓
│   └── ...
├── 机构管理
│   ├── sub_account:list   ✓
│   ├── sub_account:add    ✓
│   ├── sub_account:edit   ✓
│   └── sub_account:delete ✓

示例 - 业务员角色权限配置：
├── 订单管理
│   ├── order:list      ✓（仅看自己）
│   ├── order:add       ✓
│   ├── order:edit      ✓（仅编辑自己创建的）
│   ├── order:delete    ✗
│   └── order:export    ✗
```

> **说明**：功能点权限控制"能否执行某操作"，具体能操作哪些数据由数据权限控制模块配置。

## 八、数据权限控制

### 8.1 权限模型说明

功能点权限和数据范围权限是**两个正交维度**：

| 维度 | 作用 | 示例 |
|------|------|------|
| 功能点权限 | 控制"能不能做"某个操作 | 是否有编辑订单的权限 |
| 数据范围权限 | 控制"能查看到和操作哪些数据" | 只能查看和编辑自己创建的，还是可以查看和编辑本机构的 |

> **重要澄清**：本章节的“数据范围”既包括“按机构隔离”的范围（`org`），也包括订单业务中“按医院范围”的范围（`hospitals`）。  
> 这里的“医院”是订单创建时选择的“提单医院”（后台医院管理维护），**不是**账户归属的“机构”概念。

```
组合示例：
- 设计师 + order:edit + org    → 有编辑权限，且只能编辑本机构的订单
- 机构管理员（外部）+ order:edit + org → 有编辑权限，能编辑本机构的全部订单
```

### 8.2 数据范围类型

数据范围通过配置方式实现灵活控制，系统预设以下范围类型：

| 范围标识 | 说明 | 示例 |
|---------|------|------|
| self | 仅自己创建的数据 | 业务员只能看自己开拓的订单 |
| hospitals | 指定医院列表的数据 | 业务员只能创建/查看医院A、B、C的订单；设计师管理员只能查看医院B、C、D的设计订单 |
| dept | 所属部门的数据 | 设计师/业务员只能查看本部门的订单 |
| org | 所属机构/企业的数据 | 设计师看本企业全部订单 |
| all | 全部数据 | 公司管理员看所有数据 |

> **说明**：
> - `self`范围适用于所有账户
> - `hospitals`范围适用于需要“按医院业务范围”控制数据的角色（如业务员、区域管理员、设计师管理员等），医院范围由账号配置决定
> - `org`范围适用于需要归属机构的账户（内部用户、外部用户）
> - `dept`范围适用于需要按部门隔离数据的角色（如设计师、业务员等），数据范围由账号所属部门决定
> - `all`范围适用于公司管理员等特殊角色

> **扩展说明**：数据范围类型可通过后台配置扩展，支持自定义业务规则。

#### 8.2.1 医院范围的配置方式（方案4：预设医院组合模板）

为避免管理员在创建账户时频繁手动勾选大量医院，系统提供“医院组合模板（Hospital Group Template）”机制：

- **模板维护**：在后台“医院组合模板管理”中预先维护常用医院组合（例如：华东区医院组、口腔专科医院组、重点合作医院组等）
- **账户创建**：管理员创建账户时仅需选择一个模板，系统自动带出模板内医院列表；如有例外可进行少量增删（可选）

模板建议字段：

| 字段 | 必填 | 说明 |
|------|:---:|------|
| 模板名称 | ✓ | 模板名称（如：华东区医院组） |
| 模板编码 | ✓ | 系统唯一标识，自动生成（如：HOS-GRP-001） |
| 医院列表 | ✓ | 该模板包含的医院（多选） |
| 适用机构类型 | - | 可选：生产企业/经销商/医疗机构/其他（用于筛选） |
| 备注说明 | - | 补充信息 |

账户侧建议字段：

| 字段 | 必填 | 说明 |
|------|:---:|------|
| 医院范围模板 | - | 选择一个医院组合模板（可为空） |
| 医院范围（覆盖/追加） | - | 在模板基础上增删医院后的最终结果（以最终医院列表为准） |

### 8.3 角色-功能点-数据范围配置

每个角色的每个功能点都可单独配置数据范围，实现精细化的数据权限控制。

```
配置模型：角色 + 功能点 + 数据范围

示例配置：

| 角色         | 功能点           | 数据范围     | 说明                  |
|-------------|------------------|-------------|---------------------|
| 设计师      | order:list       | org         | 看本机构订单         |
| 设计师      | order:edit       | org         | 编辑本机构订单       |
| 设计师      | case:list        | self        | 看自己设计的案例     |
| 设计师管理员 | order:list       | dept_and_child | 看本部门及下级部门的订单 |
| 设计师管理员 | order:audit      | dept_and_child | 审核本部门及下级的设计订单 |
| 设计师管理员 | design:assign    | dept_and_child | 分配设计任务给团队成员 |
| 业务员      | order:list       | hospitals   | 看自己负责医院范围内的订单（不一定等于自己创建的） |
| 业务员      | order:add        | hospitals   | 仅可为医院范围内医院创建订单 |
| 机构管理员   | order:list       | org         | 看本机构全部订单     |
| 机构用户    | order:list       | self        | 看自己创建的订单     |
| 公司管理员   | order:list       | all         | 看全部订单           |
```

### 8.4 数据范围过滤机制

系统通过以下方式实现数据范围控制：

1. **权限加载**：用户登录时加载其角色对应的所有功能点及数据范围配置
2. **动态过滤**：业务查询时，根据当前用户权限动态注入数据过滤条件
3. **灵活配置**：新增角色无需代码修改，直接在后台配置数据范围即可

```
┌─────────────────────────────────────────────────────────────────────┐
│                    数据范围过滤原理                                   │
├─────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  业务查询示例（伪代码）：                                              │
│                                                                         │
│  function queryOrders(currentUser, permission):                      │
│      // 1. 获取用户拥有的角色及对应的数据范围                          │
│      dataScope = getDataScope(currentUser, 'order:list')            │
│                                                                         │
│      // 2. 根据数据范围动态构建查询条件                                │
│      switch (dataScope):                                              │
│          case 'self':                                                 │
│              WHERE creator_id = currentUser.id                        │
│          case 'hospitals':                                            │
│              WHERE hospital_id IN (currentUser.hospitalScopeIds)       │
│          case 'org':                                                  │
│              WHERE org_id = currentUser.orgId                         │
│          case 'all':                                                  │
│              // 不过滤，全量查询                                      │
│                                                                         │
│      // 3. 返回符合权限的数据                                         │
│      return db.select(conditions)                                     │
│                                                                         │
└─────────────────────────────────────────────────────────────────────┘
```

### 8.5 数据隔离原则

- **机构隔离**：不同企业/机构的数据默认隔离
- **角色隔离**：不同角色之间默认数据隔离
- **医院隔离（按范围）**：当角色配置为 `hospitals` 数据范围时，仅可访问医院范围内的订单数据

### 9.1 术语解释

| 术语 | 说明 |
|------|------|
| 账户分类 | 用户的来源方式划分（内部用户、外部用户） |
| 机构类型 | 机构的业务类型（生产企业、经销商、医疗机构、其他） |
| 机构 | 业务运营的实体单位，如具体的生产企业、经销商、医疗机构 |
| 部门 | 机构内的二级单位，用于更精细化管理用户 |

| 功能点 | 权限的最小控制单元，如 order:add 表示新增订单 |
| 数据范围 | 控制数据可见范围的配置项（self/hospitals/org/all） |
| 账户模式 | 结算方式，如预付费、月结等 |
