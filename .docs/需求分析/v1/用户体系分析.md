# 用户体系分析报告

## 一、文档概述

本文档详细描述医工宝系统的**用户体系概念设计**，包括账户分类、角色体系、层级关系、权限模型等核心概念。

整个用户体系采用**动态可配置化设计**，通过后台管理系统实现分类、角色、权限的灵活配置，以满足业务发展过程中的需求变化。

> **说明**：账户的创建、注册、审批等流程属于账户生命周期管理范畴，将单独进行需求分析，本文档仅专注用户体系的概念模型设计。

---

## 二、核心设计理念

### 2.1 设计目标

- **灵活性**：分类、角色、权限均可通过后台动态配置，无需代码修改
- **扩展性**：所有账户分类预留层级关系，支持未来业务扩展
- **单一角色**：一个账户对应一个角色，职责清晰，便于管理
- **数据隔离**：按角色+功能点+数据范围控制数据可见范围
- **组织归属**：账户可归属于具体组织，组织是业务运营的实体单位

### 2.2 重要概念澄清

> **账户分类 vs 组织**：
> - **账户分类**是泛称/模板概念，代表一类业务主体类型（如"生产企业"、"经销商"）
> - **组织**是具体实例，代表某一家具体的企业或机构（如"A医疗器械公司"、"XX医院"）
> - 账户 = 属于某个组织的具体用户

```
账户分类（泛称）        组织（具体实例）              账户（用户）
┌─────────────┐       ┌─────────────────┐         ┌─────────────┐
│ 生产企业    │  ←─── │ A医疗器械公司   │  ←───── │ 设计师-张三 │
│ 经销商      │       │ B医疗器械公司   │         │ 设计师-李四 │
│ 医疗机构    │       │ XX医院         │         │ 医生-王五   │
└─────────────┘       │ YY口腔诊所     │         └─────────────┘
                      └─────────────────┘
```

## 三、账户分类

### 3.1 分类说明

账户分类是对用户身份的基本划分，每个分类代表一类业务主体。

| 账户分类 | 说明 | 是否有子级 | 备注 |
|---------|------|-----------|------|
| 生产企业 | 公司内部员工 | ✓ 有（可配置启用） | 生产加工企业 |
| 经销商 | 销售渠道合作方 | ✓ 有（可配置启用） | 代理商、经销商 |
| 医疗机构 | 医院、诊所等 | ✓ 有（可配置启用） | 医院、诊所 |
| 监管机构 | 政府部门监管 | ✓ 有（可配置启用） | 药监局、卫生部门 |
| 患者 | 个人用户 | ✓ 有（可配置启用） | 预留，后期开放 |

> **重要说明**：所有账户分类都预留子级功能，通过后台配置决定是否启用。后期任何分类需要启用层级关系时，可直接在后台配置。

## 四、组织管理

### 4.1 组织概念说明

组织是业务运营的实体单位，**用于需要组织机构的账户分类**。

> **可配置设计**：账户分类是否需要归属组织，通过后台配置决定。
> - 需要组织的分类：生产企业（仅允许1个）、经销商、医疗机构
> - 不需要组织的分类：监管机构、患者（可扩展配置）

```
┌─────────────────────────────────────────────────────────────────────┐
│               账户分类是否需要组织 - 可配置设计                      │
├─────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  账户分类配置                                                         │
│  ┌──────────────┬──────────────┬──────────────┐                      │
│  │   分类       │  是否需要组织 │    说明      │                      │
│  ├──────────────┼──────────────┼──────────────┤                      │
│  │ 生产企业     │     是       │ 一个组织     │                      │
│  │ 经销商       │     是       │ 多个组织     │                      │
│  │ 医疗机构     │     是       │ 多个组织     │                      │
│  │ 监管机构     │     否       │ 特殊权限账户 │                      │
│  │ 患者         │     否       │ 个人注册账户 │                      │
│  └──────────────┴──────────────┴──────────────┘                      │
│                                                                         │
└─────────────────────────────────────────────────────────────────────┘
```

### 4.2 组织类型约束

- **生产企业**：仅允许创建一个（代表本公司）
- **经销商**：可创建多个，彼此之间无层级关系
- **医疗机构**：可创建多个，彼此之间无层级关系

## 五、角色体系

### 5.1 角色说明

角色代表用户在系统中的职能身份。

一个账户对应一个角色，职责清晰，便于管理和审计。

### 5.2 账户分类与角色的绑定关系

一个账户分类可以绑定多个可选角色（在后台配置），但一个账户只能拥有一个角色。

| 账户分类 | 可选角色 |
|---------|
| 生产企业 | 业务员、区域管理员、设计师、设计管理员、生产员、生产管理员、质管、库管、财务、公司管理员（一级）、公司管理员（二级）、信息中心 |
| 经销商 | 区域管理员、业务员（区域管理员下属角色） |
| 医疗机构 | 医生（暂定）、预留子级配置 |
| 监管机构 | 监管员、预留子级配置 |
| 患者 | 病人、预留子级配置 |

### 5.3 角色说明

| 角色 | 归属分类 | 说明 |
|------|---------|------|
| 业务员 | 生产企业/经销商 | 负责订单开拓、客户维护 |
| 区域管理员 | 生产企业/经销商 | 管理下属业务员 |
| 设计师 | 生产企业 | 负责设计工作 |
| 设计管理员 | 生产企业 | 管理设计团队、审核设计 |
| 生产员 | 生产企业 | 负责生产加工 |
| 生产管理员 | 生产企业 | 管理生产流程、调度 |
| 质管 | 生产企业 | 质量检验、质量管理 |
| 库管 | 生产企业 | 仓库管理、库存管理 |
| 财务 | 生产企业 | 财务对账、收款管理 |
| 公司管理员（一级） | 生产企业 | 系统最高权限，拥有全部系统功能（业务功能+后台系统配置功能） |
| 公司管理员（二级） | 生产企业 | 业务管理员，拥有全部业务功能（不可访问系统配置） |
| 信息中心 | 生产企业 | 系统运维、备份管理、部分系统配置权限（具体权限待定） |
| 医生 | 医疗机构 | 医生、查看数据 |
| 监管员 | 监管机构 | 监管执法 |
| 病人 | 患者 | 患者个人端（预留） |

## 六、层级关系

### 5.1 通用层级结构

所有账户分类都预留子级概念，支持后期灵活配置。

```
┌─────────────────────────────────────────────────────────────────────┐
│ 通用层级结构                                                        │
├─────────────────────────────────────────────────────────────────────┤
│  父账户（区域管理员/组长/负责人/科室主任等）                         │
│      └── 子账户（业务员/组员/成员/医生等，可多个，仅一级）           │
└─────────────────────────────────────────────────────────────────────┘
```

### 5.2 层级示例

```
示例1：生产企业
       区域管理员（父）→ 业务员（子）

示例2：经销商
       区域管理员（父）→ 业务员（子）
       （经销商分类下的层级结构与生产企业一致）

示例3：医疗机构（后期可启用）
       科室负责人（父）→ 医生（子）

示例4：生产企业-生产部门（后期可启用）
       生产管理员（父）→ 生产员（子）
```

### 5.3 层级规则

- 子账户只支持**一级**层级，不支持子账户下再创建子账户
- 父账户可以管理多个子账户
- 子账户的数据对父账户可见（用于对账、管理）
- 父账户的数据对子账户不可见

## 七、权限模型

### 7.1 权限组成

权限由三部分组成：
- **菜单权限**：控制用户可见的菜单项（分为业务功能菜单、系统配置菜单）
- **功能点权限**：控制用户在功能模块下的具体操作能力
- **数据可视范围权限**：控制用户可查询到的相关数据范围（比如仅自己、全部等）

### 7.2 菜单分类

菜单分为两大类：

| 分类 | 说明 | 示例 |
|------|------|------|
| 业务功能菜单 | 业务相关的功能菜单 | 订单管理、案例管理、财务管理、患者管理 |
| 系统配置菜单 | 系统后台管理菜单 | 账户分类管理、角色管理、菜单权限管理、系统参数配置 |

> **说明**：一级管理员可配置全部菜单权限，二级管理员仅可配置业务功能菜单权限。

### 7.3 功能点标识规范

采用"模块:操作"格式命名权限点：

| 格式 | 示例 | 说明 |
|------|------|------|
| 模块:list | order:list | 查看列表 |
| 模块:add | order:add | 新增 |
| 模块:edit | order:edit | 编辑 |
| 模块:delete | order:delete | 删除 |
| 模块:export | order:export | 导出 |
| 模块:audit | order:audit | 审核 |
| 模块:detail | order:detail | 查看详情 |

> **扩展说明**：功能点标识采用可扩展命名规范，新增功能只需在对应模块下定义新的操作标识，无需修改表结构。

### 7.4 权限配置方式

权限配置到**角色**级别，每个角色可以独立配置菜单可见性和功能点权限。

```
权限配置 = 菜单可见 + 功能点权限

示例 - 业务员角色权限配置：
├── 订单管理
│   ├── order:list      ✓
│   ├── order:add       ✓
│   ├── order:edit      ✓
│   ├── order:delete    ✗
│   ├── order:export    ✗
│   └── order:audit     ✗
│
示例 - 区域管理员角色权限配置：
├── 订单管理
│   ├── order:list      ✓
│   ├── order:add       ✓
│   ├── order:edit      ✓
│   ├── order:delete    ✓
│   ├── order:export    ✓
│   └── order:audit     ✓
│
示例 - 设计师角色权限配置：
├── 案例管理
│   ├── case:list       ✓
│   ├── case:add        ✓
│   ├── case:edit       ✓
│   └── case:detail     ✓
│
示例 - 公司管理员（一级）权限配置：
├── 全部业务功能菜单
│   ├── 订单管理 ✓
│   ├── 案例管理 ✓
│   ├── 财务管理 ✓
│   └── ...（全部业务功能）
├── 系统配置菜单
│   ├── 账户分类管理 ✓
│   ├── 角色管理 ✓
│   ├── 菜单权限管理 ✓
│   ├── 系统参数配置 ✓
│   └── ...（全部系统配置）
│
示例 - 公司管理员（二级）权限配置：
├── 全部业务功能菜单
│   ├── 订单管理 ✓
│   ├── 案例管理 ✓
│   ├── 财务管理 ✓
│   └── ...（全部业务功能）
├── 系统配置菜单
│   ├── （不可访问）✗
```

> **说明**：功能点权限控制"能否执行某操作"，具体能操作哪些数据由第七章数据权限控制模块配置。

## 八、数据权限控制

### 8.1 权限模型说明

功能点权限和数据范围权限是**两个正交维度**：

| 维度 | 作用 | 示例 |
|------|------|------|
| 功能点权限 | 控制"能不能做"某个操作 | 是否有编辑订单的权限 |
| 数据范围权限 | 控制"能查看到和操作哪些数据" | 只能查看和编辑自己创建的，还是可以查看和编辑下属的 |

```
组合示例：
- 业务员 + order:edit + self         → 有编辑权限，且只能编辑自己创建的订单
- 区域管理员 + order:edit + self-and-sub → 有编辑权限，能编辑自己及下属的订单
```

### 8.2 数据范围类型

数据范围通过配置方式实现灵活控制，系统预设以下范围类型：

| 范围标识 | 说明 | 示例 |
|---------|------|------|
| self | 仅自己创建的数据 | 业务员只能看自己开拓的订单 |
| self-and-sub | 自己及下属的数据 | 区域管理员看自己+下属的订单 |
| org | 所属组织/企业的数据 | 设计师看本企业全部订单 |
| all | 全部数据 | 公司管理员看所有数据 |
| none | 无数据权限 | 监管账户特殊权限（仅查看特定数据） |

> **特殊说明**：
> - `org`范围适用于需要归属组织的账户分类（生产企业/经销商/医疗机构）
> - `none`范围适用于不需要归属组织的账户分类（监管机构），监管账户通过其他方式获取数据查看权限

> **扩展说明**：数据范围类型可通过后台配置扩展，支持自定义业务规则。

### 8.3 角色-功能点-数据范围配置

每个角色的每个功能点都可单独配置数据范围，实现精细化的数据权限控制。

```
配置模型：角色 + 功能点 + 数据范围

示例配置：

| 角色         | 功能点           | 数据范围     | 说明                  |
|-------------|------------------|-------------|---------------------|
| 业务员      | order:list       | self        | 只看自己订单         |
| 业务员      | order:edit       | self        | 只编辑自己订单       |
| 区域管理员  | order:list       | self-and-sub| 看自己+下属订单      |
| 区域管理员  | order:audit      | self-and-sub| 审核下属订单         |
| 设计师      | order:list       | org         | 看本企业全部订单     |
| 设计师      | case:list        | self        | 看自己设计的案例     |
| 财务        | order:list       | org         | 看本企业全部订单     |
| 财务        | finance:view     | org         | 看本企业财务数据     |
| 公司管理员  | order:list       | all         | 看全部订单           |
```

### 8.4 数据范围过滤机制

系统通过以下方式实现数据范围控制：

1. **权限加载**：用户登录时加载其角色对应的所有功能点及数据范围配置
2. **动态过滤**：业务查询时，根据当前用户权限动态注入数据过滤条件
3. **灵活配置**：新增角色无需代码修改，直接在后台配置数据范围即可

```
┌─────────────────────────────────────────────────────────────────────┐
│                    数据范围过滤原理                                   │
├─────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  业务查询示例（伪代码）：                                              │
│                                                                         │
│  function queryOrders(currentUser, permission):                      │
│      // 1. 获取用户拥有的角色及对应的数据范围                          │
│      dataScope = getDataScope(currentUser, 'order:list')            │
│                                                                         │
│      // 2. 根据数据范围动态构建查询条件                                │
│      switch (dataScope):                                              │
│          case 'self':                                                 │
│              WHERE creator_id = currentUser.id                        │
│          case 'self-and-sub':                                         │
│              WHERE creator_id IN (                                    │
│                  SELECT id FROM account                               │
│                  WHERE parent_id = currentUser.id                     │
│                  OR id = currentUser.id                                │
│              )                                                        │
│          case 'dept':                                                 │
│              WHERE dept_id = currentUser.deptId                       │
│          case 'org':                                                  │
│              WHERE org_id = currentUser.orgId                         │
│          case 'all':                                                  │
│              // 不过滤，全量查询                                      │
│                                                                         │
│      // 3. 返回符合权限的数据                                         │
│      return db.select(conditions)                                     │
│                                                                         │
└─────────────────────────────────────────────────────────────────────┘
```

### 8.5 数据隔离原则

- **组织隔离**：不同企业/组织的数据默认隔离
- **角色隔离**：不同角色之间默认数据隔离
- **层级隔离**：子账户只能查看自己创建的数据
- **父级可见**：父账户可以查看下属子账户的数据（用于管理/对账）
