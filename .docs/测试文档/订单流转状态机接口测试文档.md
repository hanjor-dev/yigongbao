# 医工宝订单流转状态机 — 接口测试文档

> 本文档用于调试阶段验证状态机核心逻辑。通过 `FlowDebugController`（`/api/order/debug/*`）接口驱动订单状态流转，覆盖正常流程、分支流程、驳回/撤回循环、异常边界等全部场景。
>
> **重要**：每个场景测试结束后，必须通过重置接口将订单恢复初始状态（`phase=10, status=1001`），再开始下一个场景，避免状态污染。

---

## 一、核心概念速查

### 1.1 阶段与状态对应关系

| phase（阶段值） | 阶段名称 | status（状态值） | 状态名称 | 说明 |
|---|---|---|---|---|

| 10 | 订单阶段 | 1002 | 数据待审核 | 提交后进入 |
| 10 | 订单阶段 | 1003 | 数据审核通过 | **不可见**，自动推进到 DESIGN(2001) |
| 10 | 订单阶段 | 1004 | 数据审核不通过 | 驳回状态，可重新提交 |
| 20 | 设计阶段 | 2001 | 待设计 | 数据审核通过后进入 |
| 20 | 设计阶段 | 2002 | 设计中 | 设计师已开始设计 |
| 20 | 设计阶段 | 2003 | 设计完成 | 可选中间状态 |
| 20 | 设计阶段 | 2004 | 设计审核中 | 提交设计审核 |
| 20 | 设计阶段 | 2005 | 设计审核通过 | **不可见**，自动推进到 PRINT(3001) 或 CONFIRM(7001) |
| 20 | 设计阶段 | 2006 | 设计审核不通过 | 驳回状态，可重新开始设计 |
| 30 | 打印阶段 | 3001 | 待打印 | 仅 needsPhysicalDelivery=1 时进入 |

| 40 | 后处理阶段 | 4001 | 后处理中 | 仅 needsPhysicalDelivery=1 时进入 |

### 1.2 动作编码速查

| 动作编码 | 中文名称 | 触发前状态 | 触发后状态 | 阶段推进 | 说明 |
|---|---|---|---|---|---|
| SUBMIT_ORDER | 提交订单 | 1001（草稿） | 1002 | — | 进入待审核 |
| DATA_AUDIT_PASS | 数据审核通过 | 1002 | 1003 | → DESIGN(2001) | 审核通过，自动推进 |
| DATA_AUDIT_REJECT | 数据审核驳回 | 1002 | 1004 | — | 需填写驳回原因 |
| WITHDRAW | 撤回订单 | 1003 | 1002 | — | 退回待审核状态 |
| RESUBMIT | 重新提交 | 1004 | 1002 | — | 重新审核 |
| START_DESIGN | 开始设计 | 2006 | 2001 | — | 重新开始设计 |
| SUBMIT_DESIGN | 提交设计 | 2001/2002 | 2004 | — | 进入设计审核 |
| DESIGN_REVIEW_PASS | 设计审核通过 | 2004 | 2005 | → PRINT(3001) 或 CONFIRM(7001) | 审核通过，自动推进 |
| DESIGN_REVIEW_REJECT | 设计审核驳回 | 2004 | 2006 | — | 可重新开始设计 |
| START_PRINT | 开始打印 | 3001 | 3002 | — | 仅 needsPhysicalDelivery=1 |
| COMPLETE_PRINT | 完成打印 | 3002 | 3003 | → POST_PROCESSING(4001) | 仅 needsPhysicalDelivery=1 |
| COMPLETE_POST_PROCESSING | 完成后处理 | 4001 | 5001 | — | 仅 needsPhysicalDelivery=1 |
| QC_PASS | 质检合格 | 5001 | 5002 | → WAREHOUSE(6001) | 仅 needsPhysicalDelivery=1 |
| QC_FAIL | 质检不合格 | 5001 | 5003 | — | 仅 needsPhysicalDelivery=1 |
| REWORK | 返工 | 5004 | 3001 | — | 退回打印阶段，仅 needsPhysicalDelivery=1 |
| COMPLETE_WAREHOUSE_IN | 完成入库 | 6001 | 6002 | → COMPLETED(8001) | 仅 needsPhysicalDelivery=1 |
| USER_CONFIRM | 客户确认 | 7001 | 8001 | — | 仅 needsPhysicalDelivery=0 |

### 1.3 流程分支

**needsPhysicalDelivery = 1（需要实体交付）**：

```
ORDER(10) → DESIGN(20) → PRINT(30) → POST_PROCESSING(40) → QC(50) → WAREHOUSE(60) → COMPLETED(80)
```

**needsPhysicalDelivery = 0（不需要实体交付）**：

```
ORDER(10) → DESIGN(20) → CONFIRM(70) → COMPLETED(80)
```

### 1.4 循环次数上限

| 循环类型 | 上限 | 超限错误码 | 说明 |
|---|---|---|---|
| 审核驳回（DATA_AUDIT_REJECT） | 10次 | ORDER_EXCESSIVE_AUDIT_REJECT | 需管理员处理 |
| 设计审核驳回（DESIGN_REVIEW_REJECT） | 5次 | ORDER_EXCESSIVE_DESIGN_REJECT | 需管理员处理 |
| 返工（REWORK） | 5次 | ORDER_EXCESSIVE_REWORK | 需管理员处理 |

## 二、前置条件：创建测试订单

> 每个场景可共用同一个订单 ID，测试完成后通过重置接口恢复初始状态即可。

### 2.1 创建正式订单（直提）

**接口**：`POST /api/order`

**请求头**：`Content-Type: application/json`（需已登录，获取 `satoken`）

> **说明**：直接创建正式订单，跳过草稿保存步骤。创建成功后订单直接进入数据待审核状态（phase=10, status=1002）。
>
> `operatorName`、`operatorPhone` 由系统从当前会话用户自动填充；`hospitalName`、`deptName` 等字段由系统根据 ID 自动填充，无需传入。
>
> `imageDataFileIds` 和 `imageReportFileIds` 是否必填由系统配置项独立控制：
> - `order.image.data.required`（默认 `true`）：影像数据文件（DICOM/CT/MRI）是否必填
> - `order.image.report.required`（默认 `true`）：影像报告文件（PDF）是否必填
>
> 测试时请确保已上传对应文件，或临时将对应配置项改为 `false` 跳过校验。

**请求体**：

```json
{
  "orderType": 1,
  "needsPhysicalDelivery": 1,
  "businessType": "11.1",
  "orgId": 1,
  "hospitalId": 1,
  "deptId": 1,
  "doctorId": 1,
  "patientName": "王患者",
  "patientAge": 45,
  "patientGender": "12.1",
  "isUrgent": 0,
  "isPostal": 0,
  "expectedDeliveryDate": "2026-04-10T10:00:00",
  "imageDataFileIds": ["file_id_影像数据"],
  "imageReportFileIds": ["file_id_影像报告"],
  "items": [
    {
      "bodyPartId": 1,
      "projectId": 1,
      "projectEstimatedHours": 8.5,
      "projectDesc": "用于术前规划",
      "formingRequirement": "高精度",
      "otherRequirement": "尽快交付",
      "sortOrder": 1
    }
  ]
}
```

**预期结果**：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": 1
}
```

> 创建成功后，订单主表数据为：
> - `id` = 1（假设）
> - `phase` = 10
> - `status` = 1002（数据待审核）
> - `needsPhysicalDelivery` = 1
>
> **注意**：`status=1002` 是因为直提流程跳过了草稿状态，直接进入待审核。如需测试草稿相关场景（status=1001），请改用草稿保存接口。

**如需创建不需要实体交付的订单**：将 `needsPhysicalDelivery` 改为 `0`，后续流程将跳过打印/后处理/质检/仓储阶段。

### 场景 10：非法动作 — 状态不匹配

> **目的**：验证在不允许多状态下执行动作时正确抛出异常
>
> **初始状态**：`phase=10, status=1001`

| 3 | phase=10, status=1002（待审核） | WITHDRAW | 抛出异常：`订单状态转换不合法` |
| 4 | phase=10, status=1002（待审核） | RESUBMIT | 抛出异常：`订单状态转换不合法` |
| 5 | phase=10, status=1004（审核不通过） | DATA_AUDIT_PASS | 抛出异常：`订单状态转换不合法` |
| 6 | phase=20, status=2001（待设计） | DESIGN_REVIEW_PASS | 抛出异常：`订单状态转换不合法`（需先 SUBMIT_DESIGN） |
| 7 | phase=30, status=3001（待打印） | COMPLETE_PRINT | 抛出异常：`订单状态转换不合法`（需先 START_PRINT） |

### 6.2 不可见状态处理规则

以下状态为"不可见状态"，状态机会自动推进阶段，不会在数据库中落库：

| 不可见状态 | 值 | 推进后进入阶段 | 推进后初始状态 |
|---|---|---|---|
| DATA_AUDIT_PASSED | 1003 | DESIGN（20） | 待设计（2001） |
| DESIGN_REVIEW_PASSED | 2005 | PRINT（30）或 CONFIRM（70） | 视 needsPhysicalDelivery 而定 |
| PRINT_COMPLETED | 3003 | POST_PROCESSING（40） | 后处理中（4001） |
| QC_PASSED | 5002 | WAREHOUSE（60） | 入库中（6001） |
| WAREHOUSED | 6002 | COMPLETED（80） | 已完成（8001） |

### 6.3 needsPhysicalDelivery 变更规则

- 仅在订单阶段（phase=10）允许修改
- 仅允许 0→1 的变更（不需要→需要实体交付）
- 不允许 1→0 的变更（需要→不需要实体交付）
