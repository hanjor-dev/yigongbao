# 医工宝设计师分配模块 — Apifox 全流程手动测试文档

> **适用工具**：Apifox（或 Postman）
> **服务地址**：`http://localhost:8080`
> **文档目的**：按测试流程逐步调用接口，验证从订单创建到设计师分配完成的完整业务链路。
> **前置条件**：MySQL 8 运行于 localhost:3307，Redis 运行于 localhost:6379，应用以 dev profile 启动。

---

## 一、测试流程总览

### 1.1 业务链路

```
创建设计师账号
      ↓
关闭影像必传限制（可选）
      ↓
创建订单 → 提交订单 → 审核通过
      ↓
      ├── 手动模式（默认）→ designerId=null → 查询可分配设计师 → 手动分配 → 设计师开始设计
      │
      └── 自动模式 → 审核通过时自动分配 → 设计师开始设计
```

### 1.2 测试场景一览

| # | 场景名称 | 核心验证点 |
|---|---------|-----------|
| S0 | 前置准备 | 创建设计师账号、调整系统配置 |
| S1 | 手动分配完整流程 | 手动模式下全链路：订单创建→审核→手动分配→开始设计 |
| S2 | 自动分配流程 | 自动模式下审核通过后自动填充 designerId |
| S3 | 无匹配设计师兜底 | 专业方向无人覆盖时订单保持待分配，业务不阻断 |
| S4 | 非法操作拦截 | 非分配设计师无权 start-design；非 PENDING_DESIGN 状态无法分配 |

### 1.3 相关状态说明

| status 值 | 状态名 | 说明 |
|-----------|--------|------|
| 11 | 数据待审核 | 订单提交后 |
| 21 | PENDING_DESIGN（待设计） | 审核通过后进入，designerId 可能为 null（待分配）或已填充（已分配） |
| 22 | DESIGN_IN_PROGRESS（设计中） | 设计师点击开始设计后 |

## 二、前置准备：登录鉴权

所有接口均需携带 SaToken 认证信息。先执行登录，获取 Token。

### 步骤 1：管理员登录

| 项目 | 内容 |
|------|------|
| 方法 | POST |
| 路径 | `/api/system/auth/login` |
| Content-Type | `application/json` |

**请求体：**
```json
{
  "username": "admin",
  "password": "123456"
}
```

**预期响应：**
```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "token": "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx",
    "user": {
      "id": 1,
      "username": "admin",
      "realName": "系统管理员"
    }
  }
}
```

**操作：** 复制 `data.token` 的值，在 Apifox 中设置为全局变量 `adminToken`，后续所有管理员请求的 Header 中添加：
```
Authorization: {{adminToken}}
```

### S0-3：关闭影像文件必传限制（可选）

> 系统默认配置 `order.image.required=true`，创建订单时必须传影像文件 ID。
> 若当前没有文件上传环境，先通过以下方式关闭：
> - 方法一（推荐）：直接在数据库执行 `UPDATE sys_config SET config_value='false' WHERE config_key='order.image.required';`
> - 方法二：调用配置更新接口（需要先查出 id）

**方法二 — 查询配置 ID：**

```
POST /api/system/config/list
Authorization: {{adminToken}}
Body: {"pageNum":1,"pageSize":10,"configKey":"order.image.required"}
```

记录返回的 `data.records[0].id`，设为 `{imageConfigId}`。

**更新配置：**

| 项目 | 内容 |
|------|------|
| 方法 | PUT |
| 路径 | `/api/system/config/{imageConfigId}` |
| Header | `Authorization: {{adminToken}}` |

```json
{
  "configValue": "false"
}
```

**预期响应：** `{ "code": 200 }`

> **测试结束后记得恢复：** 将 `configValue` 改回 `"true"`。

## 八、场景 S4：非法操作拦截验证

### S4-1：非分配设计师无法开始设计

> **背景：** S1-5 中已将 `{orderId_manual}` 分配给 `designer_test01`，但此时以 `admin`（非设计师本人）身份调用 start-design。

| 项目 | 内容 |
|------|------|
| 方法 | POST |
| 路径 | `/api/order/{orderId_manual}/start-design` |
| Header | `Authorization: {{adminToken}}` |
| Body | 无 |

> **注意：** 若 S1-6 已将该订单推进到 status=22，需先重置：
> ```
> POST /api/order/debug/reset?id={orderId_manual}&phase=2&status=21
> ```

**预期响应：**
```json
{
  "code": 727,
  "message": "非分配设计师，无权操作此订单"
}
```

> **验证要点：** 接口拒绝请求，错误码 `727` ✓

---

### S4-2：非 PENDING_DESIGN 状态无法手动分配

> **背景：** 将订单重置到 status=22（DESIGN_IN_PROGRESS），再尝试分配。

**重置订单状态（Debug）：**
```
POST /api/order/debug/reset?id={orderId_manual}&phase=2&status=22
```

**尝试手动分配：**

| 项目 | 内容 |
|------|------|
| 方法 | POST |
| 路径 | `/api/order/{orderId_manual}/assign-designer` |
| Header | `Authorization: {{adminToken}}` |

```json
{
  "designerId": {designerId}
}
```

**预期响应：**
```json
{
  "code": 677,
  "message": "订单状态不允许此操作"
}
```

> **验证要点：** 状态机拦截，错误码 `677` ✓

---

### S4-3：专业方向不匹配无法手动分配

> **背景：** 创建一个 specialty=7.2 的订单，尝试分配只有 specialty=7.1 的设计师。

**创建 7.2 订单（同 S3-2），提交并审核通过，记为 `{orderId_mismatch}`。**

**尝试分配专业不匹配的设计师：**

## 九、异常与边界场景验证

### E1：分配不存在的设计师

```
POST /api/order/{orderId_manual}/assign-designer
Body: { "designerId": 99999 }
```

**预期：** `{ "code": 723, "message": "设计师不存在" }`

---

### E2：分配角色不是设计师的用户

```
POST /api/order/{orderId_manual}/assign-designer
Body: { "designerId": 1 }   ← admin 的 ID
```

**预期：** `{ "code": 724, "message": "用户角色不是设计师或设计师管理员" }`

---

### E3：查询可分配设计师时传入非法 specialty 编码（SQL 注入防护）

```
POST /api/order/designers/available
Body: { "specialties": ["' OR '1'='1", "7.1; DROP TABLE sys_user--", "../hack"] }
```

**预期响应：**
```json
{
  "code": 200,
  "data": []
}
```

> **验证要点：** 白名单正则过滤所有非法值，返回空列表而不是报错，不产生 SQL 错误 ✓

---

### E4：查询可分配设计师时 specialties 为空

```
POST /api/order/designers/available
Body: { "specialties": [] }
```

**预期响应：** `{ "code": 200, "data": [] }`

---

### E5：自动分配异常不阻断审核（容错验证）

> 将数据库中 `rebuild_project` 的 specialty 字段临时置为 null（通过 SQL），让 `getOrderSpecialty` 返回 null，再执行审核通过。

**预期：** 审核通过接口仍返回 `code=200`，订单状态推进到 `21`，`designerId=null`。
