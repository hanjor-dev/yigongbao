```java

```

**修复内容**：
```java
// 新代码：临时文件流式处理
File tempFile = Files.createTempFile("design_pkg_", fileExt).toFile();
try {
    // 写入临时文件（流式）
    file.getInputStream().transferTo(new FileOutputStream(tempFile));
    
    // 第一次读取：解析压缩包
    ArchiveParserUtil.parse(new FileInputStream(tempFile), ...);
    
    // 第二次读取：流式上传到 OSS
    fileService.uploadStream(new FileInputStream(tempFile), ...);
} finally {
    FileUtil.del(tempFile);  // 自动清理
}
```

**效果**：
- 内存占用：从 500MB → <10MB
- 磁盘临时占用：500MB（自动清理）

## 二、发现的潜在风险

### ⚠️ 风险 1：压缩包内文件全部读入内存（中等风险）

**位置**：`DesignFileServiceImpl.uploadPackage()` L178-180

**问题描述**：
```java
// archiveFiles 包含所有解压后的文件内容（byte[]）
for (ArchiveFileInfo archiveFile : archiveFiles) {
    FileVO innerFileVO = fileService.uploadBytes(
        archiveFile.getFileContent(),  // ← byte[]，占用堆内存
        archiveFile.getFileName(),
        FileBizTypeEnum.PACKAGE_FILE.getDictCode());
}
```

**风险分析**：
- 配置允许的最大压缩包：500MB
- 假设压缩比 1:2，解压后 1GB
- 如果包含 10 个 100MB 的 STL 文件，会占用 1GB 堆内存
- **并发上传时，内存占用叠加**

**影响场景**：
- 单个大压缩包上传：峰值内存 = 解压后总大小
- 并发 2 个 500MB 压缩包：可能超过 2GB 堆限制

**建议修复方案 A：添加解压后大小限制（推荐）**

```java
// 在解析后检查总大小
List<ArchiveFileInfo> archiveFiles = ArchiveParserUtil.parse(...);

// 校验解压后总大小
long totalUncompressedSize = archiveFiles.stream()
        .mapToLong(ArchiveFileInfo::getFileSize)
        .sum();

// 从配置读取限制（默认 200MB）
String maxUncompressedMbStr = configService.getConfigValue(
    SystemConfigKeyEnum.DESIGN_PACKAGE_MAX_UNCOMPRESSED_SIZE_MB.getKey());
int maxUncompressedMb = StrUtil.isNotBlank(maxUncompressedMbStr) 
    ? Integer.parseInt(maxUncompressedMbStr) : 200;
long maxBytes = (long) maxUncompressedMb * 1024 * 1024;

if (totalUncompressedSize > maxBytes) {
    log.warn("压缩包解压后总大小超限: totalSize={}bytes, maxSize={}MB", 
        totalUncompressedSize, maxUncompressedMb);
    throw new BusinessException(ErrorCodeEnum.DESIGN_ARCHIVE_TOO_LARGE);
}
```

**建议修复方案 B：改为流式处理（架构变更）**

需要修改 `ArchiveParserUtil.parse()` 返回迭代器而非 List，逐文件处理。

**优先级**：中  
**建议时间点**：下次重构时实施

### ⚠️ 风险 2：InputStreamMultipartFile 不支持重复读取（低风险）

**位置**：`yigongbao-module-basic/src/main/java/com/yigongbao/module/basic/file/util/InputStreamMultipartFile.java`

**问题描述**：
```java
@Override
public InputStream getInputStream() throws IOException {
    return inputStream;  // 只能读一次
}
```

**风险分析**：
- 如果 x-file-storage 框架调用 `getBytes()` 而非 `getInputStream()`，会触发内存读取
- 当前代码路径只调用一次 `uploadStream()`，暂时安全

**验证方式**：
1. 查看 x-file-storage 源码（推荐）
2. 大文件测试：上传 500MB 文件，监控堆内存

**建议修复**（如果框架确认调用 getBytes()）：
- 方案 A：改为可重复读取（会失去流式优势）
- 方案 B：直接用临时文件包装为 `FileSystemResource`

**优先级**：低（需先验证框架行为）
