# 模块间循环依赖解决方案

## 一、背景

在医工宝项目开发过程中，随着机构（Org）、部门（Dept）、角色（Role）、用户（User）等功能模块的逐步完善，模块之间的依赖关系日趋复杂。在代码审查中发现，**UserService 与 DeptService、RoleService 之间存在循环依赖问题**。

循环依赖不仅会影响 Spring Bean 的注入，还会导致：
- 代码维护困难
- 单元测试难以编写
- 潜在的性能问题（N+1 查询）
- 未来权限模块扩展时问题加剧

本文档详细分析当前项目的循环依赖问题，并提供 **方案A（Mapper 层下沉）+ 方案D（AOP 切面）** 的组合解决方案，同时制定模块间调用的基本规范，为后续功能模块开发提供参考。

## 三、解决方案

### 3.1 方案 A：Mapper 层下沉（核心方案）

**核心思想**：将跨模块的数据校验逻辑从 Service 层下沉到 Mapper 层，由 Mapper 直接执行数据库查询，Service 层只负责业务流程编排。

#### 3.1.1 实施步骤

**步骤 1：在 UserMapper 中添加校验方法**

```java
/**
 * 用户 Mapper
 *
 * @author hanjor
 * @date 2026-03-18
 */
public interface UserMapper extends BaseMapper<UserEntity> {

    /**
     * 统计部门下的用户数量
     *
     * @param deptId 部门ID
     * @return 用户数量
     */
    Long countByDeptId(Long deptId);

    /**
     * 统计角色下的用户数量
     *
     * @param roleId 角色ID
     * @return 用户数量
     */
    Long countByRoleId(Long roleId);
}
```

**注意**：根据项目规范，**禁止在 resource 下创建 XML 文件**，所有 SQL 操作必须使用 MyBatis-Plus 的链式查询或自定义方法实现。

**步骤 2：修改 DeptServiceImpl，移除 UserService 依赖**

```java
// 移除依赖注入
// private final UserService userService;

// 修改 hasUsers 方法，直接调用 Mapper
private boolean hasUsers(Long deptId) {
    return userMapper.countByDeptId(deptId) > 0;
}
```

**步骤 3：修改 RoleServiceImpl，移除 UserService 依赖**

```java
// 移除依赖注入
// private final UserService userService;

// 修改 hasUsers 方法，直接调用 Mapper
private boolean hasUsers(Long roleId) {
    return userMapper.countByRoleId(roleId) > 0;
}
```

#### 3.1.2 方案 A 的优势

| 优势 | 说明 |
|------|------|
| **职责清晰** | Service 负责业务流程，Mapper 负责数据查询 |
| **解耦彻底** | 移除 Service 间的循环依赖 |
| **改动最小** | 只需修改 2-3 个文件 |
| **性能最优** | 减少中间层调用，直接执行 SQL |
| **符合规范** | 与项目"禁止 XML"规范一致 |

### 3.2 方案 D：AOP 切面（辅助方案）

**核心思想**：当校验逻辑需要在多个场景复用时（如部门删除、批量删除、级联删除等），将校验逻辑抽离到 AOP 切面中，实现横切关注点与业务逻辑的分离。

#### 3.2.1 适用场景

- 多种删除场景（单条删除、批量删除）
- 多种前置校验（数据是否存在、是否有子节点、是否有关联数据）
- 权限校验（数据权限、功能权限）

#### 3.2.2 实现示例

**步骤 1：定义校验注解**

```java
/**
 * 删除前校验注解
 * 标记在需要校验的 Service 方法上
 *
 * @author hanjor
 * @date 2026-03-18
 */
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface ValidateBeforeDelete {

    /**
     * 校验类型
     */
    ValidationType value();

    /**
     * 校验类型枚举
     */
    enum ValidationType {
        /**
         * 部门下是否有用户
         */
        DEPT_HAS_USERS,
        /**
         * 角色下是否有用户
         */
        ROLE_HAS_USERS,
        /**
         * 机构下是否有部门
         */
        ORG_HAS_DEPTS,
    }
}
```

**步骤 2：创建校验切面**

```java
/**
 * 删除前校验切面
 * 用于统一处理删除前的数据完整性校验
 *
 * @author hanjor
 * @date 2026-03-18
 */
@Aspect
@Component
@RequiredArgsConstructor
@Slf4j
public class DeleteValidationAspect {

    private final UserMapper userMapper;
    private final DeptMapper deptMapper;

    /**
     * 部门删除前校验
     */
    @Before("@annotation(ValidateBeforeDelete) && args(deptId,..)")
    public void validateDeptDelete(Long deptId, ValidateBeforeDelete annotation) {
        if (annotation.value() == ValidationType.DEPT_HAS_USERS) {
            Long count = userMapper.countByDeptId(deptId);
            if (count > 0) {
                throw new BusinessException(ErrorCodeEnum.DEPT_HAS_USERS);
            }
        }
    }

    /**
     * 角色删除前校验
     */
    @Before("@annotation(ValidateBeforeDelete) && args(roleId,..)")
    public void validateRoleDelete(Long roleId, ValidateBeforeDelete annotation) {
        if (annotation.value() == ValidationType.ROLE_HAS_USERS) {
            Long count = userMapper.countByRoleId(roleId);
            if (count > 0) {
                throw new BusinessException(ErrorCodeEnum.ROLE_HAS_USERS);
            }
        }
    }
}
```

**步骤 3：在 Service 方法上使用注解**

```java
/**
 * 删除部门
 *
 * @param id 部门ID
 */
@Override
@Transactional(rollbackFor = Exception.class)
@ValidateBeforeDelete(ValidationType.DEPT_HAS_USERS)
public void removeDept(Long id) {
    // 业务逻辑
}
```

#### 3.2.3 方案 D 的优势

| 优势 | 说明 |
|------|------|
| **复用性强** | 一个切面处理多种校验场景 |
| **横切关注点** | 校验逻辑与业务逻辑分离 |
| **便于扩展** | 新增校验类型只需添加枚举值和判断逻辑 |
| **符合规范** | 符合 Spring AOP 最佳实践 |

## 四、模块间调用规范

为避免后续开发中再次出现循环依赖问题，特制定以下规范，开发人员必须严格遵守。

### 4.1 分层架构原则

```
┌─────────────────────────────────────────────────────────────┐
│                    Controller 层                           │
│  职责：接收请求、参数校验、调用 Service、返回 Result        │
│  禁止：直接操作数据库                                        │
└─────────────────────────────┬───────────────────────────────┘
                              │
┌─────────────────────────────▼───────────────────────────────┐
│                    Service 层（业务服务）                    │
│  职责：业务流程编排、事务控制、跨模块业务协调                │
│  禁止：直接操作数据库                                        │
└─────────────────────────────┬───────────────────────────────┘
                              │
┌─────────────────────────────▼───────────────────────────────┐
│                    Mapper 层（数据访问）                      │
│  职责：数据库 CRUD、跨模块数据查询                           │
│  禁止：业务逻辑                                              │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 Service 层依赖规范

| 依赖类型 | 允许 | 禁止 |
|---------|------|------|
| 同模块 Service | ✅ 允许 | - |
| **跨模块 Service** | ✅ 允许（单向） | **❌ 禁止（循环依赖）** |
| Mapper | ✅ 允许 | - |
| Utils | ✅ 允许 | - |
| Config | ✅ 允许 | - |
| 第三方 Service | - | 需评估 |

**关键理解**：
- ✅ **允许单向依赖**：A → B，只要 B 不依赖 A
- ❌ **禁止循环依赖**：A → B → A 会导致问题
- ✅ **复杂业务逻辑复用**：当其他模块需要调用当前模块的复杂业务逻辑时，允许跨模块 Service 调用

### 4.3 调用决策指南

当需要访问其他模块的数据或逻辑时，按以下优先级选择：

**场景 1：简单的数据查询/统计**

```java
// ✅ 推荐：使用 Mapper
// 场景：查询部门下有多少用户（简单 count 查询）
@Service
public class DeptServiceImpl {
    private final UserMapper userMapper;

    private boolean hasUsers(Long deptId) {
        // 简单的统计查询，直接用 Mapper
        return userMapper.countByDeptId(deptId) > 0;
    }
}
```

**场景 2：复杂的业务逻辑需要复用**

```java
// ✅ 推荐：使用 Service
// 场景：权限校验需要获取用户的完整角色信息（含缓存、权限过滤等复杂逻辑）
@Service
public class PermissionService {
    private final UserService userService;
    private final RoleService roleService;

    public boolean hasPermission(Long userId, String permission) {
        // UserService.getUserRoles() 包含复杂的业务逻辑（缓存、过滤等）
        // 应该复用，而不是在 Mapper 重新实现
        List<RoleVO> roles = userService.getUserRoles(userId);
        // ...
        return false;
    }
}
```

**场景 3：校验逻辑需要复用（多种场景）**

```java
// ✅ 推荐：使用 AOP 切面
// 场景：删除部门、批量删除部门、级联删除等都需要校验
@Service
public class DeptServiceImpl {

    @ValidateBeforeDelete(ValidationType.DEPT_HAS_USERS)
    public void removeDept(Long id) { ... }

    @ValidateBeforeDelete(ValidationType.DEPT_HAS_USERS)
    public void removeDepts(List<Long> ids) { ... }
}
```

### 4.4 循环依赖检查清单

每次新增 Service 或修改依赖时，必须完成以下检查：

- [ ] 新增的 Service 是否依赖了其他业务 Service？
- [ ] 被依赖的 Service 是否也依赖了当前 Service？
- [ ] 是否可以通过 Mapper 层方法替代 Service 间调用？
- [ ] 校验逻辑是否需要复用？（是 → 考虑 AOP 方案）
- [ ] 是否需要引入第三方 Service？（需架构评审）

## 五、权限模块前瞻性设计

### 5.1 设计原则

未来扩展权限模块时，应遵循以下原则避免循环依赖：

```
┌─────────────────────────────────────────────────────────────┐
│                    PermissionService                         │
│  (只依赖 Mapper，不依赖其他业务 Service)                     │
└───────────────────────────┬─────────────────────────────────┘
                            │
              ┌─────────────┼─────────────┐
              │             │             │
              ▼             ▼             ▼
        ┌──────────┐ ┌──────────┐ ┌──────────┐
        │UserService│ │RoleService│ │DeptService│
        │ (现有)   │ │ (现有)   │ │ (现有)   │
        └──────────┘ └──────────┘ └──────────┘
```

**关键原则**：
- 新的权限 Service（如 `PermissionService`）**只依赖 Mapper**
- **不依赖**其他业务 Service（如 UserService、RoleService）
- 如果需要查询用户/角色信息，直接使用 Mapper 层方法

### 5.2 权限模块结构建议

```
yigongbao-module-system/
└── src/main/java/com/yigongbao/module/system/
    ├── user/          # 用户模块（现有）
    ├── role/          # 角色模块（现有）
    ├── dept/          # 部门模块（现有）
    ├── org/           # 机构模块（现有）
    └── permission/    # 权限模块（未来扩展）
        ├── entity/
        │   └── PermissionEntity.java
        ├── mapper/
        │   └── PermissionMapper.java    # 只负责数据访问
        ├── service/
        │   └── PermissionService.java    # 只依赖 Mapper
        └── aspect/
            └── PermissionCheckAspect.java # 权限校验切面
```

## 七、总结

| 方案 | 适用场景 | 推荐度 |
|------|---------|--------|
| **方案 A：Mapper 层下沉** | 简单的数据查询/统计 | ⭐⭐⭐⭐⭐ |
| **方案 D：AOP 切面** | 校验逻辑需要复用（多种场景） | ⭐⭐⭐⭐ |
| **单向依赖 Service** | 复杂的业务逻辑需要复用 | ⭐⭐⭐⭐⭐ |
| **DDD 架构** | 大型复杂项目 | ⭐⭐⭐ |

**核心原则（修正后）**：
1. ✅ **允许单向依赖**：A → B，只要 B 不依赖 A
2. ❌ **禁止循环依赖**：A → B → A 是禁止的
3. **简单查询用 Mapper**：跨模块的简单统计/查询用 Mapper
4. **复杂逻辑用 Service**：涉及业务规则、事务、缓存等复杂逻辑，允许跨模块调用 Service
5. **校验复用用 AOP**：多场景复用的校验逻辑用 AOP 切面

**权限模块调用示例**：

```java
// ✅ 正确：PermissionService 单向依赖 UserService、RoleService
// 只要 UserService 和 RoleService 不依赖 PermissionService，就可以
@Service
public class PermissionService {
    private final UserService userService;
    private final RoleService roleService;

    public boolean hasPermission(Long userId, String perm) {
        // 复用 UserService 的复杂业务逻辑
        List<RoleVO> roles = userService.getUserRoles(userId);
        // 复用 RoleService 的复杂业务逻辑
        List<String> perms = roleService.getRolePermissions(roles);
        return perms.contains(perm);
    }
}
```
