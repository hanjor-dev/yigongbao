# 影像阅览模块实现方案

## 一、模块定位

`yigongbao-module-imaging` 是一个**通用只读聚合模块**，为前端影像阅览页面提供统一的数据查询接口。它跨越订单（order）和设计（design）两个业务模块，对影像文件、3D 模型文件以及颜色透明度配置进行聚合查询，不介入任何写操作。

**设计为独立模块而非内嵌于 design 模块的原因**：后续订单阶段的影像预览、其他业务阶段的模型调阅都可能需要相同的能力，独立模块可避免重复实现，并解耦读写关注点。

---

## 二、模块依赖关系

```
yigongbao-module-imaging
    └── yigongbao-module-design（compile，传递引入 order / basic / flow 等）
        └── yigongbao-module-order（compile）
            └── yigongbao-module-basic（compile）
```

imaging 模块的 pom.xml 只显式声明对 design 模块的依赖，order 及其他基础模块通过 design 的传递依赖获得，避免冗余声明。

## 三、数据来源

| 数据 | 来源表 | 访问方式 |
|------|--------|----------|
| DCM 影像文件 | `order_file`（fileCategory = `10.1`） | `OrderFileService.listByOrderIdAndCategory()` |
| 设计数据包 | `design_package` | `DesignPackageService.list()` |
| 数据包内文件 | `design_package_file` | `DesignPackageFileService.list()` |
| 可视化模型记录 | `design_model` | `DesignModelService.list()` |
| 文件详情（URL/大小） | `file_detail` | `FileService.listByIds()` |
| 部位颜色透明度 | `part_colors` | `PartColorMapper.selectList()`（imaging 自有） |

`part_colors` 表是 imaging 模块自有的配置表（无对应 Service），直接由 `PartColorMapper` 访问，不涉及跨模块问题。

**访问原则**：所有跨模块数据通过各模块暴露的 **Service 接口**获取，禁止直接注入并调用其他模块的 Mapper。

## 四、四个接口的查询流程

### 4.1 GET /imaging/dcm-packages — DCM 影像包列表

```
OrderFileService.listByOrderIdAndCategory(orderId, "10.1")
    → 收集 fileId 列表
    → FileService.listByIds(fileIds)（批量，避免 N+1）
    → 组装 DcmPackageVO
```

### 4.2 GET /imaging/package-model-files — 数据包维度模型文件

```
DesignPackageFileService.list(packageId, sortOrder ASC)
    → 收集文件名（含扩展名）
    → batchQueryColors(fileNames)（一次 IN 查询 part_colors）
    → 内存匹配（FileUtil.mainName 去扩展名 → colorMap 查找）
    → 组装 PackageModelFileVO
```

### 4.3 GET /imaging/package-model-files/by-order — 订单维度分组模型文件

```
DesignPackageService.list(orderId, packageSeq ASC)          // 查询 1
    → 收集 packageId 列表
DesignPackageFileService.list(IN packageIds, sortOrder ASC)  // 查询 2（一次 IN）
    → 收集所有文件名
PartColorMapper.selectList(IN partDetails)                   // 查询 3（一次 IN）
    → 按 packageId 分组，内存匹配颜色
    → 组装 PackageModelGroupVO（含 files 子列表）
```

整个流程固定 3 次 DB 查询，无 N+1。

### 4.4 GET /imaging/models — 可视化模型列表

```
DesignModelService.list(orderId, id ASC)
    → 收集 fileId 列表
    → FileService.listByIds(fileIds)（批量）
    → 收集文件名，batchQueryColors(fileNames)
    → 内存匹配颜色透明度
    → 组装 ModelVO
```

## 五、颜色透明度匹配机制

`part_colors` 表以**部位名称（part_detail）**为索引，值为颜色 RGB 字符串和透明度小数。

匹配规则：
1. 将文件名（如 `右肺上叶.stl`）通过 Hutool `FileUtil.mainName()` 去掉扩展名，得到 `右肺上叶`
2. 以去扩展名后的名称在 colorMap（key = partDetail）中精确匹配
3. 匹配成功则填充 `colorCode`、`opacity`；匹配失败字段为 `null`，前端按默认样式显示

**批量查询策略**：先收集当次请求涉及的所有文件名 → 去重 → 一次 `IN` 查 part_colors → 构建内存 Map。避免了逐文件查询的 N+1 问题。

## 七、数据库

`part_colors` 表结构（迁移自历史数据，新增 `opacity` 字段）：

```sql
CREATE TABLE part_colors (
    id          INT AUTO_INCREMENT PRIMARY KEY,
    part_detail VARCHAR(255) NULL    COMMENT '部位名称（与文件名去扩展名精确匹配）',
    color_code  VARCHAR(255) NULL    COMMENT '颜色RGB值，格式：R,G,B（如 255,0,0）',
    opacity     DECIMAL(3,2) DEFAULT 1.00 COMMENT '透明度，范围 0.00~1.00'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE INDEX idx_part_colors_part_detail ON part_colors (part_detail);
```

初始化数据：533 条部位颜色配置，见 `sql/init.sql`（`INSERT INTO part_colors`）。
