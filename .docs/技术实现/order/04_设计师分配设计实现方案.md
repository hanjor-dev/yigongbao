## 一、概述

### 1.1 功能背景

订单数据审核通过后，需要将订单分配给具体的设计师进行三维重建设计。本功能解决的核心问题是：**订单如何自动或手动找到对应的设计师**。

### 1.2 核心设计决策

| 决策项 | 选择方案 | 说明 |
|-------|---------|------|
| 分配模式 | 系统配置开关（`sys_config`） | 支持手动模式 / 自动模式切换 |
| 自动分配规则 | 专业方向匹配（多选）+ 负载均衡 | 订单项目 specialty（单值）与设计师 specialty（多选，逗号拼接）匹配 |
| 设计师专业方向 | 多选支持 | 设计师可同时擅长多个专业方向，如 `"7.1,7.5"` |
| 手动分配入口 | 仅管理员可操作 | 公司管理员 / 业务管理员在订单列表中指定设计师 |
| 自动分配失败处理 | 状态正常推进，`designerId` 为空 | 管理员在列表中看到待分配订单后手动分配 |
| 新增状态 | `PENDING_DESIGN(21)` | 数据审核通过后进入的中间状态，作为分配缓冲 |

### 1.3 专业方向匹配链路

设计师分配的匹配链路通过 `specialty`（专业方向）字典编码串联：

```
订单明细（order_item）
    ↓
关联重建项目（rebuild_project.projectId）
    ↓
rebuild_project.specialty    ← 新增字段，单值（如 "7.1"）
    ↓
与设计师 specialtyList 匹配
    ↓
sys_user.specialty（逗号拼接多值，如 "7.1,7.5"）
```

**核心逻辑**：
- 重建项目：单一专业方向（`specialty` 存单值，如 `"7.1"`）
- 设计师用户：多专业方向（`specialty` 存逗号拼接值，如 `"7.1,7.5"`）
- 匹配条件：项目 `specialty` 包含在设计师 `specialty` 中（`FIND_IN_SET`）
- 设计师支持同时处理头部、四肢等多个方向的项目

### 1.4 设计阶段状态流转

```
DATA_AUDIT_PASSED(12)
     ↓ 审核通过（触发分配逻辑）
PENDING_DESIGN(21)  ← 新增（已分配设计师或待分配）
     ↓ START_DESIGN
DESIGN_IN_PROGRESS(22)  ← 原 DESIGNING 顺延
     ↓ SUBMIT_DESIGN
DESIGN_COMPLETED(23)    ← 原 22 顺延
     ↓ REVIEW_DESIGN
DESIGN_REVIEWING(24)    ← 原 23 顺延
     ↓ PASS/REJECT
DESIGN_REVIEW_PASSED(25) / DESIGN_REVIEW_REJECTED(26)
```

> **编码顺延原则**：`PENDING_DESIGN` 复用原 `DESIGNING(21)` 的编码，其余设计阶段状态码顺延 +1，避免插入中间值导致现有数据状态码需要迁移。

## 三、设计师数据结构

### 3.1 设计师认定

系统中已有完整的专业方向字段，无需新建配置表：

- **设计师角色**：`sys_user.roleCode IN ('designer', 'designer-manager')`，且 `status = 1`（正常）
- **设计师专业方向**：`sys_user.specialty` 字段存储逗号拼接的多值（如 `"7.1,7.5"`），设计师角色用户创建时至少选择一个专业方向
- **专业方向字典**（`sys_dict`，根节点 `DictCodeConstants.USER_SPECIALTY = "7"`）：

```
7  - 专业方向
 ├── 7.1 - 头部方向
 │    ├── 7.1.1 - 口腔修复
 │    ├── 7.1.2 - 口腔种植
 │    └── ...
 ├── 7.2 - 四肢方向
 │    ├── 7.2.1 - 骨科
 │    └── ...
 └── 7.3 - 脊椎方向
```

### 3.2 设计师专业方向多选支持（新增）

**存储格式**：`sys_user.specialty` 字段存储逗号拼接的字典编码，如 `"7.1,7.5"`。

**相关文件改动**：

|------|---------|

| `CreateUserDTO.specialty` | `String` → `List<String>`，前端传数组，后端拼接存储 |
| `UpdateUserDTO.specialty` | `String` → `List<String>`，同上 |
| `UserVO` | 新增 `specialtyList: List<String>`（多值列表）、`specialtyNameList: List<String>`（多值名称列表） |

| `UserServiceImpl.listVo` | 填充 `specialtyNameList` 时批量翻译多值 |
| `UserServiceImpl.getUserById` | 同上 |

**校验规则调整**（`validateSpecialty`）：

```java
/**
 * 校验设计师专业方向：当角色为 designer/designer-manager 时，至少选择一个专业方向且全部为合法字典编码
 *
 * @param role           生效角色（null时跳过校验）
 * @param specialtyList  专业方向字典编码列表
 */
private void validateSpecialty(RoleEntity role, List<String> specialtyList) {
    if (role == null || role.getRoleCode() == null
            || !SPECIALTY_REQUIRED_ROLES.contains(role.getRoleCode())) {
        return;
    }
    if (CollUtil.isEmpty(specialtyList)) {
        log.warn("角色为设计师/设计师管理员，但未指定专业方向，roleId={}", role.getId());
        throw new BusinessException(ErrorCodeEnum.USER_ROLE_SPECIALTY_REQUIRED);
    }
    String prefix = DictCodeConstants.USER_SPECIALTY + ".";
    for (String specialty : specialtyList) {
        if (StrUtil.isBlank(specialty) || !specialty.startsWith(prefix)) {
            log.warn("专业方向字典编码无效，specialty={}", specialty);
            throw new BusinessException(ErrorCodeEnum.USER_SPECIALTY_INVALID, prefix);
        }
        if (dictService.getByDictCode(specialty) == null) {
            log.warn("专业方向字典编码不存在，specialty={}", specialty);
            throw new BusinessException(ErrorCodeEnum.USER_SPECIALTY_INVALID, specialty);
        }
    }
}
```

**存储与查询转换**：

```java
// 创建时：List<String> → 逗号拼接字符串存储
entity.setSpecialty(CollUtil.join(dto.getSpecialtyList(), ","));

// 查询时：逗号拼接字符串 → List<String> 展示
vo.setSpecialtyList(StrUtil.split(vo.getSpecialty(), ","));
```

### 4.2 DesignerAssignmentService 接口

```java
/**
 * 设计师分配 Service
 * 负责订单的设计师分配逻辑，包括自动分配和手动分配
 *
 * @author hanjor
 * @date 2026-04-09
 */
public interface DesignerAssignmentService {

    /**
     * 审核通过后触发分配
     * 根据系统配置决定自动分配或保持待分配状态
     *
     * @param orderId 订单ID
     */
    void triggerAssignmentAfterAudit(Long orderId);

    /**
     * 自动分配设计师
     * 根据订单项目专业方向匹配设计师（支持多选），并通过负载均衡选择最优设计师
     *
     * @param orderId 订单ID
     * @return 分配到的设计师用户ID，无可分配设计师时返回 null
     */
    Long autoAssignDesigner(Long orderId);

    /**
     * 手动分配设计师
     * 管理员在订单列表中指定设计师，仅允许在 PENDING_DESIGN 状态操作
     *
     * @param orderId 订单ID
     * @param designerId 设计师用户ID
     */
    void manualAssignDesigner(Long orderId, Long designerId);

    /**
     * 设计师开始设计
     * 设计师确认接单后调用，将状态从 PENDING_DESIGN 推进到 DESIGN_IN_PROGRESS
     * 仅允许设计师本人操作
     *
     * @param orderId 订单ID
     */
    void startDesign(Long orderId);

    /**
     * 查询可分配设计师列表（按专业方向过滤）
     * 供管理员在分配界面选择设计师
     *
     * @param specialties 订单涉及的专业方向字典编码列表（如 ["7.1", "7.5"]）
     * @return 匹配的设计师列表（包含当前工单数、多专业方向名称等信息）
     */
    List<DesignerVO> listAvailableDesigners(List<String> specialties);
}
```

### 4.3 自动分配算法

自动分配在 `auditPass`（审核通过）后触发，算法分为四个阶段：

#### 阶段一：获取订单的专业方向

从 `order_item` 表查出订单第一条明细，关联 `rebuild_project.specialty` 得到项目专业方向（单值）：

```sql
SELECT rp.specialty
FROM order_item oi
JOIN rebuild_project rp ON rp.id = oi.project_id
WHERE oi.order_id = ? AND oi.is_deleted = 0
LIMIT 1
```

> 订单所有明细的项目 specialty 必须完全一致（业务规则要求），取任意一条的 specialty 即为订单的专业方向。

#### 阶段二：候选设计师筛选

从 `sys_user` 表查询符合以下条件的用户：

1. `role_code IN ('designer', 'designer-manager')`
2. `status = 1`（正常）
3. `specialty` 字段中包含订单的项目专业方向（使用 `FIND_IN_SET`）
4. 当前设计阶段工单数 < 系统配置的容量上限（`design.assign.max.capacity`，默认 10）

**SQL 示例**（以项目方向 `"7.1"` 为例）：

```sql
SELECT u.*
FROM sys_user u
WHERE u.role_code IN ('designer', 'designer-manager')
  AND u.status = 1
  AND FIND_IN_SET('7.1', u.specialty) > 0
  AND (
      SELECT COUNT(*)
      FROM order_main om
      WHERE om.designer_id = u.id
        AND om.status BETWEEN 20 AND 29
        AND om.is_deleted = 0
  ) < ?
```

#### 阶段三：排序选择

候选设计师按当前工单数升序排列，取排名第一的设计师：

```sql
ORDER BY current_load ASC
LIMIT 1
```

#### 阶段四：分配执行

选择排名第一的设计师后，执行以下操作：

1. 更新 `order_main.designer_id` 和 `designer_name`（从 `sys_user` 读取姓名冗余存储）
2. 返回分配结果

> **无可分配设计师时**：方法返回 null，`designerId` 不写入，`PENDING_DESIGN(21)` 状态正常推进。管理员在订单列表中通过筛选 `status=21 AND designer_id IS NULL` 看到待分配订单后，执行手动分配。

### 4.4 手动分配校验规则

管理员调用 `manualAssignDesigner` 时，执行以下校验：

| 校验项 | 错误码 | 说明 |
|-------|--------|------|
| 订单存在 | 675 ORDER_NOT_FOUND | 订单不存在 |
| 订单状态为 PENDING_DESIGN(21) | 677 ORDER_STATUS_ERROR | 仅 PENDING_DESIGN 状态允许分配 |
| 设计师存在且角色合法 | 待定（新建） | 设计师不存在或角色不是 designer/designer-manager |
| 设计师状态正常 | 待定（新建） | 设计师已被禁用 |
| 设计师 specialty 包含订单项目方向 | 待定（新建） | 设计师专业方向不包含订单项目专业方向 |

手动分配成功后，同步更新 `order_main.designer_id` 和 `designer_name`。

## 五、审核通过流程集成

### 5.1 修改点

在 `OrderMainServiceImpl.auditPass` 方法中，FlowFacade 执行成功后追加分配触发逻辑：

```java
@Override
@Transactional(rollbackFor = Exception.class)
public void auditPass(Long id, AuditOrderDTO dto) {
    // ... 现有逻辑：FlowFacade 执行、订单字段更新 ...

    // 新增：触发设计师分配
    designerAssignmentService.triggerAssignmentAfterAudit(id);
}
```

### 5.2 集成位置说明

- **不修改 FlowFacade**：分配逻辑是业务层逻辑，不是状态机逻辑，Flow 模块不应感知分配策略
- **分配触发在实体更新之后**：确保订单状态已推进到 `PENDING_DESIGN(21)` 后再执行分配
- **同一事务内**：分配逻辑与审核通过在同一事务中，保证原子性

## 六、开始设计流程

### 6.1 设计师开始设计

设计师在"我的工单"中看到分配给自己的订单后，点击"开始设计"按钮，触发 `START_DESIGN` 动作。

**动作定义**：新增 `FlowActionEnum.START_DESIGN`

**前置校验**：

- 订单 `designerId` 必须等于当前登录用户 ID（设计师本人才能开始）
- 订单状态必须为 `PENDING_DESIGN(21)`

**流转规则**：`PENDING_DESIGN(21)` + `START_DESIGN` → `DESIGN_IN_PROGRESS(22)`

### 6.2 前端入口

| 场景 | 入口位置 | 按钮 |
|------|---------|------|
| 设计师查看分配给自己的订单 | 我的工单列表 / 订单详情页 | "开始设计" 按钮（仅 `designerId` 等于当前用户时显示） |
| 管理员查看待分配订单 | 订单列表（筛选 `status=21` 且 `designerId IS NULL`） | 订单详情页 "分配设计师" 按钮 |
| 管理员查看已分配订单 | 订单列表（筛选 `status=21` 且 `designerId IS NOT NULL`） | 订单详情页 "重新分配" 按钮 |

```java
return new PhaseAndStatus(FlowPhaseEnum.DESIGN, FlowStatusEnum.PENDING_DESIGN);
```

### 7.4 FlowStatusTransitionRules 改动

1. `START_DESIGN` 动作的目标状态映射：`PENDING_DESIGN(21)` → `DESIGN_IN_PROGRESS(22)`
2. 所有引用 `DESIGNING` 的地方改为 `DESIGN_IN_PROGRESS`
3. 设计阶段相关动作描述注释更新（从 `DESIGNING(21)` 更新为新编码）

### 7.5 改动影响汇总

| 文件 | 改动类型 | 说明 |
|------|---------|------|
| `FlowStatusEnum.java` | 修改 | 状态码顺延 +1，新增 `PENDING_DESIGN(21)` |
| `FlowActionEnum.java` | 新增 | 新增 `START_DESIGN` 动作 |
| `FlowPhaseTransitionRules.java` | 修改 | 审核通过后初始状态改为 `PENDING_DESIGN` |
| `FlowStatusTransitionRules.java` | 修改 | 新增 `START_DESIGN` 映射，`DESIGNING` → `DESIGN_IN_PROGRESS` |
| `FlowPhaseTransitionRulesTest.java` | 修改 | 测试用例断言值更新 |
| `FlowStatusTransitionRulesTest.java` | 修改 | 测试用例断言值更新 |
