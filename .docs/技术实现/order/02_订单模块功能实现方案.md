## 二、草稿管理

### 2.1 草稿生命周期

```
┌─────────────────────────────────────────────┐
│  草稿状态（order_draft.status）               │
│                                             │
│  1-有效  ──提交──►  2-已提交                 │
│    │                                        │
│    └──过期──►  3-已过期（定时任务标记）       │
└─────────────────────────────────────────────┘
```

> **注意**：草稿状态与订单状态（order_main.status）是完全独立的两套状态体系，不能混用。

### 2.2 创建/更新草稿（saveDraft）

**入口**：`POST /api/order/draft`，DTO：`CreateOrderDraftDTO`

**实现逻辑**（`OrderDraftServiceImpl.saveDraft`）：

1. **新增/更新判断**：DTO 中有 `id` 字段时为更新，无 `id` 时为新增。
2. **更新时校验**：
   - 草稿必须存在（`ORDER_DRAFT_NOT_FOUND`）
   - 只能修改自己的草稿（`ORDER_DRAFT_NOT_MINE`）
   - 已提交的草稿不能修改（`ORDER_DRAFT_ALREADY_SUBMITTED`）
3. **新增时设置过期时间**：从系统配置 `order.draft.expire.days` 读取（默认30天），设置 `expiresAt = now + expire_days`。
4. **业务类型校验**：校验 `businessType` 是否为合法字典值（11.1/11.2/11.3/11.4）。
5. **主表关联数据校验与填充**（`OrderDataValidator.validateAndFillMaster`，DRAFT模式）：
   - `doctorId` 有值 → 查询医生表，覆盖 `doctorName` + `doctorPhone`
   - `doctorId` 为空 + `doctorName` 有值 → 快速创建医生记录，填充 `doctorId`
   - `doctorId` 为空 + `doctorName` 为空 → 跳过（草稿模式下医生非必填）
6. **明细列表处理**（有 items 时执行）：
   - 先逻辑删除旧明细（LambdaQueryWrapper 全删）
   - 校验并填充明细关联数据（`validateAndFillItems`，DRAFT模式）
   - 校验已填写部位/项目的有效性（`validateItemsForDraft`）
   - 逐条插入新明细，`sortOrder` 未填则自动按下标（i+1）赋值

### 2.3 提交草稿（submitDraft）

**入口**：`POST /api/order/draft/{id}/submit`

**实现逻辑**（`OrderDraftServiceImpl.submitDraft`）：

1. 验证草稿存在且属于当前用户
2. 草稿不能已提交
3. **前置校验**（ORDER模式，比DRAFT更严格）：
   - 机构、医院必填
   - 患者姓名必填
   - 明细列表至少1条
   - 如果系统配置 `order.image.required=true`，必须有影像文件
4. **事务内执行**：
   - 生成订单编号（`CodeGeneratorService`，规则编码 `ORDER_NO`）
   - 从草稿实体复制字段创建 `OrderMainEntity`
   - 复制 `order_item_draft` → `order_item`（逐条插入）
   - 更新关联文件的 `biz_id`（将文件与新订单ID绑定）
   - 标记草稿 `status=2`（已提交）
   - 调用 `FlowFacade.executeFlow(orderId, CREATE, operator)` 记录创建历史
5. 返回新创建的订单ID

### 2.4 查询草稿列表

**入口**：`GET /api/order/draft/list`（GET + QueryString，草稿查询保留GET方式）

**过滤逻辑**：
- 仅返回当前用户（`operatorId = currentUserId`）的草稿
- 排除已提交的草稿（`status != 2`）
- 可选过滤：`hospitalId`、`status`（1-有效，3-已过期）
- 补充每条草稿的 `itemCount`（明细数量）和 `expiresAt`（过期时间）

## 三、订单管理

### 3.1 直提创建订单（createOrder）

**入口**：`POST /api/order`，DTO：`CreateOrderDTO`

区别于草稿提交，直提流程允许业务员直接创建正式订单，跳过草稿步骤。流程与 `submitDraft` 类似，但起点是 `CreateOrderDTO` 而非草稿记录。

**实现要点**：
- ORDER 模式严格校验（机构、医院、患者姓名、明细必填）
- 影像文件通过 `imageDataFileIds`/`imageReportFileIds` 直接传入
- 调用 `FlowFacade.executeFlow(orderId, CREATE, operator)` 完成初始化

### 3.2 分页查询订单（listOrders）

**入口**：`POST /api/order/page`，DTO：`OrderPageDTO`

**数据权限控制**（核心逻辑）：

| 数据范围类型（dataScopeType） | 过滤条件 |
|------------------------------|---------|
| ALL | 无过滤（查所有） |
| SELF | `create_by = currentUserId` |
| ORG | `org_id = currentUserOrgId` |
| HOSPITALS | `hospital_id IN (用户关联医院列表)` |
| DEPT | `operator_dept_id = currentUserDeptId`（用户无部门时降级为 SELF） |

**安全默认值**：`DataScopeTypeEnum.getByCodeOrDefault(code)` 当数据库 `data_scope_type` 值缺失或非法时，返回 `SELF`（最小权限原则），避免配置错误导致数据泄露。

**hospitalId 参数的特殊处理**：
- `HOSPITALS` 类型：传入的 `hospitalId` 必须在用户关联医院范围内，否则直接返回空列表（不报错）
- 其他类型：直接附加 `AND hospital_id = ?` 条件

**动态排序**：通过 `OrderPageDTO.sortField` + `sortOrder` 参数控制，由 `OrderQueryHelper.applySort()` 统一处理。

| 参数 | 说明 |
|------|------|
| `sortField` | 排序字段名（可选）。允许值：`createTime`、`updateTime`、`orderCode`、`patientName`、`doctorName`、`hospitalName`、`areaName`、`businessType`、`estimatedCost`、`expectedDeliveryDate`、`status`、`isUrgent` |
| `sortOrder` | 排序方向（可选，不区分大小写）：`ASC` 升序 / `DESC` 降序 |

- 两个参数均不传时，默认 `createTime DESC`（兼容旧行为）
- `sortField` 不在白名单时，静默降级为 `createTime` 并记录 warn 日志（防 SQL 注入）
- 白名单通过 `OrderQueryHelper.SORT_FIELD_MAP`（`Map<String, SFunction<OrderMainEntity, ?>>` 静态常量）维护，Lambda 引用方式保证类型安全

**跨表过滤（避免 JOIN 导致行数膨胀）**：
- `bodyPartIds` / `projectIds`：通过子查询 `IN (SELECT DISTINCT order_id FROM order_item WHERE ...)` 实现
- 只查询 `phase=1`（订单阶段）的数据

**补充字段**：分页结果转为 `OrderListVO` 后，补充每条订单的 `rebuildProjectList`（重建项目列表摘要）。

### 3.3 查询订单详情（getOrderDetail）

**入口**：`GET /api/order/{id}`

**实现要点**：
1. 校验订单存在性
2. 校验当前用户的数据权限（与 listOrders 同一套 dataScopeType 逻辑）
3. 查询 `order_item` 列表（按 `sort_order` 升序）
4. 通过 `FlowFacade.getAvailableActions(id)` 获取当前可执行动作，赋值到 `availableActions`
5. 查询订单关联文件（`order_file` 表），按 `file_category` 分类填充 `imageDataFiles`/`imageReportFiles`

### 3.4 更新订单（updateOrder）

**入口**：`PUT /api/order/{id}`（注：Controller实际为 `PUT /{id}`，但当前接口文档中未对外暴露，仅内部使用）

**needsPhysicalDelivery 变更规则**（重要约束）：

| 场景 | 是否允许 |
|------|---------|
| 0 → 1（不需要 → 需要实体交付） | 允许（仅 phase=1 时） |
| 1 → 0（需要 → 不需要实体交付） | 不允许（ORDER_NEEDS_PHYSICAL_DELIVERY_CHANGE_FORBIDDEN） |
| phase != 1 时修改 | 不允许 |

**不可变更字段**：`id`、`orderCode`、`phase`、`status`、`createTime`、`updateTime`、`createBy`、`updateBy`、`version`

### 3.5 删除订单（removeOrder）

**入口**：`DELETE /api/order/{id}`

- 仅允许删除草稿状态的订单（status 对应初始未提交状态）
- 逻辑删除（`is_deleted=1`），不物理删除

## 四、状态流转

所有状态流转统一通过 `FlowFacade` 执行，Order 模块不实现任何自定义状态转换逻辑。

### 4.1 流转操作汇总

| 操作 | 接口 | FlowAction | 说明 |
|------|------|-----------|------|
| 提交订单 | `POST /{id}/submit` | `SUBMIT_ORDER` | 草稿→待审核 |
| 撤回订单 | `POST /{id}/withdraw` | `WITHDRAW` | 待审核→草稿 |
| 审核通过 | `POST /{id}/audit-pass` | `DATA_AUDIT_PASS` | 待审核→PENDING_DESIGN；自动触发设计师分配 |
| 审核驳回 | `POST /{id}/audit-reject` | `DATA_AUDIT_REJECT` | 需填写 remark（驳回原因） |
| 创建记录 | 内部调用 | `CREATE` | 仅记录历史，不改变实体状态 |

### 4.2 标准调用模式

```java
// 构建操作人信息
FlowOperator operator = new FlowOperator(currentUserId, currentUserName, remark);

// 执行状态流转
TransitionResult result = flowFacade.executeFlow(orderId, FlowActionEnum.SUBMIT_ORDER, operator);

// 将结果写回订单（phase + status 由流程引擎决定）
entity.setPhase(result.getPhase());
entity.setStatus(result.getStatus());
updateById(entity);
```

### 4.3 审核通过集成设计师分配

审核通过（`auditPass`）在 `updateById(entity)` 之后调用 `DesignerAssignmentService.triggerAssignmentAfterAudit(orderId)`：

- 根据系统配置 `design.assign.mode` 决定自动分配还是手动分配
- 自动模式：按订单专业方向（`order_item → rebuild_project.specialty`）+ 负载均衡匹配设计师
- 手动模式：跳过自动分配，订单保持 `PENDING_DESIGN` 状态等待管理员手动操作
- **分配失败不影响审核结果**：`triggerAssignmentAfterAudit` 内部捕获所有异常，仅记录日志

### 4.4 审核驳回特殊逻辑

- `AuditOrderDTO.remark` 在驳回时必填（错误码：`ORDER_AUDIT_REMARK_REQUIRED`）
- 驳回后订单回到"已驳回"状态，操作员可重新提交（`resubmit` 动作）
- FlowContext 记录 `auditRejectCount`，超过10次抛出 `AUDIT_REJECT_EXCESSIVE_LOOPS`（错误码704）

### 4.4 查询可执行动作

**入口**：`GET /api/order/{id}/actions`

返回当前订单状态下可执行的动作名称列表（如 `["SUBMIT_ORDER", "WITHDRAW"]`），前端据此控制按钮显示。

## 五、数据验证层（OrderDataValidator）

`OrderDataValidator` 是订单数据填充与校验的专用组件，支持两种校验模式：

| 模式 | 场景 | 特点 |
|------|------|------|
| `DRAFT` | 草稿保存 | 宽松校验，未填字段跳过，允许不完整数据 |
| `ORDER` | 草稿提交/直提创建 | 严格校验，必填字段不能为空 |

### 5.1 主表关联数据填充规则（validateAndFillMaster）

| 字段组合 | 处理策略 |
|---------|---------|
| `doctorId` 有值 | 查医生表，覆盖 doctorName + doctorPhone |
| `doctorId` 空 + `doctorName` 有值 | 快速创建医生，填充 doctorId |
| `doctorId` 空 + `doctorName` 空 | DRAFT模式跳过，ORDER模式可选 |
| `hospitalId` 有值 | 查医院表，覆盖 hospitalName + areaId + areaName + fullAreaName |
| `deptId` 有值 | 查科室表，覆盖 deptName |
| `orgId` 有值 | 查机构表，覆盖 orgName |

### 5.2 明细校验规则（validateAndFillItems）

- `projectId` 有值 → 查重建项目表，填充 `projectName`、`category`、`projectEstimatedHours`
- `bodyPartId` 有值 → 查部位表，填充 `bodyPartName`
- ORDER模式：`projectId` 和 `bodyPartId` 均必填

## 九、草稿过期清理（定时任务）

**实现类**：`OrderDraftCleanupTask`

**触发时机**：定时调度（Cron 表达式在 `application.yml` 中配置）

**清理逻辑**：
1. 查询 `order_draft` 中 `expires_at < now()` 且 `status = 1`（有效）的草稿
2. 批量更新 `status = 3`（已过期）
3. 同步逻辑删除对应的 `order_item_draft` 明细

## 十三、DEPT 部门数据权限扩展（2026-04-09）

### 13.1 背景与目标

原数据权限支持 SELF / HOSPITALS / ORG / ALL 四种类型。业务管理员角色需要查看同部门（`sys_dept`）所有业务员的订单，新增 DEPT 类型满足此诉求。

### 13.2 字段变更

**历史问题**：`order_main` / `order_draft` 原有 `dept_id` / `dept_name` 字段指向"医院科室"，与新增的"提单人部门"概念冲突，造成歧义。

**字段重命名（消歧）**：

| 原字段 | 新字段 | 说明 |
|-------|--------|------|
| `dept_id` | `hospital_dept_id` | 医院科室ID（`order_main` / `order_draft`） |
| `dept_name` | `hospital_dept_name` | 医院科室名称（`order_main` / `order_draft`） |

**新增冗余字段（仅 `order_main`）**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `operator_dept_id` | BIGINT | 提单人所属部门ID（冗余自 `sys_user.dept_id`，创建时写入，不再更新） |
| `operator_dept_name` | VARCHAR(128) | 提单人所属部门名称（冗余字段，同上） |

`order_draft` 不增加 `operator_dept_*` 字段，草稿不参与 DEPT 数据范围过滤。

### 13.3 数据写入时机

- **createOrder**：从 `sys_user.dept_id` / `dept_name` 读取当前用户部门信息写入订单
- **createFromDraft**：从草稿的 `operatorId` 对应的 `sys_user` 读取部门信息写入订单；若 `operatorId` 为 null 或用户不存在，记录 `warn` 日志，字段置为 null（不阻断流程）

### 13.4 查询过滤逻辑

在 `OrderQueryHelper.buildDataScopeCondition` 新增 DEPT 分支：

```
DEPT 分支逻辑：
1. 获取 currentUserDeptId（来自 sys_user.dept_id）
2. deptId != null → wrapper.eq(operator_dept_id, deptId)
3. deptId == null → 降级为 SELF（wrapper.eq(create_by, currentUserId)）
4. currentUserId 也为 null（会话异常）→ wrapper.apply("1=0")（返回空列表）
```

降级策略：无部门配置时不暴露全量数据，降级为 SELF（最小权限）。

### 13.5 安全要点

| 要点 | 实现 |
|------|------|
| `getByCodeOrDefault` 安全默认 | 配置缺失或非法时返回 `SELF`，不暴露他人数据 |
| `getOrderDetail` 权限校验 | 按 ID 加载订单后，通过与 `listOrders` 相同的 scope 条件做 COUNT 校验；无权访问返回 `ORDER_NOT_FOUND`（不暴露存在性） |
| DEPT 降级兜底 | 用户无部门时降级 SELF；用户未登录时返回空列表，禁止 `wrapper.eq(condition=false)` 导致全表泄露 |
