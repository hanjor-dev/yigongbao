## 一、设计背景与目标

### 1.1 需求来源

基于三个核心业务流程文档的综合分析：
- 《业务流程1_订单创建.md》- 订单模块需求分析
- 《业务流程2_工单设计.md》- 工单设计阶段需求分析
- 《业务流程3_生产管理.md》- 生产管理模块需求分析

**核心设计理念**：
> "订单是唯一的数据实体，贯穿整个业务流程。工单和生产单都是订单在不同阶段的'状态表现'，而非独立数据。"

### 1.2 设计目标

1. **单一订单实体**：所有订单类型（医疗器械、非医疗器械、服务）共用同一订单数据
2. **阶段 + 状态管理**：通过 `phase` + `status` 组合精确定位流程节点
3. **完整流程追溯**：每次状态变更都记录历史，支持审计和统计
4. **清晰的代码结构**：状态转换规则集中定义，代码结构清晰易维护
5. **适度灵活性**：新增/删除状态只需修改一处，便于后续流程调整

### 1.3 设计方案选择

经过深入分析，我们对比了三种方案：

| 方案 | 描述 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| 方案A | 保持原设计 | 实现简单 | 逻辑分散，难以维护 | 需求非常稳定 |
| **方案B** | **数据库驱动** | **灵活可配置** | **需要维护配置表** | **需求频繁变化** |
| 方案C | 改进的枚举驱动 | 类型安全、结构清晰 | 需重新部署 | 偶尔改动 |

**最终选择：方案C（改进的枚举驱动方案）**

理由：
- 流程偶尔改动，但可接受部署更新
- 保持枚举类型安全，IDE 提供代码补全
- 代码结构清晰，新增状态只需修改一处
- 未来如需更灵活，可平滑升级为方案B

## 二、设计方案优化要点

### 2.1 原方案问题分析

#### 问题一：状态转换逻辑分散

原设计中，状态转换校验分散在三个位置：

```
OrderPhaseStatusMapping.getValidStatuses()      ← 有效状态列表
OrderStateMachine.validatePhaseTransition()    ← 阶段转换规则
OrderStateMachine.validateStatusTransition()   ← 阶段内状态转换
```

**问题**：新增/删除状态需要同时修改这三处，容易遗漏。

#### 问题二：switch 语句过长

`OrderStateMachine.validateStatusTransition()` 中的 switch 语句长达 170 行，包含 6 个阶段的转换规则。

**问题**：难以阅读和维护，容易引入 bug。

#### 问题三：表结构过于全面

原设计包含 12 张表，涵盖完整业务流程的每个细节。

**问题**：第一期实施工作量过大，可以区分核心功能与扩展功能分期实施。

### 2.2 优化方案

#### 优化一：状态转换规则集中定义

采用 **Map 数据结构** 集中定义所有转换规则，替代分散的 switch 语句：

```java
/**
 * 订单阶段转换规则
 * 定义阶段之间的跳转关系
 * Key: 当前阶段 → Value: 可跳转的目标阶段集合
 */
private static final Map<OrderPhaseEnum, Set<OrderPhaseEnum>> PHASE_TRANSITIONS = Map.of(
    OrderPhaseEnum.ORDER,      Set.of(OrderPhaseEnum.ORDER, OrderPhaseEnum.DESIGN),
    OrderPhaseEnum.DESIGN,     Set.of(OrderPhaseEnum.ORDER, OrderPhaseEnum.PRODUCTION, OrderPhaseEnum.COMPLETED),
    OrderPhaseEnum.PRODUCTION, Set.of(OrderPhaseEnum.QC),
    OrderPhaseEnum.QC,         Set.of(OrderPhaseEnum.WAREHOUSE, OrderPhaseEnum.PRODUCTION), // 返工可回到生产
    OrderPhaseEnum.WAREHOUSE,   Set.of(OrderPhaseEnum.COMPLETED),
    OrderPhaseEnum.COMPLETED,   Set.of() // 已完成不可跳转
);
```

```java
/**
 * 阶段内状态转换规则
 * 定义每个阶段内的状态流转关系
 * Key: (阶段, 当前状态) → Value: 可跳转的目标状态集合
 */
private static final Map<StatusKey, Set<OrderStatusEnum>> STATUS_TRANSITIONS = Map.ofEntries(
    // ========== 订单阶段 ==========
    entry(statusKey(ORDER, DRAFT), Set.of(PENDING_AUDIT)),
    entry(statusKey(ORDER, PENDING_AUDIT), Set.of(AUDIT_PASSED, AUDIT_REJECTED)),
    entry(statusKey(ORDER, AUDIT_PASSED), Set.of(PENDING_AUDIT)), // 撤回
    entry(statusKey(ORDER, AUDIT_REJECTED), Set.of(PENDING_AUDIT, DRAFT)),
    
    // ========== 设计阶段 ==========
    entry(statusKey(DESIGN, PENDING_DESIGN), Set.of(DESIGN_IN_PROGRESS)),
    entry(statusKey(DESIGN, DESIGN_IN_PROGRESS), Set.of(DESIGN_COMPLETED, PENDING_DESIGN)),
    entry(statusKey(DESIGN, DESIGN_COMPLETED), Set.of(DESIGN_REVIEWING)),
    entry(statusKey(DESIGN, DESIGN_REVIEWING), Set.of(DESIGN_REVIEW_PASSED, DESIGN_REVIEW_REJECTED)),
    entry(statusKey(DESIGN, DESIGN_REVIEW_REJECTED), Set.of(DESIGN_IN_PROGRESS, DESIGN_COMPLETED)),
    
    // ... 其他阶段
);
```

**优势**：
- 规则集中在一处，便于查看全貌
- 新增状态只需在一处添加映射
- 可以生成可视化的状态流转图

#### 优化二：区分核心表与扩展表

| 类型 | 表 | 说明 | 实施阶段 |
|------|-----|------|----------|
| **核心表** | order | 订单主表 | 第一期 |
| | order_item | 订单明细表 | 第一期 |
| | order_file | 订单文件表 | 第一期 |
| | order_status_history | 状态历史表 | 第一期 |
| **扩展表** | order_design_info | 设计信息表 | 第二期 |
| | order_instruction | 指令单表 | 第二期 |
| | order_drawing | 图纸表 | 第二期 |
| | order_production_record | 生产作业记录表 | 第二期 |
| | order_qc_record | 质检记录表 | 第二期 |
| | order_audit_record | 审核记录表 | 第二期 |
| | order_modify_record | 修改申请记录表 | 第二期 |
| | order_sign_record | 电子签名记录表 | 第二期 |

**优势**：
- 第一期聚焦核心功能，降低实施风险
- 扩展功能可以独立迭代
- 便于评估开发优先级

## 三、订单类型与流程差异

### 3.1 订单类型定义

医工宝订单采用**两级分类体系**：

```java
/**
 * 订单类型枚举（一级分类：决定主体流程）
 * 订单类型在订单创建入口处选择
 */
public enum OrderTypeEnum {
    MEDICAL_DEVICE(1, "医疗器械"),
    NON_MEDICAL(2, "非医疗器械");
}

/**
 * 【新增】是否需要实体交付（二级属性：决定是否经过生产环节）
 * 进入订单填写页后选择，订单级属性
 * - 1：需要实体交付，走完整流程（打印→后处理→质检→入库）
 * - 0：不需要实体交付，仅设计服务，跳过生产环节
 */
public enum NeedsPhysicalDeliveryEnum {
    YES(1, "需要实体交付"),
    NO(0, "不需要实体交付");
}
```

### 3.2 四种业务组合的流程差异

| 流程阶段 | 医疗器械（需实体） | 非医疗器械（需实体） | 医疗器械（不需实体） | 非医疗器械（不需实体） |
|----------|:------------------:|:------------------:|:-------------------:|:-------------------:|
| 订单阶段 | ✓ | ✓ | ✓ | ✓ |
| 设计阶段 | ✓ | ✓ | ✓ | ✓ |
| 打印阶段 | ✓ | ✓ | ✗ | ✗ |
| 后处理阶段 | ✓ | ✓ | ✗ | ✗ |
| 质检阶段 | ✓ | ✓ | ✗ | ✗ |
| 仓储阶段 | ✓ | ✓ | ✗ | ✗ |
| 确认阶段 | ✗ | ✗ | ✓ | ✓ |
| 已完成 | ✓ | ✓ | ✓ | ✓ |

> **说明**：orderType=1/2 × needsPhysicalDelivery=0/1 = 4种有效业务组合。流程差异仅由 `needsPhysicalDelivery` 属性决定：`needsPhysicalDelivery=1` 走完整流程，`needsPhysicalDelivery=0` 跳过打印/后处理/质检/仓储。

## 五、状态转换规则设计（方案C核心）

### 5.1 设计思路

采用 **规则即数据** 的设计思想，将状态转换规则定义为静态 Map 数据结构，而非散落在多处的方法调用。

**核心组件**：

1. **OrderPhaseTransitionRules** - 阶段转换规则
2. **OrderStatusTransitionRules** - 阶段内状态转换规则
3. **OrderStateMachine** - 状态机核心（调用规则校验）

### 5.2 阶段转换规则

> **说明**：规则已迁移至 `yigongbao-module-flow` 模块的 `flow.rules` 包下。

```java
package com.yigongbao.flow.rules;

/**
 * 订单阶段流转规则
 * 定义阶段之间的跳转关系
 *
 * 设计原则：
 * - 阶段通常只能向前推进（ORDER → DESIGN → ... → COMPLETED）
 * - 驳回操作可以回到上一阶段（DESIGN → ORDER）
 * - 返工操作可以回到打印阶段（QC → PRINT）
 * - 不需要实体交付的订单不经过打印/后处理/质检/仓储阶段
 *
 * 需要实体交付流程（needsPhysicalDelivery=1）：
 *   ORDER → DESIGN → PRINT → POST_PROCESSING → QC → WAREHOUSE → COMPLETED
 *
 * 不需要实体交付流程（needsPhysicalDelivery=0）：
 *   ORDER → DESIGN → CONFIRM → COMPLETED
 *
 * @author hanjor
 * @date 2026-03-31
 */
@Slf4j
@Component
public class FlowPhaseTransitionRules implements PhaseTransitionRule {

    /**
     * 阶段转换规则
     * key: 当前阶段 → value: 可跳转的目标阶段集合
     */
    private static final Map<FlowPhaseEnum, Set<FlowPhaseEnum>> PHASE_TRANSITIONS = Map.of(
        // 订单阶段：进入设计阶段
        ORDER, Set.of(DESIGN),

        // 设计阶段：进入打印阶段（需实体交付）或确认阶段（不需要实体交付）
        DESIGN, Set.of(PRINT, CONFIRM),

        // 打印阶段：进入后处理阶段
        PRINT, Set.of(POST_PROCESSING),

        // 后处理阶段：进入质检阶段
        POST_PROCESSING, Set.of(QC),

        // 质检阶段：进入仓储阶段，或返工回到打印阶段
        QC, Set.of(WAREHOUSE, PRINT),

        // 仓储阶段：进入已完成
        WAREHOUSE, Set.of(COMPLETED),

        // 确认阶段（不需要实体交付）：进入已完成
        CONFIRM, Set.of(COMPLETED),

        // 已完成：不可跳转
        COMPLETED, Set.of()
    );
    
    /**
     * 判断阶段转换是否合法
     *
     * @param fromPhase 当前阶段
     * @param toPhase   目标阶段
     * @param needsPhysicalDelivery 是否需要实体交付（用于判断不需要实体交付的订单是否可进入打印/质检/仓储）
     * @return 是否合法
     */
    public static boolean isValidPhaseTransition(
            FlowPhaseEnum fromPhase,
            FlowPhaseEnum toPhase,
            Integer needsPhysicalDelivery) {
        
        // 已完成状态不可跳转
        if (fromPhase == COMPLETED) {
            return false;
        }
        
        // 不需要实体交付的订单不能进入打印/后处理/质检/仓储阶段
        if (needsPhysicalDelivery != null && needsPhysicalDelivery == 0) {
            if (toPhase == PRINT || toPhase == POST_PROCESSING
                || toPhase == QC || toPhase == WAREHOUSE) {
                return false;
            }
        }
        
        // 校验阶段转换是否在允许范围内
        Set<OrderPhaseEnum> allowedPhases = PHASE_TRANSITIONS.getOrDefault(fromPhase, Set.of());
        return allowedPhases.contains(toPhase);
    }
    
    /**
     * 获取指定阶段的下一个默认阶段
     * 用于阶段推进时的自动跳转
     *
     * @param currentPhase 当前阶段
     * @param needsPhysicalDelivery 是否需要实体交付
     * @return 下一个阶段，如果没有则返回null
     */
    public static FlowPhaseEnum getNextPhase(FlowPhaseEnum currentPhase, Integer needsPhysicalDelivery) {
        return switch (currentPhase) {
            case ORDER -> DESIGN;
            case DESIGN -> (needsPhysicalDelivery != null && needsPhysicalDelivery == 0) ? CONFIRM : PRINT;
            case PRINT -> POST_PROCESSING;
            case POST_PROCESSING -> QC;
            case QC -> WAREHOUSE;
            case WAREHOUSE -> COMPLETED;
            case CONFIRM -> COMPLETED;
            case COMPLETED -> null;
        };
    }
}
```

### 5.3 阶段内状态转换规则

> **说明**：规则已迁移至 `yigongbao-module-flow` 模块的 `flow.rules` 包下。

```java
package com.yigongbao.flow.rules;

/**
 * 订单阶段内状态转换规则
 * 定义每个阶段内的状态流转关系
 *
 * 【核心改进】：所有转换规则集中定义，清晰易维护
 * 新增/删除状态只需修改此文件
 *
 * 【设计审核通过的不可见状态】：
 * - DESIGN_REVIEW_PASSED(2005) 为不可见状态
 * - 审核通过后系统自动将订单推进到下一阶段
 * - order_flow_status_history 表中仍记录完整的审核通过动作，便于追溯
 * - 前端不显示"设计审核通过"这个状态
 *
 * @author hanjor
 * @date 2026-03-31
 */
@Slf4j
@Component
public class FlowStatusTransitionRules {

    /**
     * 状态转换规则
     * Key: (阶段, 当前状态) → Value: 可跳转的目标状态集合
     */
    private static final Map<StatusKey, Set<FlowStatusEnum>> STATUS_TRANSITIONS;

    static {
        Map<StatusKey, Set<FlowStatusEnum>> transitions = new HashMap<>();

        // ==================== 订单阶段状态转换（1001-1099）====================
        // 草稿 → 提交后进入数据待审核
        transitions.put(statusKey(ORDER, DRAFT), Set.of(PENDING_DATA_AUDIT));

        // 数据待审核 → 数据审核通过或被拒
        transitions.put(statusKey(ORDER, PENDING_DATA_AUDIT),
            Set.of(DATA_AUDIT_PASSED, DATA_AUDIT_REJECTED));

        // 数据审核通过 → 可撤回重审
        transitions.put(statusKey(ORDER, DATA_AUDIT_PASSED), Set.of(PENDING_DATA_AUDIT));

        // 数据审核不通过 → 可重新提交
        transitions.put(statusKey(ORDER, DATA_AUDIT_REJECTED), Set.of(PENDING_DATA_AUDIT));

        // ==================== 设计阶段状态转换（2001-2099）====================
        // 待设计 → 开始设计
        transitions.put(statusKey(DESIGN, PENDING_DESIGN), Set.of(DESIGN_IN_PROGRESS));

        // 设计中 → 完成设计
        transitions.put(statusKey(DESIGN, DESIGN_IN_PROGRESS), Set.of(DESIGN_COMPLETED));

        // 设计完成 → 提交设计审核
        transitions.put(statusKey(DESIGN, DESIGN_COMPLETED), Set.of(DESIGN_REVIEWING));

        // 设计审核中 → 审核通过或被拒
        transitions.put(statusKey(DESIGN, DESIGN_REVIEWING),
            Set.of(DESIGN_REVIEW_PASSED, DESIGN_REVIEW_REJECTED));

        // 设计审核不通过 → 重新设计
        transitions.put(statusKey(DESIGN, DESIGN_REVIEW_REJECTED), Set.of(DESIGN_IN_PROGRESS));

        // ==================== 打印阶段状态转换（3001-3099）====================
        // 待打印 → 开始打印
        transitions.put(statusKey(PRINT, PENDING_PRINT), Set.of(PRINTING));

        // 打印中 → 完成打印
        transitions.put(statusKey(PRINT, PRINTING), Set.of(PRINT_COMPLETED));

        // ==================== 后处理阶段状态转换（4001-4099）====================
        transitions.put(statusKey(POST_PROCESSING, POST_PROCESSING), Set.of(QC_IN_PROGRESS));

        // ==================== 质检阶段状态转换（5001-5099）====================
        // 质检中 → 合格或不合格
        transitions.put(statusKey(QC, QC_IN_PROGRESS), Set.of(QC_PASSED, QC_FAILED));

        // 质检合格 → 进入入库
        transitions.put(statusKey(QC, QC_PASSED), Set.of(WAREHOUSE_IN));

        // 质检不合格 → 返工
        transitions.put(statusKey(QC, QC_FAILED), Set.of(REWORK));

        // 返工 → 回到待打印
        transitions.put(statusKey(QC, REWORK), Set.of(PENDING_PRINT));

        // ==================== 仓储阶段状态转换（6001-6099）====================
        // 入库中 → 完成入库
        transitions.put(statusKey(WAREHOUSE, WAREHOUSE_IN), Set.of(WAREHOUSED));

        // 已入库 → 订单完成
        transitions.put(statusKey(WAREHOUSE, WAREHOUSED), Set.of(COMPLETED));

        // 确认阶段状态转换（7001-7099，服务订单专用）
        // 待客户确认 → 完成（用户确认）
        transitions.put(statusKey(CONFIRM, AWAITING_CONFIRM), Set.of(COMPLETED));

        STATUS_TRANSITIONS = Map.copyOf(transitions);
    }

    public static boolean isValidStatusTransition(
            FlowPhaseEnum phase,
            FlowStatusEnum currentStatus,
            FlowStatusEnum targetStatus,
            Integer needsPhysicalDelivery) {

        // 获取当前状态允许的下一状态集合
        Set<OrderStatusEnum> allowedStatuses = STATUS_TRANSITIONS.get(
            statusKey(phase, currentStatus));

        if (allowedStatuses == null || allowedStatuses.isEmpty()) {
            return false;
        }

        // 特殊处理：设计审核通过后的跳转根据订单类型不同（不可见状态）
        if (currentStatus == DESIGN_REVIEW_PASSED) {
            if (needsPhysicalDelivery == 0) {
                return targetStatus == AWAITING_CONFIRM;
            } else {
                return targetStatus == PENDING_PRINT;
            }
        }

        return allowedStatuses.contains(targetStatus);
    }

    public static Set<FlowStatusEnum> getAllowedNextStatuses(
            FlowPhaseEnum phase,
            FlowStatusEnum currentStatus,
            Integer needsPhysicalDelivery) {

        Set<FlowStatusEnum> allowed = new HashSet<>();

        // 获取基础允许状态
        Set<FlowStatusEnum> baseAllowed = STATUS_TRANSITIONS.get(
            statusKey(phase, currentStatus));
        if (baseAllowed != null) {
            allowed.addAll(baseAllowed);
        }

        // 特殊处理：设计审核通过（不可见状态）
        if (currentStatus == DESIGN_REVIEW_PASSED) {
            allowed.remove(DESIGN_REVIEW_PASSED); // 移除自身
            if (needsPhysicalDelivery == 0) {
                allowed.add(AWAITING_CONFIRM);
            } else {
                allowed.add(PENDING_PRINT);
            }
        }

        return Collections.unmodifiableSet(allowed);
    }

    public static Set<FlowStatusEnum> getValidStatusesForPhase(
            FlowPhaseEnum phase, Integer needsPhysicalDelivery) {

        return switch (phase) {
            // 订单阶段：所有订单类型都相同
            case ORDER -> Set.of(DRAFT, PENDING_DATA_AUDIT, DATA_AUDIT_PASSED, DATA_AUDIT_REJECTED);

            // 设计阶段：所有订单类型都相同
            case DESIGN -> Set.of(PENDING_DESIGN, DESIGN_IN_PROGRESS, DESIGN_COMPLETED, DESIGN_REVIEWING,
                DESIGN_REVIEW_REJECTED, AWAITING_CONFIRM);

            // 打印阶段：仅医疗器械和非医疗器械
            case PRINT -> needsPhysicalDelivery == 0
                ? Set.of()
                : Set.of(PENDING_PRINT, PRINTING, PRINT_COMPLETED);

            // 后处理阶段：仅医疗器械和非医疗器械
            case POST_PROCESSING -> needsPhysicalDelivery == 0
                ? Set.of()
                : Set.of(POST_PROCESSING);

            // 质检阶段：仅医疗器械和非医疗器械
            case QC -> needsPhysicalDelivery == 0
                ? Set.of()
                : Set.of(QC_IN_PROGRESS, QC_PASSED, QC_FAILED, REWORK);

            // 仓储阶段：仅医疗器械和非医疗器械
            case WAREHOUSE -> needsPhysicalDelivery == 0
                ? Set.of()
                : Set.of(WAREHOUSE_IN, WAREHOUSED);

            // 确认阶段：仅服务订单
            case CONFIRM -> needsPhysicalDelivery == 0
                ? Set.of(AWAITING_CONFIRM)
                : Set.of();

            // 已完成阶段：所有订单类型都相同
            case COMPLETED -> Set.of(COMPLETED);
        };
    }

    private static StatusKey statusKey(FlowPhaseEnum phase, FlowStatusEnum status) {
        return new StatusKey(phase, status);
    }

    private record StatusKey(FlowPhaseEnum phase, FlowStatusEnum status) {}
}
```

#### 5.4.3 FlowStateMachineServiceImpl（状态机实现）

```java
package com.yigongbao.flow.service.impl;

import com.yigongbao.common.exception.BusinessException;
import com.yigongbao.common.enums.ErrorCodeEnum;
import com.yigongbao.flow.context.FlowContext;
import com.yigongbao.flow.enums.FlowActionEnum;
import com.yigongbao.flow.enums.FlowPhaseEnum;
import com.yigongbao.flow.enums.FlowStatusEnum;
import com.yigongbao.flow.operator.FlowOperator;
import com.yigongbao.flow.result.TransitionResult;
import com.yigongbao.flow.rules.FlowPhaseTransitionRules;
import com.yigongbao.flow.rules.FlowStatusTransitionRules;
import com.yigongbao.flow.service.FlowOrderService;
import com.yigongbao.flow.service.FlowStateMachineService;
import com.yigongbao.flow.service.FlowStatusHistoryService;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.stereotype.Service;
import java.util.List;
import java.util.stream.Collectors;

/**
 * 流程状态机 Service 实现
 * 处理订单状态流转的核心业务逻辑，供订单及后续设计/生产模块复用
 *
 * 【v4.1 变更】
 * - 方法签名由 5 参数简化为 (orderId, action, FlowOperator)
 * - executeTransition 增加 phase 为 null 的防御校验（非法数据拒绝流转）
 *
 * 【职责边界】
 * - 此实现不直接更新数据库，仅返回 TransitionResult
 * - 调用方（order 模块的 OrderMainServiceImpl）负责根据 TransitionResult 更新订单
 *
 * @author hanjor
 * @date 2026-04-01
 */
@Service
@RequiredArgsConstructor
@Slf4j
public class FlowStateMachineServiceImpl implements FlowStateMachineService {

    private final FlowOrderService flowOrderService;
    private final FlowStatusTransitionRules statusTransitionRules;
    private final FlowStatusHistoryService flowStatusHistoryService;

    @Override
    public List<String> getAvailableActions(Long orderId) {
        // 1. 通过 FlowOrderService 查询订单
        OrderMainEntity order = flowOrderService.getById(orderId);
        if (order == null) {
            throw new BusinessException(ErrorCodeEnum.ORDER_NOT_FOUND);
        }
        // 2. 从历史中构建 FlowContext（统计循环次数）
        FlowContext ctx = buildContextFromHistory(orderId);
        // 3. 通过 FlowStatusTransitionRules 获取当前状态允许的动作
        List<FlowActionEnum> availableActions = statusTransitionRules.getAvailableActions(
                order.getStatus(), order.getPhase(), order.getNeedsPhysicalDelivery());
        return availableActions.stream()
                .map(FlowActionEnum::getCode)
                .collect(Collectors.toList());
    }

    @Override
    public TransitionResult executeTransition(Long orderId, FlowActionEnum action, FlowOperator operator) {
        // Step 1: 校验订单存在
        OrderMainEntity order = flowOrderService.getById(orderId);
        if (order == null) {
            throw new BusinessException(ErrorCodeEnum.ORDER_NOT_FOUND);
        }

        Integer fromStatus = order.getStatus();
        FlowPhaseEnum currentPhase = FlowPhaseEnum.getByValue(order.getPhase());

        // 【v4.1 新增】防御：phase 为 null 时视为非法数据，拒绝流转
        if (currentPhase == null) {
            log.error("订单阶段数据异常，orderId={}, phase={}", order.getId(), order.getPhase());
            throw new BusinessException(ErrorCodeEnum.ORDER_STATUS_TRANSITION_ERROR);
        }

        try {
            // Step 2: CREATE 动作：仅记录历史，不改变状态
            if (action == FlowActionEnum.CREATE) {
                flowStatusHistoryService.recordTransition(
                        order.getId(), order.getOrderCode(), order.getPhase(),
                        fromStatus, fromStatus,
                        action.getCode(), action.getName(),
                        operator);
                return TransitionResult.of(currentPhase.getValue(), fromStatus);
            }

            // Step 3: 校验循环次数（防止无限驳回/返工/设计审核驳回）
            FlowContext ctx = buildContextFromHistory(orderId);
            applyContextAction(ctx, action);
            ctx.validateNoExcessiveLoops();

            // Step 4: 校验动作是否可执行
            if (!statusTransitionRules.canExecuteAction(fromStatus, order.getPhase(),
                    order.getNeedsPhysicalDelivery(), action)) {
                throw new BusinessException(ErrorCodeEnum.ORDER_STATUS_TRANSITION_ERROR);
            }

            // Step 5: 获取目标状态
            Integer targetStatusValue = statusTransitionRules.getTargetStatus(fromStatus, action);
            if (targetStatusValue == null) {
                throw new BusinessException(ErrorCodeEnum.ORDER_STATUS_TRANSITION_ERROR);
            }
            FlowStatusEnum targetStatus = FlowStatusEnum.getByValue(targetStatusValue);

            // Step 6: 决策阶段推进
            PhaseAndStatus phaseAndStatus = FlowPhaseTransitionRules.decideNextPhaseAndStatus(
                    currentPhase, targetStatus, action, order.getNeedsPhysicalDelivery());
            Integer nextPhase = phaseAndStatus != null && phaseAndStatus.phase() != null
                    ? phaseAndStatus.phase().getValue() : null;
            Integer initialStatus = phaseAndStatus != null ? phaseAndStatus.initialStatus().getValue() : null;

            // Step 7: 不可见状态处理（不落库中间状态）
            if (FlowPhaseTransitionRules.isInvisibleStatus(targetStatus)) {
                flowStatusHistoryService.recordTransition(
                        order.getId(), order.getOrderCode(), currentPhase.getValue(),
                        fromStatus, targetStatusValue,
                        action.getCode(), action.getName(),
                        operator);
                return TransitionResult.ofWithPhaseChange(nextPhase, targetStatusValue, initialStatus);
            }

            // Step 8: 正常状态 - 记录历史
            Integer recordPhase = (nextPhase != null) ? nextPhase : currentPhase.getValue();
            flowStatusHistoryService.recordTransition(
                    order.getId(), order.getOrderCode(), recordPhase,
                    fromStatus, targetStatusValue,
                    action.getCode(), action.getName(),
                    operator);

            // Step 9: 构建返回结果
            if (nextPhase != null) {
                Integer finalStatus = initialStatus != null ? initialStatus : targetStatusValue;
                return TransitionResult.ofWithPhaseChange(nextPhase, targetStatusValue, finalStatus);
            } else {
                return TransitionResult.of(currentPhase.getValue(), targetStatusValue);
            }
        } catch (Exception e) {
            log.error("执行订单状态转换异常，orderId={}, action={}", order.getId(), action.getCode(), e);
            throw e;
        }
    }

    private FlowContext buildContextFromHistory(Long orderId) {
        List<String> actionCodes = flowStatusHistoryService.listActionCodesByOrderId(orderId);
        return FlowContext.buildFromHistory(actionCodes);
    }

    private void applyContextAction(FlowContext ctx, FlowActionEnum action) {
        switch (action) {
            case DATA_AUDIT_REJECT -> ctx.incrementAuditReject();
            case REWORK -> ctx.incrementRework();
            case DESIGN_REVIEW_REJECT -> ctx.incrementDesignReject();
            default -> { }
        }
    }
}
```

```java
/**
 * 流程 Facade 实现
 *
 * 【v4.1 变更】

@Service
@RequiredArgsConstructor
@Slf4j

    @Override
    public List<String> getAvailableActions(Long orderId) {

    @Override
    public TransitionResult executeFlow(Long orderId, FlowActionEnum action, FlowOperator operator) {
        // 【v4.1 新增】防御：operator 为 null 时使用空对象
        if (operator == null) {
            operator = new FlowOperator();
```

### 7.1 状态转换服务调用

```java
/**
 * 提交订单
 *
 * @param orderId 订单ID
 */
@Override
@Transactional(rollbackFor = Exception.class)
public void submitOrder(Long orderId) {
    log.info("提交订单，orderId={}", orderId);

    OrderEntity order = orderMapper.selectById(orderId);
    if (order == null) {
        throw new BusinessException(ErrorCodeEnum.DATA_NOT_FOUND);
    }

    // 校验状态转换：ORDER.DRAFT → ORDER.PENDING_DATA_AUDIT
    orderStateMachine.validateTransition(
        order,
        OrderPhaseEnum.ORDER,
        OrderStatusEnum.PENDING_DATA_AUDIT
    );

    // 执行状态更新
    OrderPhaseEnum oldPhase = OrderPhaseEnum.getByValue(order.getPhase());
    OrderStatusEnum oldStatus = OrderStatusEnum.getByValue(order.getStatus());

    order.setPhase(OrderPhaseEnum.ORDER.getValue());
    order.setStatus(OrderStatusEnum.PENDING_DATA_AUDIT.getValue());
    orderMapper.updateById(order);

    // 记录状态历史
    orderStatusHistoryService.recordTransition(
        order,
        oldPhase, OrderPhaseEnum.ORDER,
        oldStatus, OrderStatusEnum.PENDING_DATA_AUDIT,
        OrderActionEnum.SUBMIT_ORDER,
        "提交订单"
    );

    log.info("订单提交成功，orderId={}", orderId);
}
```

## 十、设计优势总结

### 10.1 相比原方案的改进

| 维度 | 原方案 | 改进后（方案C） |
|------|--------|-----------------|
| 状态转换规则 | 分散在3处 | 集中在2个规则类 |
| 代码结构 | 170行switch语句 | Map数据结构，规则即数据 |
| 新增状态 | 修改3处 | 仅修改1处 |
| 表结构 | 12张表一次实施 | 4张核心表 + 8张扩展表分期实施 |
| 代码可读性 | 较难理解全貌 | 规则一目了然 |

### 10.2 方案C的核心优势

1. **规则集中**：所有转换规则定义在 `OrderStatusTransitionRules` 中，新增/修改状态只需改动一处
2. **类型安全**：仍然使用枚举，IDE 提供代码补全和类型检查
3. **易于测试**：规则是纯数据，可以轻松测试所有转换路径
4. **可视化友好**：规则结构清晰，可以生成状态流转图
5. **可扩展**：未来如需更灵活，可平滑升级为数据库驱动方案

### 10.3 灵活性评估

| 变更场景 | 需修改位置 | 工作量 |
|----------|------------|--------|
| 新增状态 | OrderStatusTransitionRules + OrderStatusEnum | 小 |
| 删除状态 | OrderStatusTransitionRules + OrderStatusEnum | 小 |

## 十一、状态修改操作手册

本章节详细说明在系统运行后，如何对订单状态进行新增、修改、删除等操作，以及相应的代码修改指引。

### 11.1 代码修改原则

**核心原则**：所有状态转换规则集中在 `FlowStatusTransitionRules` 类中定义，新增/修改状态只需修改一处。

```
修改优先级：
1. FlowStatusTransitionRules.java  ← 状态转换规则（必须）
2. FlowStatusEnum.java            ← 状态枚举（新增/删除状态时必须）
3. FlowActionEnum.java           ← 动作枚举（新增动作时必须）
4. FlowStateMachineService       ← 操作映射（新增状态时必须）
```

### 11.2 场景一：新增状态

#### 场景1.1：在现有阶段中新增一个状态

**场景描述**：在设计阶段中新增"设计暂停"状态，设计中可以暂停，暂停后可以继续。

**修改步骤**：

**Step 1：添加状态枚举**

```java
// 文件：OrderStatusEnum.java
// 在设计阶段状态区域添加（注意保持状态码顺序）

// ==================== 设计阶段（2001-2099）====================
PENDING_DESIGN(2001, "待设计"),
DESIGN_IN_PROGRESS(2002, "设计中"),
DESIGN_PAUSED(2007, "设计暂停"),      // 【新增】在现有值之后追加新状态码
DESIGN_COMPLETED(2003, "设计完成"),
DESIGN_REVIEWING(2004, "设计审核中"),
DESIGN_REVIEW_PASSED(2005, "设计审核通过"),
DESIGN_REVIEW_REJECTED(2006, "设计审核不通过"); // 注意：新码段内新增不需要顺延其他状态码
```

**Step 2：更新状态转换规则**

```java
// 文件：OrderStatusTransitionRules.java
// static 块中添加新的转换规则

// 设计中 → 完成设计、取消、或暂停
transitions.put(statusKey(DESIGN, DESIGN_IN_PROGRESS), Set.of(
    DESIGN_COMPLETED,
    PENDING_DESIGN,
    DESIGN_PAUSED  // 【新增】新增：设计中可以暂停
));

// 【新增】设计暂停 → 可以继续设计
transitions.put(statusKey(DESIGN, DESIGN_PAUSED), Set.of(DESIGN_IN_PROGRESS));

// 注意：如果状态码顺延，需要同步修改其他地方的引用
```

**Step 3：更新 getValidStatusesForPhase 方法**

```java
// 文件：OrderStatusTransitionRules.java
// 在 getValidStatusesForPhase 方法中添加新状态

case DESIGN -> Set.of(
    PENDING_DESIGN,
    DESIGN_IN_PROGRESS,
    DESIGN_PAUSED,  // 【新增】
    DESIGN_COMPLETED,
    DESIGN_REVIEWING,
    DESIGN_REVIEW_PASSED,
    DESIGN_REVIEW_REJECTED,
    AWAITING_CONFIRM
);
```

**Step 4：添加动作枚举（可选）**

```java
// 文件：OrderActionEnum.java
// 如果新状态需要特定动作，添加动作枚举

PAUSE_DESIGN("PAUSE_DESIGN", "暂停设计"),
RESUME_DESIGN("RESUME_DESIGN", "继续设计"),
```

**Step 5：更新状态机操作映射**

```java
// 文件：OrderStateMachine.java
// 在 getAllowedActions 方法中添加操作映射

case DESIGN_IN_PROGRESS -> {
    actions.add(OrderActionEnum.SUBMIT_DESIGN);
    actions.add(OrderActionEnum.PAUSE_DESIGN);  // 【新增】
}

case DESIGN_PAUSED -> {  // 【新增】
    actions.add(OrderActionEnum.RESUME_DESIGN);
}
```

**Step 6：更新后续状态码引用**

如果状态码顺延，需要同步修改以下位置：
- `OrderStatusTransitionRules` 中所有使用旧状态码的地方
- `OrderStateMachine` 中所有使用旧状态码的地方

#### 场景1.2：新增跨阶段的状态

### 11.3 场景二：删除状态

**修改步骤**：

```java
transitions.put(statusKey(ORDER, AUDIT_REJECTED), Set.of(PENDING_AUDIT, DRAFT));
```

**场景描述**：质检合格后，可以选择直接发货不入库，或先入库再发货。

**修改步骤**：

#### 场景3.3：调整阶段转换顺序

**场景描述**：将仓储阶段移到质检之前，变成"生产→仓储→质检→完成"。

**这种情况属于重大变更，需要修改多处：**

**Step 1：调整阶段枚举顺序**

```java

// 需要调整顺序（phase值需同步调整）

ORDER(10, "订单阶段"),
DESIGN(20, "设计阶段"),
PRODUCTION(30, "生产阶段"),
WAREHOUSE(40, "仓储阶段"),  // 【调整】原50→40
QC(50, "质检阶段"),        // 【调整】原40→50（与仓储互换）
COMPLETED(80, "已完成");
```

**Step 2：更新阶段转换规则**

```java
// 文件：OrderPhaseTransitionRules.java

PRODUCTION, Set.of(WAREHOUSE),  // 【修改】生产后进入仓储
QC, Set.of(WAREHOUSE, PRODUCTION),  // 【修改】质检后可返工回到生产
WAREHOUSE, Set.of(QC),          // 【修改】仓储后进入质检
```

**Step 3：更新所有阶段相关的状态码（可能需要）**

如果阶段 code 变化，可能需要调整质检阶段的状态码。

**Step 4：更新 getNextPhase 方法**

```java
public static OrderPhaseEnum getNextPhase(OrderPhaseEnum currentPhase, Integer needsPhysicalDelivery) {
    return switch (currentPhase) {
        case ORDER -> DESIGN;
        case DESIGN -> needsPhysicalDelivery == 0 ? COMPLETED : PRODUCTION;
        case PRODUCTION -> WAREHOUSE;  // 【修改】生产后进入仓储
        case WAREHOUSE -> QC;          // 【修改】仓储后进入质检
        case QC -> COMPLETED;
        case COMPLETED -> null;
    };
}
```

### 11.8 常见问题处理

#### 问题1：状态码不连续

**问题描述**：删除某个状态后，出现状态码间隙（如 22 被删除，后面的码不连续）。

**解决方案**：
- **保持不连续**：如果业务上不影响，可以保持不连续（推荐，简单）
- **重新编码**：如果需要连续编码，必须全部重新编号，工作量大

#### 问题2：状态码冲突

**问题描述**：新增状态时，与其他阶段的状态码冲突。

**解决方案**：
- 重新规划状态码分配，预留空间
- 例如：每个阶段预留 20 个状态码（0-19 保留给更细粒度的子状态）

#### 问题3：历史数据兼容性

**问题描述**：修改状态后，历史订单的状态如何处理。

**解决方案**：
- 数据库中的状态码保持不变（数字不变，名称可以更新）
- 新代码需要兼容旧数据
- 可以编写数据迁移脚本批量更新

#### 问题4：并发修改冲突

**问题描述**：两个管理员同时修改同一订单的状态。

**解决方案**：
- 在 `OrderStateMachine.validateTransition()` 中添加乐观锁检查
- 或在 Service 层添加分布式锁

### 11.9 最佳实践

1. **状态码预留空间**：新码段设计（阶段值×100 + 序号）天然为每个阶段预留了约 99 个状态码槽位，新增状态只需在对应码段内追加，无需顺延
2. **避免频繁修改状态码**：状态码一旦确定，尽量通过新增状态而非修改状态码
3. **保持向后兼容**：修改时考虑历史数据兼容性
4. **及时更新文档**：修改后同步更新本手册和代码注释
5. **充分测试**：修改状态后必须进行全面的回归测试
