# 医院管理与医院组合模板技术方案

## 一、背景与目标

### 1.1 业务背景

医院是医工宝系统中的核心基础数据，主要用于 ERP 订单创建时指定"客户"概念。医院与重建项目、产品、科室之间没有直接业务关联，仅作为业务对象的引用载体。

### 1.2 核心决策

| # | 决策内容 | 说明 |
|---|---------|------|
| 1 | AreaService 迁移 | 从 `system/basedata/area/` 迁移到 `basic/area/` |
| 2 | HospitalGroupTemplate 归属 | 放在 `basic/hospitalGroupTemplate/`，属于基础数据模板 |
| 3 | 医院删除功能 | 当前阶段不提供删除接口，仅支持 CRUD + 状态切换 |
| 4 | 用户-医院关联 | 使用 `sys_user_hospital` 中间表，不在 user 表增加字段 |
| 5 | 用户-医院关联 | 关联用户而非角色，同一角色下不同用户可有不同医院范围。角色的 `dataScopeType` 字段决定数据权限范围，`"hospitals"` 时启用医院范围权限 |
| 6 | 表名规范 | 医院表名为 `hospital`（无模块前缀） |

### 1.3 文档范围

本文档包含以下内容的完整技术方案：

- AreaService 从 system 模块迁移到 basic 模块
- Hospital 医院管理功能设计与实现
- HospitalGroupTemplate 医院组合模板功能设计与实现
- sys_user_hospital 用户-医院关联表设计
- 模块依赖关系与循环引用风险评估

```
模块依赖层次（从上到下依赖，禁止反向）：

boot → system → framework → common

依赖规则：
- basic    → framework（基础模块，依赖框架能力）
```

### 2.3 依赖方向说明

| 依赖方向 | 合法性 | 说明 |
|---------|--------|------|
| `basic → common` | ✅ 合法 | 基础模块依赖公共层 |
| `system → common` | ✅ 合法 | 系统模块依赖公共层 |
| `system → basic` | ✅ 合法 | 系统模块需要查询基础数据（医院下拉、area 服务） |
| `erp → basic` | ✅ 合法 | 业务模块需要基础数据（订单关联医院） |
| `erp → system` | ✅ 合法 | 业务模块需要权限信息（用户机构、数据范围） |
| `basic → system` | ❌ 非法 | 会导致循环依赖 |
| `system → erp` | ❌ 非法 | 会导致循环依赖 |

### 2.4 潜在风险与规避

**风险场景 1：删除医院时校验订单关联**

当前阶段不提供删除功能，此风险不存在。未来 erp 模块开发时，如需删除校验，可通过框架层定义接口，erp 实现并注入的方式解耦。

**风险场景 2：system 中的 SelectController 查询 basic 的医院**

SelectController（system）查询 HospitalService（basic）是从上往下引用，没有反向依赖，✅ 无风险。

**风险场景 3：用户医院分配涉及 system → basic**

UserHospitalService（system）注入 HospitalMapper（basic）进行基础数据查询，✅ 无风险。

### 3.2 迁移说明

| 内容 | 分析 | 结论 |
|------|------|------|
| AreaEntity | 不继承 BaseEntity（地区数据来自权威 cnarea_2023，无通用字段），迁移后无任何逻辑影响 | 整体迁移 |

| schema.sql | sys_area 表的 DDL 移动到 basic 模块的 schema.sql | 需同步调整 |

### 4.5 sys_user_hospital 用户-医院关联表

```sql
CREATE TABLE sys_user_hospital (
    id                  BIGINT          NOT NULL AUTO_INCREMENT COMMENT '主键ID',
    user_id             BIGINT          NOT NULL COMMENT '用户ID（FK → sys_user.id）',
    hospital_id         BIGINT          NOT NULL COMMENT '医院ID（FK → hospital.id）',
    create_time         DATETIME        DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    PRIMARY KEY (id),
    UNIQUE KEY uk_user_hospital (user_id, hospital_id),
    KEY idx_user_id (user_id),
    KEY idx_hospital_id (hospital_id)
) COMMENT '用户-医院关联表';
```

**说明**：

- `hospital_id` 不加外键约束，保持灵活性，避免限制数据迁移
- 用户-医院关联表归属 system 模块，因为它是权限体系的一部分（用于实现医院范围权限）
- 模板明细表归属 basic 模块，因为模板是基础数据，供 system 模块引用
- **2026-03-20 变更**：`sys_user_hospital` 的权限判断从"角色的 `dataScope == 4`"改为"角色的 `dataScopeType == 'hospitals'`"

## 五、功能设计

### 5.1 编码生成规则

#### 医院编码（HOS-XXX）

```java
private String generateHospitalCode() {
    // 查找当前最大编码
    LambdaQueryWrapper<HospitalEntity> wrapper = new LambdaQueryWrapper<>();
    wrapper.likeRight(HospitalEntity::getHospitalCode, "HOS-")
           .orderByDesc(HospitalEntity::getHospitalCode)
           .last("LIMIT 1");
    HospitalEntity lastEntity = getOne(wrapper);

    int nextSeq = 1;
    if (lastEntity != null) {
        String lastCode = lastEntity.getHospitalCode();
        String seqStr = lastCode.substring("HOS-".length());
        nextSeq = Integer.parseInt(seqStr) + 1;
    }
    return String.format("HOS-%03d", nextSeq);
    // 示例：HOS-001, HOS-002, HOS-003 ...
}
```

#### 模板编码（TPL-HOS-XXX）

生成逻辑同上，前缀为 `TPL-HOS-`，示例：`TPL-HOS-001`。

### 5.5 数据权限模型

#### 角色定义"数据权限范围"，用户定义"具体的医院范围"

```
角色 dataScopeType = "org"/"self"（不启用医院范围）
    → 用户无法查看任何医院（对于非 hospitals 类型）
    → dataScopeType 用于控制数据权限维度

角色 dataScopeType = "hospitals"（启用医院范围）
    → 用户的具体医院范围由 sys_user_hospital 表决定
    → 同一角色下，不同用户可以有完全不同的医院范围
    → 查询时用 user_id → sys_user_hospital → hospital_id 过滤
```

#### 判断逻辑变更说明（2026-03-20）

**变更背景**：原设计中，`role.dataScope` 字段定义了5种数据范围（包括 HOSPITALS），通过角色的 `dataScope == 4` 来判断是否启用医院范围权限。

**变更后设计**：
- 角色表移除 `hospital_scope_enabled` 字段，改为 `data_scope_type` 字段（VARCHAR(16)）
- `data_scope_type` 值：`self`/`hospitals`/`org`/`all`
- 过滤逻辑从"检查角色 dataScope == HOSPITALS"改为"检查角色 dataScopeType == 'hospitals'"

**变更影响范围**：

| 组件 | 变更内容 |
|------|---------|
| `sys_role` 表 | 将 `hospital_scope_enabled` 替换为 `data_scope_type VARCHAR(16)` |
| `RoleEntity` | 替换 `hospitalScopeEnabled` 为 `dataScopeType` |
| `CreateRoleDTO` | 替换 `hospitalScopeEnabled` 为 `dataScopeType` |
| `UpdateRoleDTO` | 替换 `hospitalScopeEnabled` 为 `dataScopeType` |
| `RoleVO` | 替换 `hospitalScopeEnabled/hospitalScopeEnabledName` 为 `dataScopeType/dataScopeTypeName` |
| `RoleServiceImpl` | 更新判断条件为 `dataScopeType` |
| `UserServiceImpl` | 创建/更新用户时，判断条件从 `role.hospitalScopeEnabled == 1` 改为 `"hospitals".equals(role.dataScopeType)` |
| `HospitalScopeController` | 过滤逻辑重写，根据 `dataScopeType` 决定返回用户关联医院或空列表 |

#### 用户分配医院范围流程

```
用户编辑页 → 医院范围选择
    ├── 方式A：直接勾选医院
    │       → 调用 /api/basic/hospital/options 获取医院列表
    │       → 调用 /api/system/user/{userId}/hospitals（PUT）传入选中的 hospitalIds
    │
    └── 方式B：选择模板快速分配
            → 调用 /api/basic/hospitalGroupTemplate/options 获取模板列表
            → 选择模板后，调用 /api/basic/hospitalGroupTemplate/{id} 获取模板明细
            → 获取 hospitalIds 列表，调用 /api/system/user/{userId}/hospitals（PUT）
            → 管理员可在模板分配后手动增删个别医院
```

## 八、字典关联

### 8.1 复用现有字典

医院等级和医院类型复用 `sys_dict` 表中已有的字典数据：

| 字典编码 | 字典名称 | dict_code | 使用位置 |
|---------|---------|-----------|---------|
| 医院等级 | DictCodeConstants.HOSPITAL_LEVEL | "3" | hospital.hospital_level |
| 医院类型 | DictCodeConstants.HOSPITAL_TYPE | "4" | hospital.hospital_type |

### 8.2 字典名称填充

参考 `OrgServiceImpl.toVOWithDictNames()` 的模式，在 Entity→VO 转换时填充：

```java
private HospitalVO toVOWithDictNames(HospitalEntity entity) {
    HospitalVO vo = HospitalConvert.toVO(entity);

    // 医院等级名称
    if (entity.getHospitalLevel() != null) {
        vo.setHospitalLevelName(
            dictService.getDictNameByTypeCode("3", entity.getHospitalLevel().toString())
        );
    }

    // 医院类型名称
    if (entity.getHospitalType() != null) {
        vo.setHospitalTypeName(
            dictService.getDictNameByTypeCode("4", entity.getHospitalType().toString())
        );
    }

    // 状态名称
    if (entity.getStatus() != null) {
        vo.setStatusName(StatusConstants.getStatusName(entity.getStatus()));
    }

    // 完整地区路径
    if (entity.getAreaId() != null) {
        vo.setFullAreaName(areaService.getFullAreaName(entity.getAreaId()));
    }

    return vo;
}
```
