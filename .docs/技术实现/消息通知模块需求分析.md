# 医工宝消息通知功能模块需求分析

**文档版本**：2.0  
**最后更新**：2026-06-17

---

## 一、需求背景

订单在各阶段（订单→设计→生产→质检→仓储）流转时，下游处理人员无法及时感知，缺少强提醒机制，导致订单积压风险。

**核心诉求**：
1. **消息列表**：用户可查看历史消息，支持分类筛选
2. **强制弹窗**：关键流转节点强制弹窗确认，避免遗漏
3. **实时触达**：WebSocket 推送，离线消息登录后补弹

---

## 二、模块设计

### 2.1 模块定位

**新增模块**：`yigongbao-module-notification`

**核心职责**：监听业务事件 → 生成消息记录 → WebSocket 推送 → 提供查询/操作接口

**模块依赖**：
```
yigongbao-module-notification 依赖：
├── yigongbao-common（事件定义、Result、枚举）
├── yigongbao-framework（AOP、Redis、SaToken）
└── yigongbao-module-system（用户、角色、数据权限查询）
```

---

### 2.2 消息类型

#### 2.2.1 展现形式

| 类型 | 代码 | 说明 | 用户交互 |
|-----|------|------|---------|
| 普通消息 | `MESSAGE` | 消息列表可查看 | 主动查看，标记已读 |
| 弹窗通知 | `POPUP` | 强制弹窗确认 | 必须点击"确认"关闭 |

#### 2.2.2 业务分类

| 分类代码 | 说明 | 默认展现形式 |
|---------|------|-------------|
| `ORDER` | 订单类（驳回、取消等） | MESSAGE |
| `APPROVAL` | 审核类（待审核通知） | POPUP |
| `DESIGN` | 设计类（设计师分配） | POPUP |
| `PRODUCTION` | 生产类（待生产通知） | POPUP |

> 第一阶段仅实现以上四类；QC、WAREHOUSE、SYSTEM 等分类在后续阶段扩展。

---

### 2.3 通知服务 API

对外提供三种重载方法，内部统一收束到 `List<Long> userIds` 处理：

```java
public interface INotificationService {

    /**
     * 按角色推送，内部根据角色 dataScopeType + context 过滤目标用户
     */
    void send(String roleCode, NotificationContext context, NotificationDTO dto);

    /**
     * 推送给单个用户（审核驳回、设计师分配等定向推送）
     */
    void send(Long userId, NotificationDTO dto);

    /**
     * 最终收束点，上面两个方法最终都调用此方法
     */
    void send(List<Long> userIds, NotificationDTO dto);
}
```

**NotificationContext**（角色推送时提供业务上下文）：

| 字段 | 说明 | 适用 dataScopeType |
|------|------|-------------------|
| `hospitalId` | 订单关联医院ID | HOSPITALS |
| `orgId` | 订单关联机构ID | ORG、DEPT |
| `centerId` | 加工中心ID（= 流转卡 processingCenterId） | CENTER |

---

### 2.4 按角色推送的数据权限过滤策略

调用 `send(roleCode, context, dto)` 时，读取 `sys_role.data_scope_type`，按以下规则查询目标用户：

| dataScopeType | 过滤逻辑 | context 字段 |
|--------------|---------|-------------|
| `ALL` | 查询该角色的全部用户 | — |
| `ORG` | 查询该角色在 context.orgId 机构内的用户 | orgId |
| `CENTER` | 查询该角色在 context.centerId 加工中心内的用户 | centerId |
| `HOSPITALS` | 查询该角色关联医院包含 context.hospitalId 的用户（关联 sys_user_hospital） | hospitalId |
| `DEPT` | 查询该角色在 context.orgId 机构内同部门的用户 | orgId |
| `SELF` | 不适用角色推送，应改用 send(userId, dto) | — |

**SQL 示例**：
```sql
-- ORG scope
SELECT u.id FROM sys_user u
JOIN sys_role r ON u.role_id = r.id
WHERE r.role_code = #{roleCode} AND u.org_id = #{orgId} AND u.is_deleted = 0

-- HOSPITALS scope
SELECT u.id FROM sys_user u
JOIN sys_role r ON u.role_id = r.id
JOIN sys_user_hospital uh ON uh.user_id = u.id
WHERE r.role_code = #{roleCode} AND uh.hospital_id = #{hospitalId} AND u.is_deleted = 0

-- CENTER scope（生产员专用，sys_user.center_id 为加工中心ID）
SELECT u.id FROM sys_user u
JOIN sys_role r ON u.role_id = r.id
WHERE r.role_code = #{roleCode} AND u.center_id = #{centerId} AND u.is_deleted = 0
```

## 三、数据库设计

### 3.1 消息通知表 `notification_message`

| 字段名 | 类型 | 说明 |
|--------|-----|------|
| id | BIGINT | 主键 |
| message_type | VARCHAR(20) | MESSAGE / POPUP |
| category | VARCHAR(20) | ORDER / APPROVAL / DESIGN / PRODUCTION |
| title | VARCHAR(200) | 消息标题 |
| content | TEXT | 消息正文 |
| biz_type | VARCHAR(50) | 业务数据类型：ORDER / PRODUCTION_CARD |
| biz_id | BIGINT | 业务数据ID（订单ID 或 流转卡ID） |
| biz_data | JSON | 扩展业务数据（订单号、患者姓名等） |
| biz_status | VARCHAR(20) | 业务状态：NULL=正常，CLAIMED=已被他人接收 |
| jump_url | VARCHAR(500) | 前端路由跳转路径 |
| receiver_id | BIGINT | 接收人 sys_user.id |
| is_read | TINYINT | 0=未读，1=已读 |
| read_time | DATETIME | 阅读时间 |
| is_confirmed | TINYINT | 0=未确认，1=已确认（POPUP 专用） |
| confirmed_time | DATETIME | 确认时间 |
| create_time | DATETIME | 自动填充 |
| create_by | BIGINT | 系统填 -1 |
| update_time | DATETIME | 自动填充 |
| is_deleted | TINYINT | 逻辑删除 |

**索引**：
```sql
KEY idx_receiver_read (receiver_id, is_read, create_time)  -- 查询未读
KEY idx_biz (biz_type, biz_id)                             -- 关联业务（流转卡抢占更新用）
KEY idx_category_time (category, create_time)
```

**biz_status 说明**：
- `NULL`：正常待处理，POPUP 需弹窗确认
- `CLAIMED`：流转卡已被其他生产员接收，is_confirmed 同时置为 1，前端无需强制弹窗，显示"已被他人接收"

## 五、实时推送（WebSocket）

**连接地址**：`ws://{host}/api/notification/websocket`，Token 在握手首帧消息中传递

**服务端维护**：`userId → WebSocketSession` 映射，支持心跳保活与断线清理

**推送时机**：`send(List<Long> userIds, dto)` 写库后，遍历 userIds 向在线 Session 推送

**推送消息格式**：
```json
{
  "type": "NEW_MESSAGE",
  "data": {
    "id": 1001,
    "messageType": "POPUP",
    "category": "PRODUCTION",
    "title": "流转卡YGB-RC-001设计已完成，请接收生产",
    "bizStatus": null,
    "createTime": "2026-06-17 10:30:00"
  }
}
```

**离线消息**：消息仍写入数据库；用户登录后，前端主动拉取 `isConfirmed=0` 的 POPUP 消息逐个弹窗（后端仅提供查询接口，不做服务端登录推送）。

## 六、弹窗通知交互规则

- **强制确认**：必须点击"确认"按钮，禁止遮罩层关闭
- **排队顺序**：按 createTime 升序，确认一条后弹下一条
- **已确认**：`isConfirmed=1` 或 `bizStatus=CLAIMED` 的消息不再弹窗
- **查看详情**：跳转 jumpUrl 页面，同时将消息标记已读（不触发 confirm）
- **确认操作**：调用 `/confirm` 接口，同时标记已读

**biz_status=CLAIMED 消息处理**：不强制弹窗，消息列表内显示"已被他人接收"灰色状态

**业务跳转链接**：

| category | bizType | jumpUrl |
|---------|---------|---------|
| PRODUCTION | PRODUCTION_CARD | `/production/list` |
| DESIGN | ORDER | `/design/list` |
| APPROVAL | ORDER | `/order/detail/{bizId}` |
| ORDER | ORDER | `/order/detail/{bizId}` |

## 七、第一阶段事件规则

### 7.1 事件总览

| 事件类 | 发布位置 | 定向类型 |
|------|---------|---------|
| `OrderSubmittedEvent` | `OrderMainServiceImpl.submitOrder()` | 按角色 |
| `RegionalAuditPassedEvent` | `OrderMainServiceImpl.passAudit()` 仅试用订单 | 按角色 |
| `AuditRejectedEvent` | `OrderMainServiceImpl.rejectAudit()` | 按 userId |
| `DesignerAssignedEvent` | `DesignerAssignmentServiceImpl` | 按 userId |
| `OrderModifyApplySubmittedEvent` | `OrderModifyApplyServiceImpl.submitApply()` | 按角色 |
| `OrderModifyApplyRejectedEvent` | `OrderModifyApplyServiceImpl.auditApply()` | 按 userId |
| `ProductionCardsCreatedEvent` | 生产模块 `DesignCompletedListener` 创建完所有流转卡后发布 | 按角色（流转卡维度） |
| `ProductionCardClaimedEvent` | 生产模块下载数据包 Service | 内部触发 CLAIMED 更新 |

> `DesignCompletedEvent` 和 `ProductionCardClaimedEvent` 由通知模块监听；其余事件在发布后由 `NotificationEventListener` 处理。

---

### 7.2 各事件通知规则详情

#### 7.2.1 订单提交（`OrderSubmittedEvent`）

字段：`orderId, businessType, hospitalId, orgId, createBy`

| 条件 | 接收角色 | context | 消息类型 | 分类 |
|-----|---------|---------|---------|------|
| 试用订单（businessType=11.3） | `regional-manager` | HOSPITALS + hospitalId | POPUP | APPROVAL |
| 其他订单 | `designer-manager` | ORG + orgId | POPUP | APPROVAL |

> 试用订单提交后只通知区域管理员；区域审核通过后再触发设计管理员通知（见 7.2.2）。

---

#### 7.2.2 区域审核通过（`RegionalAuditPassedEvent`，仅试用订单）

字段：`orderId, orgId`

| 接收角色 | context | 消息类型 | 分类 |
|---------|---------|---------|------|
| `designer-manager` | ORG + orgId | POPUP | APPROVAL |

---

#### 7.2.3 审核驳回（`AuditRejectedEvent`）

字段：`orderId, createBy, rejectReason`

推送方式：`send(createBy, dto)`，消息类型：MESSAGE，分类：ORDER

---

#### 7.2.4 设计师分配（`DesignerAssignedEvent`）

字段：`orderId, newDesignerId, oldDesignerId（可为null）`

| 场景 | 接收对象 | 消息类型 | 分类 |
|-----|---------|---------|------|
| 首次分配（自动/手动） | newDesignerId | POPUP | DESIGN |
| 重新分配 - 通知新设计师 | newDesignerId | POPUP | DESIGN |
| 重新分配 - 通知旧设计师（任务被撤销） | oldDesignerId | MESSAGE | DESIGN |

---

#### 7.2.5 订单修改申请提交（`OrderModifyApplySubmittedEvent`）

字段：`orderId, orgId, applyUserId`

| 接收角色 | context | 消息类型 | 分类 |
|---------|---------|---------|------|
| `designer-manager` | ORG + orgId | POPUP | APPROVAL |

---

#### 7.2.6 订单修改申请驳回（`OrderModifyApplyRejectedEvent`）

字段：`applyId, applyUserId, rejectReason`

推送方式：`send(applyUserId, dto)`，消息类型：MESSAGE，分类：ORDER

---

#### 7.2.7 设计完成→生产通知（`ProductionCardsCreatedEvent`，流转卡维度）

**触发链**：设计模块发布 `DesignCompletedEvent` → 生产模块 `DesignCompletedListener` 创建所有流转卡 → 完成后发布 `ProductionCardsCreatedEvent`，通知模块监听此事件，避免竞态（若直接监听 `DesignCompletedEvent`，流转卡可能尚未写库）。

**通知维度**：一个订单 → N 张流转卡 → 每张流转卡各发一组通知

字段：`List<Long> recordIds`（已创建的流转卡ID列表）

每条通知按流转卡独立推送，`context.centerId = record.processingCenterId`：

| 接收角色 | context | 消息类型 | 分类 |
|---------|---------|---------|------|
| `production-worker` | CENTER + record.processingCenterId | POPUP | PRODUCTION |
| `production-manager` | CENTER + record.processingCenterId | POPUP | PRODUCTION |

每条通知的 biz 信息：
- `bizType = PRODUCTION_CARD`
- `bizId = recordId`（流转卡ID，非订单ID）

---

#### 7.2.8 流转卡被接收（`ProductionCardClaimedEvent`）

**触发时机**：某生产员执行 `DOWNLOAD_DATA_PACKAGE` 动作，流转卡状态变为 `PENDING_PRINT(3010)`

字段：`recordId, claimedByUserId`

**处理逻辑**（不向外推送，仅更新已有通知记录）：

```sql
UPDATE notification_message
SET biz_status = 'CLAIMED',
    is_confirmed = 1,
    confirmed_time = NOW()
WHERE biz_type = 'PRODUCTION_CARD'
  AND biz_id = #{recordId}
  AND receiver_id != #{claimedByUserId}
  AND is_confirmed = 0
  AND is_deleted = 0
```

> 接收该流转卡的生产员自己的通知不受影响，由其正常确认。

## 九、典型流程

### 9.1 设计完成 → 生产通知

```
设计完成 → DesignCompletedEvent
    ↓
NotificationEventListener 查询该订单所有流转卡 (N 张)
    ↓
每张流转卡：send("production-worker", Context(centerId=record.orgId), dto)
             send("production-manager", Context(centerId=record.orgId), dto)
    ↓
CENTER scope 过滤 → 获取目标用户列表
    ↓
批量写入 notification_message (bizType=PRODUCTION_CARD, bizId=recordId)
    ↓
WebSocket 推送在线用户 → 弹窗强制确认
```

### 9.2 流转卡抢占处理

```
生产员A 下载数据包 → DOWNLOAD_DATA_PACKAGE → PENDING_PRINT(3010)
    ↓
发布 ProductionCardClaimedEvent(recordId, userIdA)
    ↓
NotificationEventListener 批量更新其他生产员的通知：
  biz_status=CLAIMED, is_confirmed=1
    ↓
生产员B 打开消息列表：显示"已被他人接收"，无需处理
```

### 9.3 试用订单审核链

```
提交试用订单
    ↓ OrderSubmittedEvent
通知区域管理员 (HOSPITALS scope) → POPUP
    ↓ 区域管理员审核通过 → RegionalAuditPassedEvent
通知设计管理员 (ORG scope) → POPUP
    ↓ 设计管理员审核通过 → DesignerAssignedEvent
通知新设计师 (send by userId) → POPUP
```
