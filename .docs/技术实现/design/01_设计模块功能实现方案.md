## 一、概述

### 1.1 模块定位

设计模块是医工宝订单流程的第二阶段（phase=2），承接数据审核通过后的订单，负责将医学影像转化为可用于3D打印的数字化产品。设计阶段由设计师账户专属操作，是订单从"接单"到"生产制造"之间的核心桥梁。

**设计阶段与其他模块的关系**：

```
┌─────────────────────────────────────────────────────────────────┐
│                        订单全流程                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  订单阶段（phase=1）   设计阶段（phase=2）   生产阶段（phase=3~6）│
│  ┌──────────────┐     ┌──────────────┐     ┌──────────────┐     │
│  │  业务员提单   │ ──► │  设计师接单   │ ──► │  生产员接单   │     │
│  │  数据审核    │     │  上传设计文件  │     │  打印排产    │     │
│  │  审核通过    │     │  填写打印信息  │     │  后处理      │     │
│  └──────────────┘     │  生成指令单    │     │  质检入库    │     │
│                        │  生成图纸      │     └──────────────┘     │
│                        │  设计审核     │                          │
│                        │  审核通过     │ ──────────────────────────┼──► 确认完成（phase=7~8）
│                        └──────────────┘                          │
└─────────────────────────────────────────────────────────────────┘
```

### 1.2 功能范围

本方案覆盖设计阶段的全部功能：

| 功能域 | 描述 | 优先级 |
|--------|------|:------:|
| 设计师工单列表 | "我的工单"专属视图，按设计师过滤待设计订单 | P0 |
| 开始设计 | 设计师接收订单，记录设计开始时间 | P0 |
| 设计文件上传 | 打印文件（ZIP）、设计报告、可视化模型上传 | P0 |
| 打印信息填写 | 产品级联选择（产品→型号→材质→颜色→注册证） | P0 |
| 指令单生成 | 按数据包生成指令单（预览/下载/打印） | P0 |
| 图纸生成 | 按数据包生成图纸（预览/下载/上传修订版） | P0 |
| 提交设计 | 前置条件校验，触发设计审核 | P0 |

## 二、核心概念与编号规则

### 2.1 核心概念

| 概念 | 说明 |
|------|------|
| **数据包（Package）** | 设计师上传的打印文件包（ZIP格式），每个包对应一份指令单和一份图纸 |
| **打印文件** | STL/3MF/OBJ 等3D打印设计文件，存储于数据包内 |
| **打印信息** | 每个数据包关联的产品明细（产品名称、型号规格、材质、颜色、注册证号、打印模型、数量） |
| **指令单** | 生产指令单（ZL-xxx），用于指导生产人员按产品明细生产 |
| **图纸** | 设计图纸（TZ-xxx），包含3D模型图、二维码、订单信息等 |

### 2.2 编号规则

**所有编号通过 `CodeGeneratorService` 生成，规则如下**：

| 编号类型 | 规则 | 示例 | 生成时机 |
|----------|------|------|----------|
| 订单编号（已有） | `{年}{月}{日}-{6位流水}` | `20260407-000001` | 草稿提交时 |
| **数据包编号** | `{订单编号}-{序号}` | `20260407-000001-1` | 上传打印文件包时 |
| **指令单编号** | `ZL-{订单编号}-{序号}` | `ZL-20260407-000001-1` | 生成指令单时 |
| **图纸编号** | `TZ-{订单编号}-{序号}` | `TZ-20260407-000001-1` | 生成图纸时 |

> **说明**：序号从1开始，一个订单若有N个数据包，则序号为1~N，每份数据包对应唯一的指令单和图纸。

### 2.3 字典码扩展

设计阶段需要扩展以下文件类别字典（追加到现有 `10.x` 体系中）：

| 字典码 | 字典名称 | 说明 | 归属父节点 |
|--------|----------|------|------------|
| `10.1` | 影像数据 | CT/MRI等影像文件（已有） | 10 |
| `10.2` | 影像报告 | 医生出具的影像分析报告（已有） | 10 |
| `10.3` | 订单其他附件 | 订单相关其他附件（已有） | 10 |
| **`10.4`** | **打印文件** | **数据包（ZIP格式），含3D打印设计文件** | **10** |
| **`10.5`** | **设计报告** | **设计说明、设计参数（PDF/Word）** | **10** |
| **`10.6`** | **可视化模型** | **3D展示模型（3DPDF/PLY/STL）** | **10** |

| **`10.8`** | **图纸** | **设计图纸（系统生成+人工修订）** | **10** |

## 三、数据库设计

### 3.1 现有表扩展

#### 3.1.1 订单明细表扩展（order_item）

`order_item` 表在设计阶段需要新增以下字段，用于关联数据包和设计信息：

```sql
-- ==================== 设计阶段扩展字段 ====================
/**
 * 关联的数据包编号（order_design_package.package_no）
 * 设计师上传打印文件包时，系统自动生成数据包编号并回填至此字段
 */
ALTER TABLE order_item ADD COLUMN design_package_no VARCHAR(50) COMMENT '关联数据包编号' AFTER other_requirement;

/**
 * 关联的产品ID（product.id）
 * 设计师填写打印信息时选择，用于关联产品型号
 */
ALTER TABLE order_item ADD COLUMN product_id BIGINT COMMENT '关联产品ID' AFTER design_package_no;

/**
 * 产品名称（冗余，来自 product.product_name）
 */
ALTER TABLE order_item ADD COLUMN product_name VARCHAR(200) COMMENT '产品名称（冗余）' AFTER product_id;

/**
 * 型号规格（冗余，来自 product.spec）
 */
ALTER TABLE order_item ADD COLUMN product_spec VARCHAR(128) COMMENT '型号规格（冗余）' AFTER product_name;

/**
 * 材质（冗余，来自 product.material）
 */
ALTER TABLE order_item ADD COLUMN material VARCHAR(128) COMMENT '材质' AFTER product_spec;

/**
 * 颜色（设计师填写）
 */
ALTER TABLE order_item ADD COLUMN color VARCHAR(64) COMMENT '颜色' AFTER material;

/**
 * 注册证ID（关联 registration_cert.id）
 */
ALTER TABLE order_item ADD COLUMN cert_id BIGINT COMMENT '关联注册证ID' AFTER color;

/**
 * 注册证号（冗余，来自 registration_cert.cert_code）
 */
ALTER TABLE order_item ADD COLUMN cert_code VARCHAR(64) COMMENT '注册证号' AFTER cert_id;

/**
 * 数量（设计师填写）
 */
ALTER TABLE order_item ADD COLUMN quantity INT DEFAULT 1 COMMENT '数量' AFTER cert_code;

/**
 * 打印模型（JSON数组，设计师多选，关联 product.print_models）
 */
ALTER TABLE order_item ADD COLUMN print_models JSON COMMENT '打印模型（JSON数组）' AFTER quantity;

/**
 * 产品标识（用于追溯，设计师手动填写）
 */
ALTER TABLE order_item ADD COLUMN product_mark VARCHAR(128) COMMENT '产品标识' AFTER print_models;
```

### 3.2 新增表结构

#### 3.2.1 设计数据包表（order_design_package）

存储每个打印文件数据包的基本信息，每个数据包对应一份指令单和一份图纸。

```sql
-- ============================================================
-- 设计数据包表（order_design_package）
-- 用于存储设计师上传的打印文件包信息
-- 每个数据包对应一份指令单和一份图纸
-- ============================================================
DROP TABLE IF EXISTS order_design_package;
CREATE TABLE order_design_package (
    id                  BIGINT          NOT NULL AUTO_INCREMENT COMMENT '主键ID',
    order_id            BIGINT          NOT NULL COMMENT '订单ID',
    order_code         VARCHAR(50)     NOT NULL COMMENT '订单编号',
    order_item_id      BIGINT          COMMENT '关联的订单明细ID（可为null，表示与整个订单关联）',

    -- ==================== 数据包基本信息 ====================
    package_no         VARCHAR(50)     NOT NULL COMMENT '数据包编号（格式：{订单编号}-{序号}，如 20260407-000001-1）',
    package_name       VARCHAR(256)    COMMENT '数据包名称（设计师自定义，可选）',
    file_count         INT             DEFAULT 0 COMMENT '数据包内文件数量',

    -- ==================== 设计阶段状态 ====================
    status              TINYINT         DEFAULT 1 COMMENT '状态：1-待处理，2-处理中，3-已完成',

    -- ==================== 版本管理 ====================
    version             VARCHAR(10)     DEFAULT 'V1.0' COMMENT '版本号（如 V1.0、V1.1）',

    -- ==================== 公共字段 ====================
    create_time         DATETIME        DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    update_time         DATETIME        DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    create_by           BIGINT          COMMENT '创建人ID',
    update_by           BIGINT          COMMENT '更新人ID',
    is_deleted          TINYINT         DEFAULT 0 COMMENT '是否删除：0-否，1-是',

    PRIMARY KEY (id),
    UNIQUE KEY uk_package_no (package_no, is_deleted),
    KEY idx_package_order_id (order_id),
    KEY idx_package_order_item_id (order_item_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='设计数据包表';
```

### 4.2 第1步：查看工单

**入口**：设计师登录系统，进入「我的工单」页面

**数据范围**：查询当前设计师ID对应的订单，状态为「数据审核通过」或「设计中」

**查询条件**：

| 条件 | 说明 |
|------|------|
| `phase = 2`（设计阶段） | 仅显示设计阶段订单 |
| `status IN (12, 21, 23)` | 数据审核通过 / 设计中 / 设计审核中 |
| `designer_id = 当前用户ID` 或 `designer_id IS NULL AND phase=2` | 设计师本人的订单 + 待分配订单 |
| `is_deleted = 0` | 未删除 |

**列表展示字段**（精简版）：

| 字段 | 说明 |
|------|------|
| 订单编号 | order_code |
| 患者姓名 | patient_name |
| 部位 | 订单明细中的部位名称 |
| 重建项目 | 订单明细中的项目名称 |
| 期望交付时间 | expected_delivery_date |
| 当前状态 | statusName（设计中 / 待分配） |
| 操作 | 「查看详情」按钮 |

**状态说明**：

| status | 状态名称 | 含义 |
|--------|----------|------|
| `12` | 数据审核通过 | 订单已审核通过，等待设计师接单 |
| `21` | 设计中 | 设计师已开始设计 |
| `23` | 设计审核中 | 设计已提交，等待审核 |

### 4.3 第2步：开始设计

**触发时机**：设计师点击「开始设计」按钮

**前置条件**：

| 检查项 | 要求 |
|--------|------|
| 订单状态 | 必须是 `12-数据审核通过` |
| 当前用户 | 必须是订单当前处理人或管理员 |
| 设计师分配 | 如果 `designer_id` 为空，系统自动将 `designer_id` 设为当前用户 |

**执行动作**：

   - `designer_id` = 当前用户ID（如果为空）

   - `design_start_time` = 当前时间

   - `order_flow_status_history` 插入一条记录
   - `action = "START_DESIGN"`，`action_name = "开始设计"`

3. **发送通知**（可选）：
   - 通知设计师开始处理
   - 记录工时起点

**状态流转**：

```
12-数据审核通过  ──点击"开始设计"──►  21-设计中
```

### 4.4 第3步：上传设计文件

**触发时机**：设计师点击「上传设计文件」按钮

**上传类型**：

| 文件类型 | 字典码 | 必填 | 格式要求 | 说明 |
|----------|--------|:----:|----------|------|
| 打印文件（数据包） | `10.4` | ✅ 是 | **ZIP格式** | 包含 STL/3MF/OBJ 等打印文件，每个包对应一份指令单 |
| 设计报告 | `10.5` | ✗ 否 | PDF / Word | 设计说明、设计参数等 |
| 可视化模型 | `10.6` | ✗ 否 | 3DPDF / PLY / STL | 用于展示的三维模型 |

**数据包处理逻辑**：

1. **上传ZIP包**：
   - 前端将ZIP文件作为 `file_category=10.4` 上传
   - 系统存储文件，记录 `file_detail`
   - **自动生成数据包编号**：`{订单编号}-{序号}`，如 `20260407-000001-1`
   - 创建 `order_design_package` 记录
   - 在 `order_file` 表中关联 `package_no`

2. **数据包与订单明细关联**：
   - 设计师可选择将数据包关联到具体的订单明细（order_item）
   - 如果不关联，则数据包与整个订单关联

3. **序号生成规则**：
   - 查询该订单下已有的数据包数量 +1
   - 使用 `generateWithSeqSuffix(DATA_PACKAGE_NO, orderCode)` 生成

**上传接口请求示例**：

```json
POST /api/order/design/file/upload
{
  "orderId": 123,
  "fileCategory": "10.4",
  "packageNo": "20260407-000001-1",   // 系统自动生成，前端可传空
  "orderItemId": 456,                  // 可选，关联到具体明细
  "file": [文件二进制]
}
```

**响应示例**：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "fileId": "xxx",
    "fileName": "设计文件.zip",
    "fileUrl": "https://xxx/xxx.zip",
    "fileSize": 1024000,
    "packageNo": "20260407-000001-1",
    "packageId": 1
  }
}
```

#### 4.6.2 生成图纸

**前置条件检查**：

| 检查项 | 要求 |
|--------|------|
| 数据包数量 | 至少已上传1个打印文件数据包 |
| 数据包内文件 | 数据包内至少包含1个可渲染的文件 |

**图纸编号生成**：

- 规则：`TZ-{订单编号}-{序号}`，如 `TZ-20260407-000001-1`
- 使用 `generateWithBizPrefix(DRAWING_NO, 订单编号)` 生成

**页码规则**：

- 每份图纸为独立PDF文档（非同一PDF内的多页）
- 底部标注「第X页/共Y页」
- X = 当前数据包在该订单中的序号
- Y = 该订单下打印文件数据包总数

**图纸模板内容**：

| 区域 | 字段 | 数据来源 |
|------|------|----------|
| 主体网格 | 序号 | 系统按数据包内模型数量自动编号（1、2、3...） |
| 主体网格 | 文件名称 | 数据包内文件名（如「左髋」「左股骨」） |
| 主体网格 | 产品名称 | order_item.product_name |
| 主体网格 | 3D模型图片 | 数据包内文件渲染图（需前端上传预览图，或系统自动生成缩略图） |
| 右上角 | 二维码 | 指向在线3D模型查看链接（含订单流水号+访问令牌） |
| 底部信息区 | 订单编号 | order_main.order_code |
| 底部信息区 | 数据包编号 | package_no |
| 底部信息区 | 设计/日期 | 系统当前日期 |
| 底部信息区 | 审批/日期 | 设计审核时填写 |
| 底部信息区 | 第X页/共Y页 | 当前序号/数据包总数 |
| 底部信息区 | 生产机构名称 | 系统配置 `system.production.org.name` |
| 底部信息区 | 备注 | 可自动带出 order_item.product_mark，或人工填写 |
| 可选 | 版本号 | 当前版本号（如 V1.0） |

**图纸生成逻辑**：

1. 查询订单基本信息
2. 查询该数据包关联的产品明细
3. 查询数据包内的文件列表
4. 生成3D模型预览图（二维码链接需要系统配置）
5. 拼接图纸JSON内容
6. 创建 `order_design_drawing` 记录
7. 版本号：首次生成 `V1.0`，每次重新生成递增

**图纸操作**：

| 操作 | 说明 |
|------|------|
| 预览 | 在弹窗中展示图纸内容 |
| 下载 | 生成PDF文件并下载 |
| 上传修订版 | 上传人工修改后的图纸PDF |
| 电子签名 | 设计师点击签名 |

### 4.7 第6步：提交设计

**触发时机**：设计师完成所有设计工作后，点击「提交设计」按钮

**前置条件检查**：

| 检查项 | 要求 | 提示信息 |
|--------|------|----------|
| 设计文件 | 每个重建项目至少关联1个数据包 | "请先上传打印文件" |
| 打印信息 | 每个重建项目必填字段完整 | "请填写完整的打印信息" |
| 指令单 | 每个数据包必须生成指令单 | "请生成指令单" |
| 图纸 | 每个数据包必须生成图纸 | "请生成图纸" |

**提交后动作**：

1. **更新订单状态**：
   - `design_submit_time` = 当前时间
   - `status` = `23`（设计审核中）
   - `current_handler_id` = 分配给审核人员（或设计管理员）

2. **创建审核任务**：
   - 在审核任务列表中新增一条记录
   - 分配给设计管理员/业务管理员/系统管理员

3. **记录状态历史**：
   - `order_flow_status_history` 插入记录
   - `action = "SUBMIT_DESIGN"`，`action_name = "提交设计"`

**状态流转**：

```
21-设计中  ──点击"提交设计"──►  23-设计审核中
```

### 4.8 第7步：设计审核

**审核角色**：

| 角色 | 审核权限 |
|------|----------|
| 设计管理员 | ✅ 可审核 |
| 业务管理员 | ✅ 可审核 |
| 系统管理员 | ✅ 可审核 |

**审核操作**：

#### 4.8.1 审核通过

**前置条件**：

| 检查项 | 说明 |
|--------|------|
| 指令单 | 设计师已签名（designer_sign_url 不为空） |
| 图纸 | 设计师已签名（designer_sign_url 不为空） |

**执行动作**：

1. **更新审核信息**：
   - `reviewer_sign_url` = 审核签名图片URL
   - `reviewer_sign_time` = 当前时间
   - `review_remark` = 审核备注（可选）

2. **更新订单状态**：
   - 根据 `needs_physical_delivery` 判断后续流程
   - **需要实体交付**（=1）：`status = 31`（待打印），流转至生产模块
   - **不需要实体交付**（=0）：`status = 71`（待客户确认），流转至确认阶段

3. **记录状态历史**：
   - `action = "DESIGN_REVIEW_PASS"`，`action_name = "设计审核通过"`

**状态流转**：

```
23-设计审核中  ──审核通过──►  31-待打印（需实体交付）
                             或
                          71-待客户确认（不需实体交付）
```

#### 4.8.2 审核驳回

**前置条件**：

| 检查项 | 说明 |
|--------|------|
| 驳回原因 | 必须填写（audit_remark 必填） |

**执行动作**：

1. **更新审核信息**：
   - `design_review_remark` = 驳回原因

2. **更新订单状态**：
   - `status` = `25`（设计审核不通过）
   - `current_handler_id` = 设计师ID（便于设计师重新处理）

3. **记录状态历史**：
   - `action = "DESIGN_REVIEW_REJECT"`，`action_name = "设计审核驳回"`

4. **发送通知**：
   - 通知设计师设计被驳回
   - 包含驳回原因

**状态流转**：

```
23-设计审核中  ──审核驳回──►  25-设计审核不通过
```

#### 4.8.3 驳回后重新提交

设计师修改后重新提交：

```
25-设计审核不通过  ──修改后重新提交──►  23-设计审核中
```

---

### 4.9 不需要实体交付订单的特殊处理

**适用场景**：设计服务订单，仅提供设计成果，不涉及实物生产和交付

**流程差异**：

| 阶段 | 需要实体交付 | 不需要实体交付 |
|------|:------------:|:-------------:|
| 设计审核通过后 | 进入 31-待打印 | 进入 71-待客户确认 |
| 后续流程 | 生产 → 质检 → 入库 → 确认 → 完成 | 客户确认 → 完成 |

**确认操作**：

| 项目 | 说明 |
|------|------|
| 触发条件 | 设计审核通过，且 `needs_physical_delivery=0` |
| 操作角色 | 业务员/区域管理员/经销商（订单创建者） |
| 操作动作 | 点击「确认完成」按钮 |
| 状态变更 | `status = 80`（已完成） |
| 确认记录 | 确认时间、确认人自动记录 |

## 十三、风险与注意事项

### 13.1 数据包与订单明细的关联

- 一个数据包可关联一个或多个订单明细
- 一个订单明细只能关联一个数据包
- 删除数据包时需校验是否被引用

### 13.2 打印信息的版本管理

- 每次修改打印信息后，指令单和图纸的版本号应递增
- 版本号格式：`V{主版本}.{次版本}`，如 V1.0 → V1.1
- 重新生成指令单/图纸时自动递增

### 13.3 文件清理

- 上传的设计文件应与订单绑定，不允许跨订单使用
- 数据包删除时级联删除关联的指令单和图纸记录
- 修订版文件保留历史记录，便于追溯

### 13.4 权限控制

- 「我的工单」页面仅展示当前设计师的订单
- 设计审核功能仅限设计管理员/业务管理员/系统管理员
- 文件上传/删除需校验是否为当前订单的设计师

### 13.5 性能考虑

- 数据包内文件数量可能较多，上传时建议分片上传
- PDF 生成可能耗时较长，考虑异步处理 + 轮询
- 订单详情页加载时，设计文件列表建议懒加载
