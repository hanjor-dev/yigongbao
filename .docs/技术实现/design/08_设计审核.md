## 一、任务概述

实现设计审核功能，包括审核列表、审核详情、审核通过/驳回操作。审核记录追加写入 `design_review` 表，不覆盖历史。

---

## 二、涉及接口

| 接口 | 方法 | 说明 |
|------|------|------|
| `POST /design/review/list` | POST | 查询待审核工单列表 |
| `GET /design/review/{orderId}` | GET | 获取审核详情 |
| `POST /design/review/{orderId}/pass` | POST | 审核通过 |
| `POST /design/review/{orderId}/reject` | POST | 审核驳回 |

## 三、业务逻辑

### 3.1 审核列表

- 复用 `DesignWorkorderService.listWorkorders` 查询逻辑
- 强制覆盖 `queryDTO.status = 2040`，前端无需传 status
- 筛选条件：订单编号、患者姓名、设计师姓名

### 3.2 审核详情

- `DesignReviewDetailVO extends DesignWorkorderDetailVO`，继承工单详情全部字段
- `BeanUtils.copyProperties` 复制工单详情，追加 `reviewHistory` 列表
- 审核历史按 `reviewTime` 倒序

### 3.3 审核通过

- 前置状态：2040 设计审核中（DESIGN_REVIEWING）
- 写入审核记录（`reviewResult=1`，通过）
- **单次调用** `FlowActionEnum.DESIGN_REVIEW_PASS`
  - Flow 模块内部根据 `needsPhysicalDelivery` 自动分支：
    - `=1` → 2050（不可见） → 3010 待打印
    - `=0` → 2050（不可见） → 7010 待客户确认
  - `TransitionResult.getFinalStatus()` 返回最终可见状态（3010 或 7010）
- 回写 `order_main.status = finalStatus`，清空 `currentHandlerId/Name`

### 3.4 审核驳回

- 前置状态：2040 设计审核中（DESIGN_REVIEWING）
- 目标状态：2060 设计审核不通过（DESIGN_REVIEW_REJECTED）
- 写入审核记录（`reviewResult=0`，驳回，含 `rejectReason`）
- 调用 `FlowActionEnum.DESIGN_REVIEW_REJECT`
- 回写 `order_main`：
  - `designReviewRemark = rejectReason`（快照，供列表/详情展示）
  - `currentHandlerId/Name` 恢复为 `order.designerId/designerName`

## 四、数据模型

### design_review 表（审核历史，追加写入）

| 字段 | 说明 |
|------|------|
| `orderId` | 订单 ID |
| `reviewerId` | 审核人 ID |
| `reviewerName` | 审核人姓名（冗余，防止用户改名后历史显示异常） |
| `reviewResult` | 0=驳回，1=通过 |
| `comment` | 审批意见（可选，通过时填写） |
| `rejectReason` | 驳回原因（驳回时必填） |
| `reviewTime` | 审核时间 |

### DesignReviewDetailVO

```
DesignWorkorderDetailVO
  └── List<DesignReviewHistoryVO> reviewHistory
        ├── id
        ├── reviewerName
        ├── reviewResult（0/1）
        ├── reviewResultName（"驳回"/"通过"）
        ├── comment
        ├── rejectReason
        └── reviewTime
```

## 五、关键实现细节

**Integer 比较安全写法**（避免自动拆箱 NPE）：

```java
Integer.valueOf(1).equals(entity.getReviewResult()) ? "通过" : "驳回"
```

**审核通过单次调用原则**：不需要在业务层判断 `needsPhysicalDelivery`，flow 模块封装了分支逻辑，`TransitionResult` 直接返回最终目标状态。
