# 05_用户管理功能实现方案

## 一、模块概述

用户管理模块是医工宝系统的基础权限管理模块，负责管理系统中的所有用户账号。该模块与机构管理、部门管理、角色管理、资源管理、鉴权模块紧密关联，共同构成系统的用户权限体系。

### 1.1 核心能力

- 用户账号的创建、编辑、删除、状态管理
- 用户密码的初始化、重置和修改
- 用户与机构、部门、角色的关联管理
- 用户医院范围权限的分配（基于角色配置）
- 用户个人信息的自管理（修改手机号、头像）

## 二、数据库设计

### 2.1 用户表（sys_user）

```sql
CREATE TABLE sys_user (
    id                  BIGINT          NOT NULL AUTO_INCREMENT COMMENT '主键ID',
    username            VARCHAR(32)     NOT NULL COMMENT '用户名（登录账号）',
    password            VARCHAR(128)    NOT NULL COMMENT '登录密码（BCrypt加密）',
    real_name           VARCHAR(32)    NOT NULL COMMENT '真实姓名',
    phone               VARCHAR(20)     NOT NULL COMMENT '手机号',
    email               VARCHAR(64)     COMMENT '邮箱',
    sex                 TINYINT         COMMENT '性别（0=女，1=男）',
    avatar              VARCHAR(512)    COMMENT '头像路径',
    account_type        TINYINT         NOT NULL COMMENT '账户分类（1=内部用户，2=外部用户）',
    org_id              BIGINT          NOT NULL COMMENT '所属机构ID',
    org_name            VARCHAR(128)    COMMENT '所属机构名称（冗余字段）',
    dept_id             BIGINT          COMMENT '所属部门ID',
    dept_name           VARCHAR(128)    COMMENT '所属部门名称（冗余字段）',
    role_id             BIGINT          COMMENT '关联角色ID',
    role_name           VARCHAR(64)     COMMENT '关联角色名称（冗余字段）',
    role_code           VARCHAR(32)     COMMENT '关联角色编码（冗余字段）',

    -- 扩展字段
    employee_no         VARCHAR(32)     COMMENT '工号',
    specialty           VARCHAR(255)    COMMENT '专业方向（多选，逗号拼接，如 7.1,7.5）',
    qualification       VARCHAR(256)    COMMENT '资质证书信息',
    settlement_type     TINYINT         COMMENT '结算类型',

    -- 状态与安全
    status              TINYINT         DEFAULT 1 COMMENT '状态（0=禁用，1=正常）',
    login_fail_count    TINYINT         DEFAULT 0 COMMENT '连续登录失败次数',
    lock_time           DATETIME        COMMENT '账户锁定时间',
    remark              VARCHAR(512)    COMMENT '备注说明',

    -- 通用字段
    create_time         DATETIME        DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    update_time         DATETIME        DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    create_by           BIGINT          DEFAULT NULL COMMENT '创建人ID',
    update_by           BIGINT          DEFAULT NULL COMMENT '更新人ID',
    is_deleted          TINYINT         DEFAULT 0 COMMENT '是否删除（0=否，1=是）',

    PRIMARY KEY (id),
    UNIQUE KEY uk_username (username),
    UNIQUE KEY uk_phone (phone),
    KEY idx_user_org_id (org_id),
    KEY idx_user_dept_id (dept_id),
    KEY idx_user_role_id (role_id),
    KEY idx_user_account_type (account_type),
    KEY idx_user_status (status)
);
```

### 2.2 用户医院关联表（sys_user_hospital）

```sql
CREATE TABLE sys_user_hospital (
    id                  BIGINT          NOT NULL AUTO_INCREMENT COMMENT '主键ID',
    user_id             BIGINT          NOT NULL COMMENT '用户ID',
    hospital_id         BIGINT          NOT NULL COMMENT '医院ID',
    create_time         DATETIME        DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',

    PRIMARY KEY (id),
    UNIQUE KEY uk_user_hospital (user_id, hospital_id),
    KEY idx_user_id (user_id),
    KEY idx_hospital_id (hospital_id)
);
```

### 2.3 字段设计说明

| 分类 | 字段 | 设计说明 |
|-----|------|---------|
| 登录凭证 | username, password | username 全局唯一，BCrypt 加密存储密码 |
| 身份信息 | real_name, phone, email, sex, avatar | 基本个人信息 |
| 账户分类 | account_type | 区分内部用户（1）和外部用户（2），用于角色权限隔离 |
| 组织架构 | org_id, org_name, dept_id, dept_name | 用户归属的机构和部门，含冗余字段优化查询 |
| 角色关联 | role_id, role_name, role_code | 用户关联的角色，含冗余字段 |
| 业务扩展 | employee_no, specialty, qualification, settlement_type | specialty 支持多选（逗号拼接），存储设计师擅长专业方向列表；其余为医工宝业务相关扩展字段 |
| 安全控制 | status, login_fail_count, lock_time | 账户状态和登录失败锁定机制 |

## 四、核心业务逻辑

### 4.1 用户创建流程

```
创建用户（createUser）
  │
  ├─1. 校验用户名唯一性
  │    └─ isUsernameExists(username)
  │         └─ 抛出 USER_EXISTS(617)
  │
  ├─2. 校验手机号唯一性
  │    └─ isPhoneExists(phone)
  │         └─ 抛出 USER_PHONE_EXISTS(618)
  │
  ├─3. 校验所属机构存在
  │    └─ OrgService.getById(orgId)
  │         └─ 抛出 USER_ORG_NOT_FOUND(619)
  │
  ├─4. 校验所属部门存在（如有）
  │    └─ DeptService.getById(deptId)
  │         └─ 抛出 USER_DEPT_NOT_FOUND(620)
  │
  ├─5. 校验角色存在（如有）
  │    └─ RoleService.getById(roleId)
  │         └─ 抛出 USER_ROLE_NOT_FOUND(621)
  │
  ├─6. 填充冗余字段
  │    └─ fillRedundantFields(entity)
  │         ├─ orgName = OrgService.getById(orgId).orgName
  │         ├─ deptName = DeptService.getById(deptId).deptName
  │         └─ roleName/roleCode = RoleService.getById(roleId).roleName/roleCode
  │
  ├─7. 处理密码
  │    ├─ 如提供密码：使用提供的密码
  │    └─ 如未提供：从系统配置获取默认密码
  │         └─ configService.getConfigValue("default.password")
  │    └─ BCrypt 加密存储
  │
  ├─8. 保存用户
  │    └─ save(entity)
  │
  └─9. 处理医院范围权限
       └─ 如角色 dataScopeType="hospitals" 且提供了 hospitalIds
            └─ UserHospitalService.assignHospitals(userId, hospitalIds)
```

### 4.2 用户更新流程

```
更新用户（updateUser）
  │
  ├─1. 校验用户存在
  │    └─ getById(id)
  │         └─ 抛出 USER_NOT_FOUND(600)
  │
  ├─2. 校验手机号唯一性（排除自身）
  │    └─ isPhoneExistsExcludingId(phone, id)
  │         └─ 抛出 USER_PHONE_EXISTS(618)
  │
  ├─3. 校验所属机构存在（且有变更）
  │    └─ OrgService.getById(orgId)
  │         └─ 抛出 USER_ORG_NOT_FOUND(619)
  │    └─ 更新 orgName 冗余字段
  │
  ├─4. 校验所属部门存在（且有变更）
  │    └─ DeptService.getById(deptId)
  │         └─ 抛出 USER_DEPT_NOT_FOUND(620)
  │    └─ 更新 deptName 冗余字段
  │
  ├─5. 校验角色存在（且有变更）
  │    └─ RoleService.getById(roleId)
  │         └─ 抛出 USER_ROLE_NOT_FOUND(621)
  │    └─ 更新 roleName/roleCode 冗余字段
  │
  ├─6. 处理医院范围权限变更
  │    ├─ 角色变更时：根据新角色处理医院范围
  │    └─ 角色未变更但医院列表有变更：根据当前角色处理
  │    └─ 前提：新/当前角色的 dataScopeType="hospitals"
  │
  ├─7. 更新用户信息
  │    └─ BeanUtils.copyProperties，排除不可修改字段
  │         └─ id, username, password, createTime, updateTime, createBy, updateBy
  │
  └─8. 保存更新
       └─ updateById(entity)
```

### 4.3 密码管理

| 操作 | 接口 | 说明 |
|-----|------|------|
| 创建用户 | POST /api/system/user | 密码可选，未提供时使用系统默认密码（`default.password` 配置） |
| 重置密码 | PUT /api/system/user/{id}/reset-password | 强制设为系统默认密码 |
| 修改密码 | PUT /api/system/user/{id}/change-password | 需验证旧密码 |

**密码加密**：使用 BCryptPasswordEncoder，密码存储格式为 `$2a$10$...`（盐值内置）。

### 4.4 医院范围权限机制

医院范围权限是系统中非常重要的数据权限控制机制，用于限制用户只能访问特定医院的业务数据。

#### 4.4.1 核心概念

- **启用条件**：当用户角色的 `dataScopeType="hospitals"` 时，该角色的用户才具有分配医院范围的能力
- **数据来源**：`sys_user_hospital` 表存储用户与医院的关联关系
- **控制粒度**：用户级别的医院数据范围控制

#### 4.4.2 医院范围分配流程

```
assignHospitals(userId, hospitalIds)
  │
  ├─1. 校验用户存在
  │    └─ UserMapper.selectById(userId)
  │         └─ 抛出 USER_NOT_FOUND(600)
  │
  ├─2. 校验医院ID有效性
  │    ├─ 查询所有医院
  │    ├─ 过滤不存在的医院 → 抛出 PARAM_ERROR
  │    └─ 检查是否有禁用的医院 → 抛出 PARAM_ERROR
  │
  ├─3. 删除旧关联
  │    └─ UserHospitalMapper.deleteByUserId(userId)
  │
  └─4. 插入新关联
       └─ 逐条插入 UserHospitalEntity
```

#### 4.4.3 医院范围查询

| 方法 | 说明 |
|-----|------|
| `getHospitalIdsByUserId(userId)` | 获取单个用户的医院ID列表 |
| `listHospitalIdsByUserIds(userIds)` | 批量获取用户的医院ID列表 |
| `getHospitalsByUserId(userId)` | 获取单个用户的医院详情列表 |

### 4.5 关联模块说明

| 关联模块 | 关系 | 作用 |
|---------|------|------|
| OrgService（机构管理） | 用户 → 机构（N:1） | 用户必须归属某个机构；机构下有用户时禁止删除 |
| DeptService（部门管理） | 用户 → 部门（N:1） | 用户可选归属某个部门；部门下有用户时禁止删除 |
| RoleService（角色管理） | 用户 → 角色（N:1） | 用户必须关联一个角色；决定用户的权限集合 |
| ConfigService（系统配置） | 用户 ← 配置 | 从配置中获取默认密码 `default.password` |
| HospitalModule（医院管理） | 用户 ↔ 医院（N:N） | 通过 sys_user_hospital 表实现多对多关联 |

### 4.6 管理员新建用户场景操作流程

管理员新建用户时，根据用户类型和角色不同，有以下几种典型场景：

#### 4.6.1 场景一：创建内部用户（设计师/生产员）

适用角色：`ROLE_DESIGNER`（设计师）、`ROLE_PRODUCTION`（生产员）等 `dataScopeType="org"` 的内部用户。

```
前端操作流程：
  │
  ├─1. 选择账户分类
  │    └─ accountType = 1（内部用户）
  │
  ├─2. 填写基本信息
  │    ├─ username（登录账号）
  │    ├─ realName（真实姓名）
  │    ├─ phone（手机号）
  │    ├─ sex（性别）
  │    └─ email（邮箱，可选）
  │
  ├─3. 选择所属机构（必选）
  │    └─ orgId（关联机构）
  │
  ├─4. 选择所属部门（可选）
  │    └─ deptId（关联部门）
  │
  ├─5. 选择角色（必选）
  │    └─ roleId = 2（设计师）或 roleId = 3（生产员）
  │    └─ 注意：dataScopeType = "org"，不显示医院选择区域
  │
  ├─6. 填写业务扩展信息（设计师角色必填，其他可选）
  │    ├─ employeeNo（工号）
  │    ├─ specialtyList（专业方向，多选，从字典 7.x 中选择，如 ["7.1.1", "7.2.1"]）
  │    ├─ qualification（资质证书）
  │    └─ settlementType（结算类型）
  │
  └─7. 提交创建
       └─ POST /api/system/user
       └─ hospitalIds 字段不传或传空数组

后端处理要点：
  ├─ 填充冗余字段：orgName、deptName、roleName、roleCode
  ├─ 密码处理：未提供密码时使用系统默认密码（default.password）
  └─ 医院范围：不分配（dataScopeType="org"，非 hospitals）
```

**请求示例**：

```json
{
  "username": "designer_new",
  "realName": "新设计师",
  "phone": "13900000001",
  "accountType": 1,
  "orgId": 1,
  "deptId": 1,
  "roleId": 2,
  "specialtyList": ["7.1.1", "7.2.1"],
  "settlementType": 1
}
```

#### 4.6.2 场景二：创建外部用户（机构管理员/机构用户）

适用角色：`ROLE_ORG_ADMIN`（机构管理员）、`ROLE_ORG_USER`（机构用户）等 `accountType=2` 的外部用户。

```
前端操作流程：
  │
  ├─1. 选择账户分类
  │    └─ accountType = 2（外部用户）
  │
  ├─2. 填写基本信息（同场景一）
  │
  ├─3. 选择所属机构（必选）
  │    └─ orgId（外部机构，如经销商、医院等）
  │
  ├─4. 选择所属部门（可选）
  │    └─ deptId
  │
  ├─5. 选择角色（必选）
  │    └─ roleId = 6（机构管理员）或 roleId = 7（机构用户）
  │    └─ 注意：dataScopeType = "org"，不显示医院选择区域
  │
  └─6. 提交创建

后端处理要点：
  └─ 与场景一类似，但 accountType = 2
```

#### 4.6.3 场景三：创建业务员用户（启用医院范围权限）

适用角色：`ROLE_SALES`（业务员）等 `dataScopeType="hospitals"` 的用户。

这是最复杂的场景，需要管理员为用户分配具体的医院范围。

```
前端操作流程：
  │
  ├─1. 选择账户分类
  │    └─ accountType = 1（内部用户）
  │
  ├─2. 填写基本信息（同场景一）
  │
  ├─3. 选择所属机构（必选）
  │    └─ orgId（如经销商机构）
  │
  ├─4. 选择角色（必选）
  │    └─ roleId = 4（业务员）
  │    └─ 系统自动检测：dataScopeType = "hospitals" → 显示医院选择区域
  │
  ├─5. 分配医院范围
  │    │
  │    ├─ 方式A：直接勾选医院（推荐）
  │    │    ├─ 调用 GET /api/system/user/hospital/options 获取可分配的医院列表
  │    │    ├─ 前端展示树形/列表供管理员勾选
  │    │    └─ 选中的 hospitalIds 提交到后端
  │    │
  │    └─ 方式B：使用医院组合模板（简化操作）
  │         ├─ 调用 GET /api/basic/hospitalGroupTemplate/list 获取模板列表
  │         ├─ 管理员选择一个模板，预览模板包含的医院
  │         ├─ 可在模板基础上微调（增删个别医院）
  │         └─ 最终的 hospitalIds 提交到后端
  │
  └─6. 提交创建
       └─ POST /api/system/user
       └─ hospitalIds 字段传入选中的医院ID列表

后端处理要点：
  ├─ 校验角色 dataScopeType = "hospitals"
  ├─ UserHospitalService.assignHospitals(userId, hospitalIds)
  │    ├─ 校验所有 hospitalIds 存在且状态正常
  │    ├─ 删除旧关联（覆盖式）
  │    └─ 插入新关联
  └─ 分配结果：用户只能访问其被分配的医院的业务数据
```

#### 4.6.4 场景四：创建医生用户

适用角色：`ROLE_DOCTOR`（医生），`dataScopeType="self"`，但用户数据与医院紧密相关。

```
前端操作流程：
  │
  ├─1. 选择账户分类
  │    └─ accountType = 1（内部用户）
  │
  ├─2. 选择所属机构（必选）
  │    └─ orgId（如医疗机构）
  │
  ├─3. 选择角色
  │    └─ roleId = 5（医生）
  │    └─ dataScopeType = "self"，不单独分配医院
  │    └─ 医生所属医院通过 orgId 隐式关联
  │
  └─4. 提交创建

后端处理要点：
  ├─ 医生可查看本机构（orgId）下的所有数据
  └─ 不使用 sys_user_hospital 表分配医院
```

## 六、数据权限设计

### 6.1 用户数据权限的层级结构

医工宝系统的数据权限采用五级控制机制（见 `DataScopeConstants`）：

| 值 | 常量 | 说明 |
|----|------|------|
| 1 | ALL | 全部数据（系统管理员） |
| 2 | ORG | 本机构数据 |
| 3 | SELF | 仅自己的数据 |
| 4 | HOSPITALS | 医院范围数据（通过 sys_user_hospital 限制） |
| 5 | DEPT | 本部门数据 |

### 6.2 医院范围权限的实现

数据权限的具体实现需要结合业务模块。以医院管理模块为例：

1. 用户登录后，系统通过 `UserHospitalService.getHospitalIdsByUserId(userId)` 获取该用户可访问的医院ID列表
2. 业务查询时，在 SQL 或 Service 层添加 `hospital_id IN (...)` 条件限制
3. 仅当用户的角色配置了 `dataScopeType="hospitals"` 时，才会分配医院范围
