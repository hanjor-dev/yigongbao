# 05_用户管理功能实现方案

## 一、模块概述

用户管理模块是医工宝系统的基础权限管理模块，负责管理系统中的所有用户账号。该模块与机构管理、部门管理、角色管理、资源管理、鉴权模块紧密关联，共同构成系统的用户权限体系。

### 1.1 核心能力

- 用户账号的创建、编辑、删除、状态管理
- 用户密码的初始化、重置和修改
- 用户与机构、部门、角色的关联管理
- 用户医院范围权限的分配（基于角色配置）
- 用户个人信息的自管理（修改手机号、头像）

## 二、数据库设计

### 2.1 用户表（sys_user）

```sql
CREATE TABLE sys_user (
    id                      BIGINT          NOT NULL AUTO_INCREMENT COMMENT '主键ID',
    username                VARCHAR(32)     NOT NULL COMMENT '用户名（登录账号）',
    password                VARCHAR(128)    NOT NULL COMMENT '登录密码（BCrypt加密）',
    real_name               VARCHAR(32)     NOT NULL COMMENT '真实姓名',
    phone                   VARCHAR(20)     NOT NULL COMMENT '手机号',
    email                   VARCHAR(64)     COMMENT '邮箱',
    sex                     VARCHAR(8)      COMMENT '性别（字典值）',
    avatar                  VARCHAR(512)    COMMENT '头像路径',
    account_type            TINYINT         NOT NULL DEFAULT 1 COMMENT '账户分类（1=内部用户，2=外部用户）',
    org_id                  BIGINT          NOT NULL COMMENT '所属机构ID',
    org_name                VARCHAR(128)    COMMENT '所属机构名称（冗余字段）',
    dept_id                 BIGINT          COMMENT '所属部门ID',
    dept_name               VARCHAR(128)    COMMENT '所属部门名称（冗余字段）',
    role_id                 BIGINT          COMMENT '关联角色ID',
    role_name               VARCHAR(64)     COMMENT '关联角色名称（冗余字段）',
    role_code               VARCHAR(32)     COMMENT '关联角色编码（冗余字段）',

    -- 扩展字段
    employee_no             VARCHAR(32)     COMMENT '工号',
    specialty               VARCHAR(255)    COMMENT '专业方向（多选，逗号拼接，如 7.1,7.5）',
    qualification           VARCHAR(256)    COMMENT '资质证书信息',
    settlement_type         TINYINT         COMMENT '结算类型',

    -- 列设置
    order_column_settings   TEXT            COMMENT '订单列表列设置（JSON）',
    design_column_settings  TEXT            COMMENT '设计列表列设置（JSON）',

    -- 状态与安全
    status                  TINYINT         DEFAULT 1 COMMENT '状态（0=禁用，1=正常）',
    login_fail_count        TINYINT         DEFAULT 0 COMMENT '连续登录失败次数',
    lock_time               DATETIME        COMMENT '账户锁定时间',
    remark                  VARCHAR(512)    COMMENT '备注说明',

    -- 通用字段
    create_time             DATETIME        DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    update_time             DATETIME        DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    create_by               BIGINT          DEFAULT NULL COMMENT '创建人ID',
    update_by               BIGINT          DEFAULT NULL COMMENT '更新人ID',
    is_deleted              TINYINT         DEFAULT 0 COMMENT '是否删除（0=否，1=是）',

    PRIMARY KEY (id),
    KEY idx_user_org_id (org_id),
    KEY idx_user_dept_id (dept_id),
    KEY idx_user_role_id (role_id),
    KEY idx_user_account_type (account_type),
    KEY idx_user_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';

-- 函数唯一索引（支持逻辑删除后重建）
CREATE UNIQUE INDEX uk_user_username
    ON sys_user ((CASE WHEN is_deleted = 0 THEN username ELSE NULL END));
CREATE UNIQUE INDEX uk_user_phone
    ON sys_user ((CASE WHEN is_deleted = 0 THEN phone ELSE NULL END));
CREATE UNIQUE INDEX uk_user_email
    ON sys_user ((CASE WHEN is_deleted = 0 THEN email ELSE NULL END));
```

### 2.2 用户医院关联表（sys_user_hospital）

```sql
CREATE TABLE sys_user_hospital (
    id                  BIGINT          NOT NULL AUTO_INCREMENT COMMENT '主键ID',
    user_id             BIGINT          NOT NULL COMMENT '用户ID',
    hospital_id         BIGINT          NOT NULL COMMENT '医院机构ID（引用 sys_org.id，orgType=1.3）',
    create_time         DATETIME        DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',

    PRIMARY KEY (id),
    KEY idx_user_hospital_user_id (user_id),
    KEY idx_user_hospital_hospital_id (hospital_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户医院关联表';

CREATE UNIQUE INDEX uk_user_hospital
    ON sys_user_hospital ((CASE WHEN 1=1 THEN user_id ELSE NULL END), hospital_id);
```

### 2.3 字段设计说明

| 分类 | 字段 | 设计说明 |
|-----|------|---------|
| 登录凭证 | username, password | username 全局唯一（函数索引），BCrypt 加密存储密码 |
| 身份信息 | real_name, phone, email, sex, avatar | sex 存储字典值字符串 |
| 账户分类 | account_type | 1=内部用户，2=外部用户，默认为 1 |
| 组织架构 | org_id, org_name, dept_id, dept_name | 含冗余字段优化查询 |
| 角色关联 | role_id, role_name, role_code | 必填，含冗余字段 |
| 业务扩展 | employee_no, specialty, qualification, settlement_type | specialty 逗号拼接多值；内部部门用户 employee_no 必填 |
| 列设置 | order_column_settings, design_column_settings | 用户个性化列显示配置，JSON 格式 |
| 安全控制 | status, login_fail_count, lock_time | 账户状态和登录失败锁定机制 |
| 医院关联 | sys_user_hospital.hospital_id | 引用 sys_org.id（orgType=1.3 的医院机构），非独立医院表 |

## 四、核心业务逻辑

### 4.1 用户创建流程

```
createUser(dto)
  │
  ├─1. roleId 必填校验（@NotNull 注解层保证）
  │
  ├─2. accountType 默认值：null → 1（内部用户）
  │
  ├─3. 校验用户名唯一性
  │    └─ 抛出 USER_EXISTS(603)
  │
  ├─4. 校验手机号唯一性
  │    └─ 抛出 USER_PHONE_EXISTS(604)
  │
  ├─5. 校验邮箱唯一性（如有）
  │    └─ 抛出 USER_EMAIL_EXISTS(636)
  │
  ├─6. 校验机构存在
  │    └─ 抛出 USER_ORG_NOT_FOUND(628)
  │
  ├─7. 校验部门存在（如有）
  │    └─ 抛出 USER_DEPT_NOT_FOUND(629)
  │
  ├─8. 部门类型分支逻辑（deptId 存在时）
  │    │
  │    ├─ deptType=1（内部部门）
  │    │    ├─ orgId 强制覆盖为系统配置 MANUFACTURER_ORG_ID
  │    │    │    └─ 配置缺失 → 抛出 SYSTEM_CONFIG_MISSING(627)
  │    │    └─ employeeNo 必填
  │    │         └─ 为空 → 抛出 EMPLOYEE_NO_REQUIRED(626)
  │    │
  │    └─ deptType=2（外部部门）
  │         ├─ 校验 orgId 属于该部门（sys_dept_org 关联）
  │         │    └─ 不属于 → 抛出 ORG_NOT_BELONG_TO_DEPT(623)
  │         └─ 校验 org 类型必须为经销商（orgType=1.2）
  │              └─ 不符合 → 抛出 ORG_TYPE_MUST_BE_DEALER(624)
  │
  ├─9. 校验角色存在，填充 roleName/roleCode/dataScopeType
  │
  ├─10. 专业方向校验（设计师/设计主管角色）
  │     └─ specialtyList 为空 → 抛出 USER_ROLE_SPECIALTY_REQUIRED(633)
  │
  ├─11. 医院范围处理
  │     └─ 仅当角色 dataScopeType="hospitals" 时
  │          ├─ hospitalIds 为空 → 抛出 USER_ROLE_HOSPITAL_SCOPE_REQUIRED(631)
  │          ├─ 校验所有 hospitalIds 在 sys_org 中存在（orgType=1.3）
  │          │    └─ 无效ID → 抛出 USER_HOSPITAL_INVALID(632)
  │          └─ UserHospitalService.assignHospitals(userId, hospitalIds)
  │
  ├─12. 填充冗余字段：orgName、deptName、roleName、roleCode
  │
  ├─13. 密码处理
  │     ├─ 提供密码：BCrypt 加密
  │     └─ 未提供：读取系统配置 DEFAULT_PASSWORD → BCrypt 加密
  │
  └─14. save(entity)
```

### 4.2 用户更新流程

```
updateUser(id, dto)
  │
  ├─1. 校验用户存在
  │    └─ 抛出 USER_NOT_FOUND(601)
  │
  ├─2. 校验手机号唯一性（排除自身）
  │    └─ 抛出 USER_PHONE_EXISTS(604)
  │
  ├─3. 校验邮箱唯一性（排除自身，如有）
  │    └─ 抛出 USER_EMAIL_EXISTS(636)
  │
  ├─4. 机构/部门/角色变更时重新校验并更新冗余字段
  │    ├─ orgId 变更 → 校验存在，更新 orgName
  │    ├─ deptId 变更 → 校验存在，更新 deptName；重新执行部门类型分支逻辑
  │    └─ roleId 变更 → 校验存在，更新 roleName/roleCode/dataScopeType
  │
  ├─5. 专业方向校验（同创建逻辑）
  │
  ├─6. 医院范围处理（基于生效角色的 dataScopeType）
  │    ├─ dataScopeType="hospitals"：hospitalIds 非空时调用 assignHospitals（含去重校验）
  │    └─ 角色从 HOSPITALS 切换为其他类型时：自动清空 sys_user_hospital 旧记录
  │
  └─7. updateById(entity)
```

### 4.3 密码管理

| 操作 | 接口 | 说明 |
|-----|------|------|
| 创建用户 | POST /api/system/user | 密码可选，未提供时使用系统配置 DEFAULT_PASSWORD |
| 重置密码 | PUT /api/system/user/{id}/reset-password | 强制重置为系统默认密码 |
| 修改密码 | PUT /api/system/user/{id}/change-password | 需验证旧密码 |

密码使用 BCryptPasswordEncoder 加密，存储格式为 `$2a$10$...`。

### 4.4 医院范围权限机制

#### 4.4.1 核心概念

- **启用条件**：角色 `dataScopeType="hospitals"` 时才分配医院范围
- **数据来源**：`sys_user_hospital` 表，`hospital_id` 引用 `sys_org.id`（orgType=1.3 的医院机构）
- **控制粒度**：用户级别的医院数据范围控制

#### 4.4.2 医院范围分配流程

```
assignHospitals(userId, hospitalIds)
  │
  ├─1. 校验用户存在 → USER_NOT_FOUND(601)
  ├─2. 对 hospitalIds 去重（distinct），再校验所有 ID 在 sys_org 中存在且 orgType=1.3
  │    └─ 无效ID → HOSPITAL_NOT_FOUND(632)
  ├─3. 删除旧关联（覆盖式）
  └─4. 批量插入新关联
```

#### 4.4.3 医院范围查询

| 方法 | 说明 |
|-----|------|
| `getHospitalIdsByUserId(userId)` | 获取单个用户的医院ID列表 |
| `listHospitalIdsByUserIds(userIds)` | 批量获取用户的医院ID列表 |
| `getHospitalsByUserId(userId)` | 获取单个用户的医院详情列表 |

### 4.5 关联模块说明

| 关联模块 | 关系 | 作用 |
|---------|------|------|
| OrgService | 用户 → 机构（N:1） | 用户必须归属某个机构；外部部门校验 orgId 属于部门且为经销商 |
| DeptService | 用户 → 部门（N:1） | 部门类型决定内部/外部分支逻辑 |
| RoleService | 用户 → 角色（N:1） | roleId 必填；决定 dataScopeType 和专业方向校验 |
| ConfigService | 用户 ← 配置 | DEFAULT_PASSWORD（默认密码）、MANUFACTURER_ORG_ID（厂商机构ID） |
| sys_org（医院） | 用户 ↔ 医院（N:N） | hospitalIds 引用 sys_org.id（orgType=1.3），通过 sys_user_hospital 关联 |

## 五、错误码定义

| 错误码 | 枚举值 | 说明 |
|-------|--------|------|
| 601 | USER_NOT_FOUND | 用户不存在 |
| 602 | USER_DISABLED | 用户已被禁用 |
| 603 | USER_EXISTS | 用户名已存在 |
| 604 | USER_PHONE_EXISTS | 手机号已存在 |
| 623 | ORG_NOT_BELONG_TO_DEPT | 所选机构不属于该部门 |
| 624 | ORG_TYPE_MUST_BE_DEALER | 机构类型必须为经销商 |
| 626 | EMPLOYEE_NO_REQUIRED | 内部部门用户工号必填 |
| 627 | SYSTEM_CONFIG_MISSING | 系统配置缺失（如 MANUFACTURER_ORG_ID） |
| 628 | USER_ORG_NOT_FOUND | 所属机构不存在 |
| 629 | USER_DEPT_NOT_FOUND | 所属部门不存在 |
| 631 | USER_ROLE_HOSPITAL_SCOPE_REQUIRED | 角色数据权限为医院范围，请选择可操作的医院 |
| 632 | USER_HOSPITAL_INVALID | 存在无效的医院ID |
| 633 | USER_ROLE_SPECIALTY_REQUIRED | 设计师/设计主管角色必须选择专业方向 |
| 634 | USER_SPECIALTY_INVALID | 专业方向无效 |
| 635 | USER_PASSWORD_WEAK | 密码强度不足 |
| 636 | USER_EMAIL_EXISTS | 邮箱已存在 |

## 六、数据权限设计

### 6.1 数据权限层级

| 值 | 常量 | 说明 |
|----|------|------|
| 1 | ALL | 全部数据（系统管理员） |
| 2 | ORG | 本机构数据 |
| 3 | SELF | 仅自己的数据 |
| 4 | HOSPITALS | 医院范围数据（通过 sys_user_hospital 限制） |
| 5 | DEPT | 本部门数据 |

### 6.2 医院范围权限的实现

1. 用户登录后，通过 `UserHospitalService.getHospitalIdsByUserId(userId)` 获取可访问的医院ID列表
2. 业务查询时在 Service 层添加 `hospital_id IN (...)` 条件
3. 仅当角色 `dataScopeType="hospitals"` 时才分配医院范围；其他 dataScopeType 的角色不写入 sys_user_hospital
