# 09_系统安全限流签名实现方案

## 一、模块概述

本模块在现有 SaToken Token 认证基础上，新增两层安全防护：

| 层级 | 功能 | 实现方式 |
|------|------|---------|
| 基础层 | 限流防刷 | `@RateLimit` + `RateLimitAspect`，Redis 固定窗口 |
| 增强层 | 请求签名验证 | `@RequireSign` + `SignAspect`，MD5 + nonce 防重放 |

两者均基于 AOP 注解体系，复用现有 `RedisTemplate<String, Object>`，无需引入新依赖。

## 二、限流防刷

### 2.1 核心文件

| 文件 | 说明 |
|------|------|
| `yigongbao-framework/.../annotation/RateLimit.java` | 限流注解 |
| `yigongbao-framework/.../aspect/RateLimitAspect.java` | 限流切面，`@Order(1)` |

### 2.2 注解定义

```java
@RateLimit(
    limit = 60,                        // 时间窗口内最大请求数，默认 60
    window = 60,                       // 时间窗口（秒），默认 60
    dimension = RateLimit.Dimension.USER  // USER 或 IP
)
```

`Dimension.USER`：已登录用户按用户ID限流，未登录自动降级为 IP 维度。
`Dimension.IP`：始终按客户端 IP 限流（适合登录等未登录接口）。

### 2.3 算法：Redis 固定窗口

使用 Lua 脚本保证 INCR + EXPIRE 原子性：

```lua
local c = redis.call('INCR', KEYS[1])
if c == 1 then redis.call('EXPIRE', KEYS[1], tonumber(ARGV[1])) end
if c > tonumber(ARGV[2]) then return 0 end
return 1
```

**Redis key 格式：**
- IP 维度：`rate:ip:{ip}:{uri}`
- 用户维度：`rate:user:{userId}:{uri}`

其中 `uri` 将 `/` 替换为 `_`，例如 `/system/auth/login` → `_system_auth_login`。

### 2.4 降级策略

Redis 不可用时 **fail-open**（放行请求），记录 WARN 日志，避免 Redis 故障导致全站不可用。

### 2.5 已标注接口

| 接口 | 配置 | 说明 |
|------|------|------|
| `POST /system/auth/login` | `limit=10, window=60, dimension=IP` | 登录接口，强制 IP 维度防暴力破解 |

其他业务接口按需标注，通用建议值：`@RateLimit`（默认 60次/分钟，USER 维度）。

### 2.6 超限响应

```json
{ "code": 429, "message": "操作过于频繁，请稍后再试", "data": null }
```

HTTP 状态码仍为 200（与系统统一响应规范一致）。

## 三、请求签名验证

### 3.1 核心文件

| 文件 | 说明 |
|------|------|
| `yigongbao-framework/.../annotation/RequireSign.java` | 签名验证注解 |
| `yigongbao-framework/.../aspect/SignAspect.java` | 签名验证切面，`@Order(2)` |
| `application-dev.yml` → `app.sign.secret` | 签名密钥配置 |

### 3.2 请求 Header

| Header | 说明 | 示例 |
|--------|------|------|
| `X-App-Key` | 应用标识 | `web` |
| `X-Timestamp` | 秒级时间戳 | `1746662400` |
| `X-Nonce` | 6位随机字符串 | `a1b2c3` |
| `X-Signature` | 签名结果（MD5，小写） | `8f4e2d1c...` |

### 3.3 签名算法

```
sign = MD5(appKey + timestamp + nonce + appSecret)
```

使用 `org.springframework.util.DigestUtils`（spring-web 自带）。

### 3.4 验证流程

```
1. Header 存在性校验     → 缺失返回 {"code":781, "message":"缺少签名参数：X-Xxx"}
2. timestamp 时间窗口    → 超过 5 分钟返回 {"code":782, "message":"请求已过期，请检查系统时间"}
3. nonce 防重放          → Redis SET NX，已存在返回 {"code":783, "message":"重复请求"}
4. 签名比对              → 不一致返回 {"code":784, "message":"签名验证失败"}
```

**nonce Redis key：** `sign:nonce:{nonce}`，value=`"1"`，TTL=5min。

签名失败时删除 nonce，允许客户端修正参数后重试（每次请求应生成新 nonce）。

### 3.5 密钥配置

```yaml
# application-dev.yml
app:
  sign:
    secret: ${APP_SIGN_SECRET:dev-secret-change-in-prod}
```

生产环境通过环境变量 `APP_SIGN_SECRET` 注入，不提交明文到 git。

### 3.6 安全定位（方案 A）

签名密钥存在于前端代码中，接受被逆向的风险。目标是**增加攻击成本**，防止低级爬虫和脚本，而非绝对安全。真正的安全保障由 HTTPS + SaToken Token 认证提供。

### 3.7 前端集成

```js
// src/utils/sign.js
import md5 from 'md5'

const APP_KEY = 'web'
const APP_SECRET = 'your-secret'  // 与后端 app.sign.secret 一致

export function buildSignHeaders() {
  const timestamp = Math.floor(Date.now() / 1000).toString()
  const nonce = Math.random().toString(36).slice(2, 8)
  const sign = md5(APP_KEY + timestamp + nonce + APP_SECRET)
  return {
    'X-App-Key': APP_KEY,
    'X-Timestamp': timestamp,
    'X-Nonce': nonce,
    'X-Signature': sign
  }
}
```

在 Axios 请求拦截器中对需要签名的接口注入 Header：

```js
axios.interceptors.request.use(config => {
  const needsSign = SIGN_REQUIRED_PATHS.some(p => config.url?.includes(p))
  if (needsSign) {
    Object.assign(config.headers, buildSignHeaders())
  }
  return config
})
```

## 四、AOP 执行顺序

两个切面同时标注时，执行顺序由 `@Order` 控制：

```
请求进入 → RateLimitAspect(@Order=1) → SignAspect(@Order=2) → 业务方法
```

先限流（轻量，单次 Redis INCR）再验签（两次 Redis 操作），避免无效签名计算消耗资源。
