## 一、需求背景

### 1.1 业务需求

企业需要区分自营业务和经销商业务，当前系统仅支持经销商机构类型（`1.2`），无法标识企业自营业务机构。

**核心需求**：
1. 新增"服务商"机构类型（`1.4`），表示企业自营业务机构
2. 新增"业务员（自营）"角色（`salesman-self`），用于处理自营业务订单
3. 服务商属于企业类型机构，而非外部业务类型
4. 业务员（自营）账户也属于企业类型账户（`6.1`）

### 1.2 架构设计决策

基于brainstorming分析，确认以下关键决策：

| 决策点 | 方案 | 理由 |
|--------|------|------|
| 服务商归属部门类型 | **企业部门（6.1）** | 服务商是企业自营机构，本质上是企业类型而非外部业务类型 |
| 服务商数量 | **可以有多个** | 支持企业建立多个自营业务机构（如不同区域分公司） |
| 企业机构绑定方式 | **从部门关联动态获取** | 废弃硬编码的"生产企业机构ID"配置，改为从 `sys_dept_org` 关联表获取 |
| salesman-self 数据权限 | **与 salesman 一致（HOSPITALS）** | 两者业务职能相同，仅账户分类不同 |
| 统计维度 | **后续确定** | 暂不实施统计逻辑调整 |

### 1.3 核心概念对比

| 维度 | 生产企业（1.1） | 服务商（1.4，新增） | 经销商（1.2） |
|------|----------------|---------------------|--------------|
| 机构类型 | 企业类型 | **企业类型** | 业务类型 |
| 归属部门类型 | 企业部门（6.1） | **企业部门（6.1）** | 业务部门（6.2） |
| 部门关联规则 | 唯一（1个企业部门→1个生产企业） | **唯一（1个企业部门→1个服务商）** | 多个（1个业务部门→多个经销商） |
| 账号前缀 | 必填 | **必填** | 必填 |
| 医院关联 | 不需要 | **需要（sys_org_hospital）** | 需要 |
| 典型角色 | designer、production-worker | **salesman-self（业务员-自营）** | salesman、regional-manager |
| 账户分类 | 企业账户（6.1） | **企业账户（6.1）** | 业务账户（6.2） |

## 二、架构设计

### 2.1 整体架构

```
系统机构体系
├── 企业类型机构
│   ├── 生产企业（1.1）
│   │   └── 归属：企业部门（6.1）
│   │   └── 角色：designer、production-worker、admin 等
│   │   └── 账户：企业账户（6.1）
│   └── 服务商（1.4）【新增】
│       └── 归属：企业部门（6.1）
│       └── 角色：salesman-self（业务员-自营）【新增】
│       └── 账户：企业账户（6.1）
└── 业务类型机构
    ├── 经销商（1.2）
    │   └── 归属：业务部门（6.2）
    │   └── 角色：salesman、regional-manager
    │   └── 账户：业务账户（6.2）
    └── 医疗机构（1.3）
```

### 2.2 核心设计原则

#### 原则1：企业部门的唯一性与灵活性平衡

**现状**：企业部门（6.1）强制绑定唯一的生产企业（硬编码 MANUFACTURER_ORG_ID）

**新设计**：
- 企业部门通过 `sys_dept_org` 关联企业机构（生产企业或服务商）
- 每个企业部门仍只能关联 **1个** 企业机构（保持唯一性）
- 不同企业部门可以关联不同类型的企业机构：
  - 设计部门 → 生产企业
  - 自营业务部门 → 服务商A
  - 区域自营部门 → 服务商B

**关键变化**：
```java
// 旧逻辑：硬编码
Long manufacturerOrgId = Long.valueOf(
    configService.getConfigValue(SystemConfigKeyEnum.MANUFACTURER_ORG_ID.getKey()));
dto.setOrgId(manufacturerOrgId);

// 新逻辑：从部门关联动态获取
List<Long> deptOrgIds = deptOrgMapper.selectList(
    new LambdaQueryWrapper<DeptOrgEntity>()
        .eq(DeptOrgEntity::getDeptId, dto.getDeptId()))
    .stream().map(DeptOrgEntity::getOrgId).collect(Collectors.toList());

if (deptOrgIds.size() != 1) {
    throw new BusinessException("企业部门必须关联唯一企业机构");
}
dto.setOrgId(deptOrgIds.get(0));
```

#### 原则2：角色权限的一致性

**salesman-self** 角色设计：
- 账户分类：企业账户（6.1）
- 数据权限：与 salesman 完全一致（HOSPITALS）
- 业务权限：与 salesman 完全一致（订单创建、查看、修改等）
- 差异点：**仅账户分类不同**，用于区分内部员工和外部业务员

#### 原则3：机构-医院关联的扩展

服务商需要维护服务范围（关联医院），逻辑与经销商一致：
- `sys_org_hospital` 表记录服务商与医院的关联关系
- 业务员（自营）创建订单时，选择的医院必须在服务商关联范围内
- 前端机构管理界面对服务商显示"关联医院"功能

WHERE role_id = @salesman_role_id AND is_deleted = 0;

- salesman-self 与 salesman 的业务权限完全相同
- 包括：订单创建、查看、修改、提交等所有订单相关权限

### 3.5 **【关键发现】数据迁移脚本（必须执行）**

#### 风险点：现有企业部门未维护 sys_dept_org 关联

**问题描述**：
- 现有系统通过硬编码的 `MANUFACTURER_ORG_ID` 配置（值为1）绑定生产企业
- 从 `init.sql` 可见，生产企业机构ID固定为1：`INSERT INTO sys_org (id, ...) VALUES (1, '嘉一高科（企业）', ...)`
- **但 `sys_dept_org` 表可能没有为现有企业部门创建关联记录**
- 修改后的代码从 `sys_dept_org` 动态获取机构，若无记录会导致用户创建失败

**数据迁移SQL（部署前必须执行）**：

```sql
-- ============================================================
-- 服务商功能数据迁移脚本
-- 执行时机：代码部署前
-- 功能：为现有企业部门补充与生产企业的关联记录
-- ============================================================

-- 1. 查询系统配置的生产企业机构ID（默认为1）
SET @manufacturer_org_id = (
    SELECT config_value 
    FROM sys_config 
    WHERE config_key = 'manufacturer.org.id' 
      AND is_deleted = 0
);

-- 2. 如果配置为空，使用默认值1（嘉一高科）
SET @manufacturer_org_id = IFNULL(@manufacturer_org_id, 1);

-- 3. 查询所有企业部门（dept_type = '6.1'）
SELECT 
    d.id AS dept_id, 
    d.dept_name, 
    IFNULL(do.org_id, '未关联') AS current_org_id
FROM sys_dept d
LEFT JOIN sys_dept_org do ON d.id = do.dept_id AND do.is_deleted = 0
WHERE d.dept_type = '6.1' 
  AND d.is_deleted = 0;

-- 4. 为所有未关联机构的企业部门补充关联记录
INSERT INTO sys_dept_org (dept_id, org_id, create_time, update_time, is_deleted)
SELECT 
    d.id, 
    @manufacturer_org_id, 
    NOW(), 
    NOW(), 
    0
FROM sys_dept d
WHERE d.dept_type = '6.1' 
  AND d.is_deleted = 0
  AND NOT EXISTS (
      SELECT 1 FROM sys_dept_org do 
      WHERE do.dept_id = d.id AND do.is_deleted = 0
  );

-- 5. 验证：查询企业部门关联情况
SELECT 
    d.id AS dept_id,
    d.dept_name,
    do.org_id,
    o.org_name,
    o.org_type
FROM sys_dept d
LEFT JOIN sys_dept_org do ON d.id = do.dept_id AND do.is_deleted = 0
LEFT JOIN sys_org o ON do.org_id = o.id AND o.is_deleted = 0
WHERE d.dept_type = '6.1' 
  AND d.is_deleted = 0
ORDER BY d.id;

-- 预期结果：所有企业部门都应该关联 org_id = 1（嘉一高科）
```

**执行结果验证**：
- 所有 `dept_type = '6.1'` 的部门都应该在 `sys_dept_org` 表中有对应记录
- `org_id` 应为生产企业的ID（默认为1）
- 如果企业有多个生产企业或服务商，需要手动调整关联关系

### 4.5 订单模块分析

#### OrderDataValidator.java

**结论**：**无需修改**

**原因**：

### 7.3 数据迁移风险

#### 风险点：现有企业部门未维护 `sys_dept_org` 关联

**问题描述**：
- 现有系统中，企业部门通过硬编码的 `MANUFACTURER_ORG_ID` 绑定生产企业
- `sys_dept_org` 表可能没有对应的关联记录
- 修改后，创建企业部门用户会因为找不到关联机构而失败

**应对方案**：数据迁移脚本

```sql
-- 1. 查询配置的生产企业机构ID
SET @manufacturer_org_id = (SELECT config_value FROM sys_config WHERE config_key = 'manufacturer.org.id' AND is_deleted = 0);

-- 2. 查询所有企业部门（dept_type = 6.1）
SELECT id, dept_name FROM sys_dept WHERE dept_type = '6.1' AND is_deleted = 0;

-- 3. 为所有企业部门补充 dept_org 关联记录
INSERT INTO sys_dept_org (dept_id, org_id, create_time, update_time, is_deleted)
SELECT id, @manufacturer_org_id, NOW(), NOW(), 0
FROM sys_dept
WHERE dept_type = '6.1' AND is_deleted = 0
  AND id NOT IN (SELECT dept_id FROM sys_dept_org WHERE is_deleted = 0);

-- 4. 验证：查询企业部门关联情况
SELECT d.id, d.dept_name, do.org_id, o.org_name, o.org_type
FROM sys_dept d
LEFT JOIN sys_dept_org do ON d.id = do.dept_id AND do.is_deleted = 0
LEFT JOIN sys_org o ON do.org_id = o.id AND o.is_deleted = 0
WHERE d.dept_type = '6.1' AND d.is_deleted = 0;
```

**执行时机**：在代码修改部署前执行，确保数据完整性。
